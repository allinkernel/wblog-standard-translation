## 0. 导读总览

### 0.1 本章在整卷中的位置

POSIX.1-2024 由四个主要部分（卷）组成：

| 卷 | 缩写 | 内容 | 本章中的称呼 |
|---|---|---|---|
| Base Definitions | XBD | 通用术语、概念、头文件定义、字符集、locale、正则表达式等 | 《基础定义》卷 |
| System Interfaces | XSH | C 语言函数接口（fork、exec、open、read…） | 《系统接口》卷 |
| Shell and Utilities | XCU | shell 命令语言 + 各种实用程序（命令） | 本卷 |
| Rationale | XRAT | 设计理由（informative） | 不在本章正文引用范围内 |

XCU 卷的**正文主体**是第 2 章（Shell 命令语言）和第 3 章（实用程序，每个工具一个 manpage 式的描述页）。
第 1 章是**开篇的"总纲"**：它不做具体规定，而是回答三个问题：

1. **本卷与其他卷是什么关系？**（1.1 节）
2. **本卷描述里反复出现的默认行为是什么？**（1.2、1.3、1.4 节）
3. **本卷的工具在系统里以什么形态存在？**（1.5、1.6、1.7 节）

### 0.2 为什么需要这样一章？

规范文档有一个矛盾：每一卷都要自洽可读，但内容又大量依赖其他卷。
如果每个实用程序描述都把"进程是什么、文件怎么创建"重写一遍，整卷会膨胀到不可维护，而且各处的措辞必然产生细微分歧。

第 1 章的解法是**"一次定义、处处引用"**：

- 凡是 XSH 卷已经精确定义的概念（进程属性、文件创建语义、路径名解析），本章只做**引用 + 少量默认假设**；
- 凡是 XCU 卷自己的"常规默认值"（选项怎么写、错误怎么办、退出状态怎么约定），本章**集中定义**，第 3 章每个工具页只要说"Default."或"None."即可；
- 后文（第 2、3 章）的工具描述遇到未加说明的细节，就回到本章找答案。

所以第 1 章读起来"很薄"，但它是整个 XCU 卷的**解释学基础**——读第 3 章任何一个工具页时，遇到"Default Behavior"字样，答案都在 1.4 节。

## 1. 引言 (Introduction)

### 1.1 与其他文档的关系 (Relationship to Other Documents)

**为什么存在这一节**

XCU 卷不重复发明轮子。它大量借用 XSH 卷（C 函数接口）和 XBD 卷（概念定义）的内容。
但"借用"需要一个**边界**：本卷到底默认哪些外部功能一定存在？本卷的描述与外部定义冲突时听谁的？

1.1 节就干这件事：

- **1.1.1**：列出 XSH 卷中本卷"假定全局可用"的功能（进程、文件、路径、locale…）；
- **1.1.2**：规定本卷工具内部算术/语义的"母语"是 ISO C 标准。

还有一个重要原则（1.1.1 开头两段）：

> 实用程序和函数描述的陈述在适当时**覆盖**这些默认值。

意思是：本章的默认假设只是"默认"。某个具体工具页如果写明了不同行为，以工具页为准。
这是贯穿整个 POSIX 的层级原则：**具体描述 > 章节默认 > 跨卷默认**。

#### 1.1.1 系统接口 (System Interfaces)

本卷每个工具都运行在某个进程里、要操作文件、要解析路径名。
1.1.1 把"每个 POSIX 系统都必须有的东西"固定下来，这样第 3 章描述工具时就不用每次重申。

##### 1.1.1.1 进程属性 (Process Attributes)

规范要求所有进程都具备下列属性（attributes），清单如下：

| 属性 | 通俗含义 | 在 shell 脚本里的体现 |
|---|---|---|
| Controlling Terminal | 控制终端 | 前台/后台作业、`jobs`、作业控制信号 |
| Current Working Directory | 当前工作目录 | `pwd`、相对路径的基准 |
| Effective Group ID / Effective User ID | 有效组 ID / 有效用户 ID | 决定文件访问权限；`id`、`setuid` 程序 |
| File Descriptors | 文件描述符 | `0/1/2` 标准输入输出错误；重定向 |
| File Mode Creation Mask | 文件模式创建掩码 | `umask`，新文件权限的"减去项" |
| Process Group ID | 进程组 ID | 作业控制的基础 |
| Process ID | 进程 ID | `$$` |
| Real Group ID / Real User ID | 真实组 ID / 真实用户 ID | `id -r`；登录身份 |
| Root Directory | 根目录 | `/`；`chroot` 改变它 |
| Saved Set-Group-ID / Saved Set-User-ID | 保存的设置组/用户 ID | setuid/setgid 切换 |
| Session Membership | 会话成员资格 | 会话（session）与进程组的关系 |
| Supplementary Group IDs | 补充组 ID | 附加组权限 |

> **核心思想**：本卷说"进程"时，指的是具备以上全部属性的实体。
> 实现可以加更多属性，但不能少——少了任何一个，工具描述就失去立足点。

##### 1.1.1.2 进程的并发执行 (Concurrent Execution of Processes)

本卷要求所有系统上：

1. 进程能**独立并发执行**（互不杀死对方）；
2. 进程能通过 `fork()` + `exec` 系列函数创建新进程，新进程继承 1.1.1.1 的全部属性。

> **关键概念**：`fork()` 复制进程，`exec` 替换进程映像。
> 本卷（XCU）不要求实现用某种特定机制，只要求"具有 fork+exec 的语义效果"。
> 这解释了 shell 为什么能 `cmd &`、管道为什么能同时跑两个进程。

##### 1.1.1.3 文件访问权限 (File Access Permissions)

一句话：**XBD 4.7 的文件访问控制机制必须适用于本卷所有文件**。
也就是说，`chmod` 的 rwx 位、属主/属组、以及权限检查规则，在本卷是硬性前提。
工具描述里"如果文件访问权限拒绝访问，请求的操作应失败"都是从这里来的。

##### 1.1.1.4 文件的读、写与创建 (File Read, Write, and Creation)

这一小节是整个第 1 章**信息密度最高**的地方，也是后面所有工具页"创建文件"行为的共同出处。

**（a）创建新文件的 7 条默认规则**

当工具要写一个不存在的文件时：

| # | 规则 | 直观理解 |
|---|---|---|
| 1 | 文件 user ID = 调用进程 effective user ID | 谁创建就是谁的 |
| 2 | 文件 group ID = 调用进程 effective group ID **或** 所在目录的 group ID | 组归属两种都允许（继承目录组是 BSD 风格） |
| 3 | 普通文件权限 = `S_IRUSR\|S_IWUSR\|S_IRGRP\|S_IWGRP\|S_IROTH\|S_IWOTH`（0666）再清除 umask 位；目录 = `S_IRWXU\|S_IRWXG\|S_IRWXO`（0777）再清除 umask 位 | 这就是 `open()` 的 0666/0777 惯例，最终权限 = 模式 & ~umask |
| 4 | 三个时间戳（访问/修改/状态更改）按 XBD 4.12 更新 | atime/mtime/ctime 语义 |
| 5 | 新目录必须为空；新普通文件长度为零 | 创建即"干净" |
| 6 | 创建符号链接：若目录无 `{POSIX2_SYMLINKS}` 生效，效果未定义 | 某些系统可禁用 symlink |
| 7 | 除非另有说明，创建的是普通文件 | 默认类型 = 普通文件 |

> **常见误解澄清**：很多程序员以为"新建文件权限=0666"，其实规范只说"0666 再清掉 umask 位"。
> 如果某工具描述写明了不同的模式（如 `touch` 有 -m 选项），以工具页为准——这正是 1.1 开头"覆盖默认值"原则的实例。

**（b）创建已存在文件时的动作表：怎么读这张 13 列大表**

表 `tagtcjh_9` 的结构是：

- **行** = 你想创建的"新类型"（New Type）：块特殊、字符特殊、目录、FIFO、符号链接、共享内存、信号量、消息队列、普通文件、套接字、类型化内存；
- **列** = 已存在文件的类型（B/C/D/F/L/M/P/Q/R/S/T）；
- **交叉格** = 当"想建 X、而那里已有 Y"时，工具必须采取的动作代码；
- 最后一列 = 通常用于创建该类型的函数（`mknod()`、`mkdir()`、`mkfifo()`、`symlink()`、`shm_open()`、`sem_open()`、`mq_open()`、`open()`、`bind()`）。

动作代码的含义（表下方的定义列表）：

| 代码 | 含义 | 举例 |
|---|---|---|
| F | 失败（Fail）：操作失败，工具继续或报错退出 | 想建目录但已存在同名普通文件 → F |
| FL | 跟随链接（Follow link）：按路径名解析跟随符号链接 | 想建普通文件、已有符号链接 → 对链接目标操作 |
| O | 打开 FIFO：若已有 FIFO，为写打开它（必要时阻塞等待读者） | 想建普通文件、已有 FIFO → O |
| OF | 按该文件类型定义的后果直接打开 | 已存在正是想要类型的设备文件 |
| RF | 普通文件已存在：不改变 UID/GID/权限、截断为零、更新时间戳 | `>` 重定向的经典行为 |
| — | 实现定义（implementation-defined） | 实现可自行规定 |
| U | 未指定（unspecified） | 什么都不保证 |
| `*` | 没有可移植的创建方式 | 如类型化内存 |
| `**` | 不可移植 | `mknod()` 本身 |

> **一行看懂表**：几乎所有"新类型"行，当已存在类型是 B/C/D/F/L 时都是 F（失败）；
> 只有"想建普通文件"这一行最丰富——R 列是 RF（截断）、L 列是 FL（跟随链接）、F 列是 O（打开 FIFO）。
> 这正是 shell 重定向 `> file` 的真实语义来源。

**（c）追加与读写**

- 追加（append）= 用 `O_APPEND` 且不带 `O_TRUNC` 打开；
- 读/写文件必须以对应访问模式打开；权限不足则操作失败。

> 你可以把 1.1.1.4 理解成“`open()`/`creat()` 的 shell 世界版说明书”。

**七个规则的 shell 场景示例**

把规则套到日常命令上，理解会深得多（以下都是规范语义的直接推论）：

| 场景 | 规则套用 | 结果 |
|---|---|---|
| `umask 022` 后 `echo x > newfile` | 规则 3：0666 清除掩码位 022 | 新文件权限 0644（rw-r--r--） |
| `umask 077` 后 `mkdir d` | 规则 3：目录 0777 清除掩码位 077 | 新目录权限 0700 |
| 重定向到已存在的普通文件 | 表：新类型 R、已有类型 R → RF | 文件被截断为零长度（UID/GID/权限不变） |
| 重定向 `>>` 到已存在文件 | 追加规则：O_APPEND 且不带 O_TRUNC | 数据追加到末尾 |
| `ln -s target link` 后 `> link` | 表：新类型 R、已有类型 L → FL | 跟随链接，对 target 操作（相当于 `> target`） |
| `rm` 正在被某进程写入的文件 | 1.1.1.5：链接计数减到零但仍有打开者 | 文件内容保留到引用关闭，写者继续写 |
| 创建文件时未设置 umask 相关位 | 规则 1-2：属主=调用者 effective ID，组=effective 组 ID 或目录组 ID | 新文件归属可预期 |

**（d）权限拒绝时的行为**

读/写文件必须以对应访问模式打开；如果文件访问权限拒绝访问，请求的操作应失败（fail）。
注意这里的措辞是“应失败”——工具页可能进一步规定失败后的动作（诊断消息、退出状态等），那些在 1.4 节的
CONSEQUENCES OF ERRORS 默认清单里。

**（e）与 XSH 卷的分工**

1.1.1.4 只规定“外部可观察的文件系统效果”。具体的错误码（EACCES、EEXIST…）、
打开标志的完整语义都在 XSH 卷的 `open()`/`creat()` 描述里。
本卷只说“应按照《系统接口》卷定义的特性”——需要实现细节时，去 XSH 卷查。

##### 1.1.1.5 文件移除 (File Removal)

删除文件的本质是**删目录项、减链接计数**。要点：

- 删除任何进程的根目录或当前工作目录 → 实现定义；
- 链接计数减到零且没人打开 → 空间释放、文件消失；
- 链接计数减到零但**还有进程打开** → 内容保留到引用关闭（这就是 Unix 里"删了还能读"的现象）；
- 空目录被删除时，若有人打开着，目录内容保留到引用关闭；
- 非空目录的删除只更新 ctime；
- 包含目录的 mtime/ctime 要更新。

> **为什么重要**：shell 脚本里 `rm` 一个正在被写的日志文件，写者还能继续写——正是这条语义。

##### 1.1.1.6 文件时间值 (File Time Values)

所有文件必须有三个时间值（atime/mtime/ctime），语义在 XBD 4.12。本小节只是把"必有"钉死。

##### 1.1.1.7 文件内容 (File Contents)

本节给"文件的 contents"一个**精确的操作性定义**：

```
while (read (fildes, buf, nbytes) > 0)
    ;
```

即：文件内容 = 用 `open(pathname, O_RDONLY)` + 连续 `read()` 读到的全部数据。
`nbytes` 未指定（以返回最多数据为准）；若 `read()` 会出错，出错点之后的数据算不算内容——未指定。

> **为什么需要**：工具描述里说"读取文件内容"时，必须有一个无歧义的参考实现。
> 这就是那个参考。它不要求实现真的用 read() 循环，只要求**效果等价**（呼应 1.1.1.11）。

##### 1.1.1.8 路径名解析 (Pathname Resolution)

路径名解析算法 = XBD 4.16（另见 XBD 4.8 文件层级）。本卷所有路径操作默认走这套算法。
"`a/../b` 怎么解析""符号链接怎么展开"等细节都在 XBD 4.16，工具页不再重复。

##### 1.1.1.9 更改当前工作目录 (Changing the Current Working Directory)

要改当前工作目录时，除非工具描述另有说明，**只要 `chdir()` 不失败就该成功**。
这等于说：工具页不需要逐个声明"我遵守 chdir 语义"，默认就是。

##### 1.1.1.10 建立区域设置 (Establish the Locale)

`setlocale()` 的功能在所有一致系统上可用；需要"国际操作环境"的工具可以设置 locale 类别。
这是工具能输出不同语言/排序/字符集消息的基础（结合 1.4 节的 LANG/LC_ALL/NLSPATH）。

##### 1.1.1.11 与函数等价的动作 (Actions Equivalent to Functions)

工具描述说"动作等价于 `open()`/`mkdir()`…"时，只要求**外部可观察效果**等价；
工具内部（仅工具自己可见的）状态不必等价。

> **关键概念**：这是"黑盒等价"原则。实现可以完全不用 C 函数，
> 只要文件系统上看到的最终结果一致即可——给实现留了极大的自由。

#### 1.1.2 源自 ISO C 标准的概念 (Concepts Derived from the ISO C Standard)

**为什么存在**

像 `bc`、`expr`、`awk`、`yacc`/`lex` 这类工具有自己的表达式语言和算术运算。
如果不规定“算术的精度、类型转换、控制流按什么来”，不同实现就会各说各话（比如整数溢出行为、除法舍入、类型提升）。

1.1.2 的回答很干脆：**除非特别说明，工具内部的算术和语义概念与 ISO C 标准等价**。
同时明确：不要求工具用 C 语言实现——只要求语义等价（再次呼应黑盒等价原则）。

##### 1.1.2.1 算术精度与运算 (Arithmetic Precision and Operations)

**两个硬性规定：**

| 数据类别 | 必须等价于 | 后果 |
|---|---|---|
| 整数变量与常量（含操作数、选项参数值） | ISO C 的 **signed long** | 至少 32 位、有符号；溢出行为以 C 语义为准 |
| 浮点数 | ISO C 的 **double** | 至少 IEEE-754 双精度级别 |

其他要点：

- 类型转换按 ISO C 规则（整型提升、隐式转换等）；
- 所有变量默认初始化为零（除非输入显式赋值）——这对 `bc`/`awk` 未初始化变量的行为很重要；
- 算术运算符与控制流关键字对照 ISO C 标准第 6.5/6.8 节，具体清单见表 `tagtcjh_10`。

**运算符对照表怎么读**（表 tagtcjh_10）：左边是工具表达式语言里出现的运算，右边是 ISO C 标准对应章节。
例如 `expr ? expr : expr` 对应 6.5.15 条件运算符，`&&`/`||` 对应 6.5.13/6.5.14。
有一个故意排除：**逗号运算符**（6.5.17）不需要实现支持（表中明确注释）。

> 实际影响：如果你在 `awk`/`bc` 里写表达式，可移植的程序应把整数当作 `long`、把浮点当作 `double` 来推理。

##### 1.1.2.2 数学函数 (Mathematical Functions)

凡与 ISO C 标准第 7.12 节（数学函数 `<math.h>`）和第 7.22.2 节（伪随机序列生成）同名的函数，
必须返回与调用 ISO C 对应函数等价的结果。

> 比如 `awk` 里的 `sin()`、`sqrt()`、`rand()` 的数值行为以 C 标准为基准，保证跨实现结果一致。

### 1.2 实用程序限制 (Utility Limits)

**为什么存在**

工具要处理多长的行？`bc` 允许多大的进制？正则重复多少次？
如果每个工具都自由发挥，可移植脚本就没法写——你不知道对方的极限是多少。

1.2 节把这类问题集中解决，机制是**花括号记法**：`{LIMIT}`。
注意：**花括号不是名字的一部分**，`{LINE_MAX}` 的名字是 `LINE_MAX`，花括号只是记号。

**两张表的分工**

| 表 | 名字 | 作用 |
|---|---|---|
| tagtcjh_11 | Utility Limit Minimum Values（实用程序限制最小值） | 一致实现**必须**提供的底线值；应用可以**无条件依赖** |
| tagtcjh_12 | Symbolic Utility Limits（符号化实用程序限制） | 实现**可以放宽**的值；通过符号名查询实际值 |

**第一张表（最小值，应用可直接依赖）：**

| 符号 | 含义 | 最小值 |
|---|---|---|
| `{POSIX2_BC_BASE_MAX}` | `bc` 的最大 `obase`（输出进制） | 99 |
| `{POSIX2_BC_DIM_MAX}` | `bc` 数组最大元素数 | 2048 |
| `{POSIX2_BC_SCALE_MAX}` | `bc` 最大 `scale`（小数位） | 99 |
| `{POSIX2_BC_STRING_MAX}` | `bc` 字符串常量最大长度 | 1000 |
| `{POSIX2_COLL_WEIGHTS_MAX}` | locale 定义中 `LC_COLLATE` 条目最大权重数 | 2 |
| `{POSIX2_EXPR_NEST_MAX}` | `expr` 括号嵌套最大层数 | 32 |
| `{POSIX2_LINE_MAX}` | 文本行最大长度（字节，含结尾换行） | 2048 |
| `{POSIX_RE_DUP_MAX}` | BRE/ERE 区间表达式最大重复次数 | 255 |

**第二张表（符号化，实际值可能更大）：**
去掉 `POSIX2_` 前缀的同名符号（`{BC_BASE_MAX}`、`{LINE_MAX}`…），最小值为对应 `POSIX2_` 值，
但具体实现上可能更大——用 `getconf` 查实际值。

**怎么查实际值：getconf / sysconf**

- `getconf` 实用程序或 `sysconf()` 函数返回每个符号在**该实现**上的值；
- 查到的值是**会话创建时确定、整个会话内可用**的最大（最宽松）值；
- 表中字面名称只适用于 `getconf`；高级语言绑定（C 语言接口）用各自的确切名称形式。

示例：

```sh
getconf LINE_MAX        # 通常是 2048 或更大
getconf POSIX2_LINE_MAX # 最小值版本
getconf BC_BASE_MAX
```

**与 XSH 数值限制的关系**

XSH 卷定义的所有数值限制（如 `{PATH_MAX}`）也适用于本卷；本卷所有工具隐式受其约束。

**限制值不等于保证可达**

**重要警告**：即使实现声明了某限制，应用**不一定真能到达**该值——
虚拟内存不足等资源问题可能提前失败。限制值只表示“实现没有施加更严格的任意限制”。

**`{POSIX2_SYMLINKS}`：逐目录可变的特例**

它可能在整个实现内是常量，也可能**随路径名不同而变化**（某些文件系统支持符号链接、某些不支持）：

- 涉及目录时：系统支持在该目录内创建符号链接；
- 涉及非目录文件时：其含义未定义。

> 这就是 1.1.1.4 第 6 条规则（创建符号链接效果未定义）的配套机制。

**限制的思维方式：最小值 vs 实际值 vs 可达值**

读 1.2 节时，脑中要区分三个层次：

1. **最小值（POSIX2_ 符号）**：一致实现必须提供，应用可无条件依赖；
2. **实际值（无前缀符号）**：实现可能放宽，用 `getconf` 查询；
3. **可达值（不保证）**：即使实现声明了某值，资源不足时仍可能达不到。

| 想表达什么 | 用哪个 | 例子 |
|---|---|---|
| “可移植脚本必须能跑” | 最小值 | `{POSIX2_LINE_MAX}` = 2048 |
| “我的系统能处理多长” | 实际值 | `getconf LINE_MAX` |
| “会不会一定失败” | 可达值 | 没有保证——别依赖 |

**会话（session）概念的提醒**

规范说实际值“在会话创建时确定，整个会话生存期内可用”。
这里的“会话”是进程会话（setsid 意义上的 session），不是 shell 的一次登录脚本。
含义是：限制值不会在运行中途悄悄变化——应用可以缓存查询结果。

**为什么 `{PATH_MAX}` 也适用**

XSH 卷的数值限制（`{PATH_MAX}`、`{NAME_MAX}`、`{ARG_MAX}` 等）对本卷全部适用。
比如路径名最长 `{PATH_MAX}`（通常 4096），工具处理路径名时隐式受此约束。
工具页里“路径名过长”类错误，多数都能追溯到这些 XSH 限制。

### 1.3 文法约定 (Grammar Conventions)

**为什么存在**

本卷描述某些工具（如 `bc`、`awk`、`yacc` 的语法）的**输入语法**时，用一套特殊的文法记法。
不解释这套记法，读者会误以为它是完整的 yacc 源文件。

**核心思想**

- 文法基于 `yacc` 语法，但**不是可运行的 yacc 输入**：词法处理和语义要求只用文字描述；
- 文法不是任何传统实现的源代码，也没用配套语义代码测试过——它只是**描述工具**；
- 实现不必用 yacc 或任何特定语言/算法，只要**支持的语法与文法表示的一致**即可。

**三种排版约定（看到就能认出）**

| 写法 | 含义 | 例子 |
|---|---|---|
| 首字母大写 | 保留字（语言关键字，终结符） | `While`、`Case` |
| 全大写 + 下划线 | 终结符（token） | `NEWLINE`、`ASSIGN_OP`、`NAME` |
| 全小写 | 非终结符（语法成分） | `command`、`pipeline` |

> 一句话记忆：**大写开头=关键字，全大写=token，小写=语法成分**。
> 以后读第 2 章 shell 语法、或 `awk`/`bc` 的语法框时，这套约定直接可用。

### 1.4 实用程序描述默认值 (Utility Description Defaults)

**为什么存在（本章最实用的一节）**

第 3 章每个实用程序页都按**固定模板**写：NAME、SYNOPSIS、DESCRIPTION、OPTIONS…直到 CHANGE HISTORY，共 21 个小节。
如果每个工具页都把“选项不认识怎么办”“标准错误什么时候用”写一遍，会重复几百次。

解法：1.4 节**一次定义所有小节的用途 + 全局默认值**。
工具页只需写“Default.”或“None.”，读者回这里查即可。

**21 个小节速查表**

| 小节 | 用途 | 常见默认值 |
|---|---|---|
| NAME | 工具名 + 一句话用途 | — |
| SYNOPSIS | 调用语法（选项、选项参数、操作数） | — |
| DESCRIPTION | 动作描述；复杂工具有 EXTENDED DESCRIPTION | — |
| OPTIONS | 选项及选项参数，如何改变行为 | “None.”= 无需支持任何选项 |
| OPERANDS | 操作数及作用 | “None.”= 无需支持操作数 |
| STDIN | 标准输入 | “Not used.”= 不读标准输入 |
| INPUT FILES | 除标准输入外的输入文件 | “None.”= 无需输入文件 |
| ENVIRONMENT VARIABLES | 影响工具的环境变量 | “None.”= 不受影响 |
| ASYNCHRONOUS EVENTS | 信号等事件处理 | “Default.”= 继承信号动作 |
| STDOUT | 标准输出 | “Not used.”= 不写标准输出 |
| STDERR | 标准错误 | 默认：仅诊断消息 |
| OUTPUT FILES | 创建/修改的文件 | “None.”= 不创建文件 |
| EXTENDED DESCRIPTION | 复杂命令语言的描述位置 | “None.”= 无需进一步描述 |
| EXIT STATUS | 返回值与条件 | 0=成功完成；>0=错误 |
| CONSEQUENCES OF ERRORS | 出错时对环境的影响 | “Default.”= 影响未指定 |
| APPLICATION USAGE | 使用建议（informative） | — |
| EXAMPLES | 示例（informative） | — |
| RATIONALE | 设计理由（informative） | — |
| FUTURE DIRECTIONS | 未来方向（informative） | — |
| SEE ALSO | 相关条目（informative） | — |
| CHANGE HISTORY | 变更史（informative） | — |

**必须记住的全局默认值（重点）**

**（1）OPTIONS：识别不出就报错**

- 不认识的选项 / 缺少必需的选项参数 → 向标准错误发诊断消息，退出状态指示出错；
- 所有工具必须支持**八位透明**（eight-bit transparency）：参数中的任意 8 位字节值都能处理（不把字节当控制字符/元字符）；
- 接受操作数但不接受选项的工具，必须认识 `--`（作为第一个参数时丢弃）：

  ```sh
  foo -- -myfile   # 避免 -m 被当作扩展选项
  ```

> `--` 约定的意义：应用需要一种方式“屏蔽”实现可能提供的任意扩展选项。

**（2）OPERANDS：按顺序、可指定标准输入**

- 操作数按命令行顺序处理；
- 若某工具允许 `-` 表示“用标准输入”，会明确写出；同一命令里多次用 `-` 表示标准输入 → 未指定。

**（3）STDIN：后台脚本别用交互功能**

- 标准输入接终端时，后台运行的工具可能因读取输入而停止——所以**不要**在要放后台的脚本里用交互特性；
- 标准输入的格式不得依赖环境变量的存在或值。

**（4）INPUT FILES：可查找文件的位置保证**

- 处理可查找（seekable）输入文件时，工具提前正常终止必须把**文件偏移**留在“最后处理的字节之后”；
- 不可查找文件的偏移状态未指定；
- 因此这三个命令**不一定等价**：

  ```sh
  tail -n +2 file
  (sed -n 1q; cat) < file   # 仅当 file 可查找时与第一个等价
  cat file | (sed -n 1q; cat)  # 偏移未指定
  ```

- 文本文件处理：输入非文本文件时结果未定义；
- 续行约定（转义换行）：一组续行累计不能超过 `{LINE_MAX}`；转义换行后立刻 EOF → 未指定；
- 记录格式用类似 C `printf()` 的记法（XBD 5 章）；
- 实现必须**记录**受非明显资源限制的工具（如目录树深度限制）。

**（5）ENVIRONMENT VARIABLES：只有写明的才生效**

- 全局影响变量：`LANG`、`LC_ALL`，以及 XSI 选项下的 `NLSPATH`（XBD 8 章）；[译者注：原文中 XSI 选项内容以 opt-start/opt-end 图标标示起止，此处以文字表示]；
- 本卷描述的环境变量**不得以其他方式**影响工具行为；未描述变量的影响未指定；
- 用环境变量选工具时（如 `make` 的 `CC`），该字符串走 `PATH` 路径搜索；
- 环境变量名/值也要八位透明。

**（6）ASYNCHRONOUS EVENTS：信号默认继承**

“Default.”= 按信号动作继承规则：父进程忽略就忽略；父进程是默认动作就按默认动作执行。
需要终止时，工具可先做清理、恢复默认动作、再向自己重发信号。

**（7）STDOUT / STDERR：输出格式与“display”动词**

- STDOUT 不依赖环境变量；用“display”描述的输出在输出指向终端时必须直接写终端；
- STDERR 默认只用于诊断消息（出错时）；`LC_MESSAGES` 影响诊断消息语言惯例；
- 后台脚本同样别用标准输出/错误的交互功能。

**（8）OUTPUT FILES：临时文件的规矩**

- 临时文件命名必须保证不同工具/多实例可并发（只依赖进程 ID 之类的特性），两个例外：
  1. 名称空间之外的资源（磁盘空间、目录项、进程数）不保证；
  2. 工具间传递的固定名文件（如 `lex` 生成 `lex.yy.c`）例外；
- 实现创建的临时文件在成功退出/错误退出/被 SIGHUP、SIGINT、SIGTERM 终止前必须删除；
- SIGQUIT 一般直接终止（绕过恢复动作）；
- 临时文件位置建议用 `TMPDIR`。

**（9）EXIT STATUS：0 成功、>0 出错，别依赖具体错误码**

- 若未列具体数值：0=成功，>0=错误；
- **严格一致应用不应依赖范围内的具体值**（比如“1=文件不存在”），要测试“是否为 0”；
- 未列出的错误条件可用未列出的特定值表示。

**（10）CONSEQUENCES OF ERRORS：出错时的默认责任清单**

除非工具页另有说明，每个工具必须：

1. 对某操作数无法执行请求的动作 → 诊断消息到标准错误 + 继续下一个操作数 + 最终退出状态指示出错（递归遍历工具同理）；
2. 选项/选项参数无法执行 → 诊断 + 出错退出状态；
3. 不可恢复错误 → 以指示出错的退出状态退出；
4. 任何错误条件 → 写诊断消息到标准错误。

可能的善后动作：删除临时/中间文件、删除不完整文件、检查文件系统/目录有效性。

**（11）informative 小节（APPLICATION USAGE ~ CHANGE HISTORY）**

这些小节**不是规范要求**（informative），只是建议、示例、理由、历史。
示例与规范性内容冲突时，**规范性材料优先**。

**最后一段的提醒**

工具若调用其他工具/应用程序（如把命令串传给 shell），被调用者的外部影响/效果
（STDIN、STDOUT、错误后果等）**不在调用者的工具页里描述**——要看被调用工具自己的页面。

### 1.5 支持任意大小文件的实用程序的注意事项 (Considerations for Utilities in Support of Files of Arbitrary Size)

**为什么存在**

某些工具处理文件时要写“大小相关数值”（文件大小、偏移量、行号、块计数），或要解析含此类数值的命令行参数。
如果实现把这类值塞进 32 位整数，大文件（>2GB）场景就会出错。
1.5 节点名一批工具，要求它们**支持大到实现可创建的最大值的任意大小文件**。

**被点名的 26 个工具**

| 工具 | 用途 | 工具 | 用途 |
|---|---|---|---|
| *basename* | 返回路径名非目录部分 | *ls* | 列出目录内容 |
| *cat* | 连接并打印文件 | *mkdir* | 创建目录 |
| *cd* | 更改工作目录 | *mv* | 移动文件 |
| *chgrp* | 更改文件组属主 | *pathchk* | 检查路径名 |
| *chmod* | 更改文件模式 | *pwd* | 返回工作目录名 |
| *chown* | 更改文件属主 | *rm* | 移除目录项 |
| *cksum* | 写校验和与大小 | *rmdir* | 移除目录 |
| *cmp* | 比较两个文件 | *sh* | shell，标准命令语言解释器 |
| *cp* | 复制文件 | *test* | 求值表达式 |
| *dd* | 转换并复制文件 | *touch* | 更改文件访问/修改时间 |
| *df* | 报告可用磁盘空间 | *ulimit* | 设置/报告文件大小限制 |
| *dirname* | 返回路径名目录部分 | | |
| *du* | 估算文件空间使用 | | |
| *find* | 查找文件 | | |
| *ln* | 链接文件 | | |

> 注意 *dd*、*du*、*find*、*ls*、*cksum*、*df*、*ulimit* 都是“要输出/处理大数值”的典型代表。

**两个豁免（不必支持任意大文件）**

1. **把文件当命令脚本/配置/控制文件用**：如不要求 `sh` 能读任意大的 `.profile`；
2. **shell 输入输出重定向**：不要求 `sum < file`、`echo foo > file` 对任意大的现有文件成功。

> 为什么豁免？脚本和重定向的“大文件”场景极少且成本高；规范的务实取舍。

### 1.6 内置实用程序 (Built-In Utilities)

**为什么存在**

工具实现有两种形态：独立可执行文件，或 shell 内部的内置（built-in）。
内置能提高性能（省去 fork/exec）或实现独立进程做不到的功能（如 `cd`、`umask` 必须改 shell 自身状态）。

**三种“内置”概念的区分（易混淆，重点）**

| 概念 | 英文 | 含义 | 关键点 |
|---|---|---|---|
| 常规内置 | regular built-in | shell 内部实现的工具 | 任何标准工具都可做成常规内置 |
| 特殊内置 | special built-in | 第 2 章 2.15 定义的 14 个特殊工具 | 语法/执行规则特殊（见下） |
| 内在实用程序 | intrinsic utility | 第 1.7 节点名的 16 个工具 | **不受 PATH 搜索约束** |

**核心规定**

除以下两类外，**所有标准工具都必须能以独立可执行文件形态存在**（可通过 `exec` 函数族访问）：

- 2.15 的特殊内置；
- 1.7 的内在实用程序（`kill` 除外）。

为什么？因为 `env`、`find`、`nice`、`nohup`、`time`、`xargs` 这些工具需要**直接调用**其他工具
（例如 `find -exec cmd`、`xargs cmd`、`nohup cmd`），被调用的工具必须是可执行文件。

> 一句话：**shell 可以把任何工具做成内置提速，但除了特殊内置和内在实用程序，
> 每个工具都必须保留“可执行文件”的形态**，否则无法被其他工具调用。

**特殊内置（special built-in）是什么**

第 2 章 2.15 定义了一组“特殊内置实用程序”，包括 `.`（dot）、`:`（colon）、`break`、`continue`、
`eval`、`exec`、`exit`、`export`、`readonly`、`return`、`set`、`shift`、`times`、`trap`、`unset`。
它们“特殊”在：

- 由 shell 直接执行，**不创建独立进程**；
- 语法错误会**导致 shell（或脚本）退出**——这是与普通命令最大的区别；
- 变量赋值给它们时，赋值**影响当前 shell 环境**（普通命令的赋值只影响命令本身）。

> 为什么 1.6 节要把特殊内置排除在“必须可独立执行”之外？
> 因为它们的语义（修改当前 shell 状态、语法错误即退出）在独立进程里根本无法实现。

**三类内置的识别速记**

| 碰到的情况 | 属于 | 关键后果 |
|---|---|---|
| `cd`、`umask`、`alias`、`read`… | 内在实用程序 | 不走 PATH，无法用同名可执行文件覆盖 |
| `.`、`:`、`exec`、`exit`、`export`… | 特殊内置 | 不 fork；语法错误使 shell 退出 |
| `cat`、`ls`、`grep`…（若内置） | 常规内置 | 提高性能；但必须同时有可执行文件形态 |

### 1.7 内在实用程序 (Intrinsic Utilities)

**为什么存在**

`cd`、`umask`、`read` 这类工具**本质上必须修改 shell 自身状态**，无法用外部程序实现；
而 `alias`、`jobs`、`fg`、`bg` 等又必须访问 shell 内部数据结构。
它们被固定为“内在”工具，命令搜索时不走 `PATH`（见第 2 章 2.9.1.4）。

**16 个内在实用程序清单**

| | | | | | |
|---|---|---|---|---|---|
| *alias* | *command* | *getopts* | *kill* | *ulimit* | *wait* |
| *bg* | *fc* | *hash* | *read* | *umask* | |
| *cd* | *fg* | *jobs* | *type* | *unalias* | |

**实践含义**

- **应用无法用 `PATH` 里的同名可执行文件覆盖它们**（这正是“内在”的意义）；
- 因此规范建议：实现**不要**把清单之外的任何工具设为内在——否则应用将无法覆盖它；
- 是否把额外工具设为内在是实现定义的。

> 试着 `which cd`：多数 shell 会回答“shell builtin”——`cd` 的 PATH 版本要么不存在，要么只是摆设。

## 附录 A：常见问题 (FAQ)

**Q1：工具页里写 “Default.” 是什么意思？**

A：指向 1.4 节对应小节的默认行为。例如 ASYNCHRONOUS EVENTS 的 “Default.” 表示按信号继承规则处理。

**Q2：工具页写 “None.” 呢？**

A：该小节无内容/无要求。如 OPTIONS 为 “None.” 表示实现无需支持任何选项（但按 1.4 仍须认识 `--`）。

**Q3：为什么 `> file` 能截断文件，而 `>> file` 是追加？**

A：见 1.1.1.4 的“创建已存在文件时的动作”表：想建普通文件而已有普通文件 → RF（截断为零长度）；追加则用 O_APPEND 语义。

**Q4：为什么有时“删不掉”的文件还能继续被写？**

A：1.1.1.5：链接计数减到零但仍有进程打开时，文件内容保留到所有引用关闭。

**Q5：脚本里一行最长能多长？**

A：可移植地依赖 `{POSIX2_LINE_MAX}` = 2048 字节（含换行）；更长的行在部分实现上可用 `getconf LINE_MAX` 查询。

**Q6：`--` 是干什么的？**

A：1.4 OPTIONS 默认值：让操作数免受实现扩展选项的影响，如 `foo -- -myfile`。

**Q7：为什么 `awk` 的整数表现得像 C 的 long？**

A：1.1.2.1：工具内部算术语义等价于 ISO C 标准（整数=signed long、浮点=double）。

**Q8：为什么 `alias`、`cd` 没法用 PATH 覆盖？**

A：1.7：它们是内在实用程序，命令搜索不走 PATH。

**Q9：工具说自己“等价于 open()”是什么意思？**

A：1.1.1.11：只要求外部效果等价，内部实现随便。

**Q10：环境变量会影响工具行为吗？**

A：只影响工具页 ENVIRONMENT VARIABLES 小节写明的变量；全局的 `LANG`/`LC_ALL`（和 XSI 的 `NLSPATH`）除外。

**Q11：工具说“文件内容”时，到底指什么？**

A：1.1.1.7：等价于 `open(pathname, O_RDONLY)` 后连续 `read()` 读到的全部数据。

**Q12：为什么 `(sed -n 1q; cat) < file` 不一定等于 `tail -n +2 file`？**

A：1.4 INPUT FILES：只有可查找文件才保证偏移停留在“最后处理字节之后”；管道/不可查找文件偏移未指定。

**Q13：诊断消息的语言是什么决定的？**

A：1.4 STDERR：`LC_MESSAGES`（以及 XSI 的 `NLSPATH`）影响未指定格式的诊断消息的语言与文化惯例。

**Q14：示例（EXAMPLES）里的命令带引号，为什么？**

A：1.4 EXAMPLES：示例展示命令如何正确传给 shell 或 `system()`，因此加了引号；用 `exec` 族直接调用时不需要。

## 附录 B：工具页走查——把 1.4 节用起来

以第 3 章一个典型过滤器工具页为例，走一遍 21 个小节的阅读流程（具体工具不同，此处讲通用方法）：

1. **NAME**：先确认工具名与一句话用途——判断是不是你要找的工具；
2. **SYNOPSIS**：看语法骨架：哪些选项、哪些操作数；
3. **DESCRIPTION**：读行为描述；复杂的看 EXTENDED DESCRIPTION；
4. **OPTIONS**：逐个选项查语义；若写 “None.”，记住 1.4 的默认：仍须认识 `--`；
5. **OPERANDS**：操作数含义与顺序；`-` 是否表示标准输入；
6. **STDIN / INPUT FILES**：输入从哪来、什么格式；注意“文本文件”前提与 `{LINE_MAX}` 续行限制；
7. **ENVIRONMENT VARIABLES**：哪些变量影响行为（默认只有 `LANG`/`LC_ALL` 全局生效）；
8. **ASYNCHRONOUS EVENTS**：“Default.” = 按信号继承规则；
9. **STDOUT / STDERR / OUTPUT FILES**：输出内容、诊断消息用途、创建/修改哪些文件（含临时文件规矩）；
10. **EXIT STATUS**：0=成功；>0=错误；别依赖具体错误码；
11. **CONSEQUENCES OF ERRORS**：出错后的默认责任（诊断到标准错误、继续处理、最终状态指示出错）；
12. **informative 小节**：APPLICATION USAGE 给建议、EXAMPLES 给示例、RATIONALE 讲理由、
    FUTURE DIRECTIONS 看走向、SEE ALSO 找相关页、CHANGE HISTORY 看版本演化。

> 实际阅读时：**先看 SYNOPSIS + EXIT STATUS，再回读 DESCRIPTION**，效率最高。
> 遇到 “Default.” / “None.” / “Not used.” 就翻回本导读 1.6 节查默认含义。

## 附录 C：自测题（答案在题目下方，先做后看）

**1. `{LINE_MAX}` 的花括号有意义吗？**

答案：没有。花括号只是记号，名字是 `LINE_MAX`；最小值 `{POSIX2_LINE_MAX}` = 2048 字节（含换行）。

**2. 一个工具页 OPTIONS 写 “None.”，它还需要认识 `--` 吗？**

答案：需要（若它接受操作数）。1.4 OPTIONS 默认：接受操作数但不接受选项的工具，必须把 `--` 作为第一个参数丢弃。

**3. `umask 022` 时 `echo hi > new`，`new` 的权限是什么？**

答案：0666 清除 022 → 0644（rw-r--r--）。规则见 1.1.1.4 第 3 条。

**4. `> file`（file 已存在）会发生什么？**

答案：RF 语义——不改变 UID/GID/权限，截断为零长度，更新时间戳。见“创建已存在文件时的动作”表。

**5. 为什么 `cd` 不能是外部可执行文件？**

答案：`cd` 是内在实用程序（1.7），且必须修改 shell 自身的当前工作目录，外部进程改不了调用者的目录。

**6. “等价于 open()”要求实现真的调用 open() 吗？**

答案：不要求。1.1.1.11 只要求外部效果等价（黑盒等价）。

**7. 工具删除一个正被其他进程打开的文件，会发生什么？**

答案：链接计数减到零但内容保留到所有引用关闭（1.1.1.5）。

**8. 哪些工具可以不受 PATH 搜索约束？**

答案：内在实用程序（1.7 的 16 个）。注意：特殊内置不涉及 PATH 搜索问题，它们是 shell 语法的一部分。

**9. `getconf LINE_MAX` 和 `getconf POSIX2_LINE_MAX` 区别？**

答案：前者是该实现的实际值（可能更大），后者是最小保证值。见 1.2。

**10. 工具页 RATIONALE 小节是必须遵守的吗？**

答案：不是。它是 informative（提供信息的），不构成要求；与规范性内容冲突时以规范性内容为准。

**11. 后台脚本为什么别用交互功能？**

答案：标准输入/输出/错误接终端时，后台工具可能因读写而停止（1.4 STDIN/STDOUT/STDERR）。

**12. `awk` 里的整数溢出行为按什么来？**

答案：按 ISO C 标准的 `signed long` 语义（1.1.2.1）。

**13. 实现能不能把 `ls` 也做成“内在实用程序”？**

答案：技术上可以实现定义，但规范建议不要（应用无法覆盖），且 `ls` 不在 1.7 清单里。

**14. 诊断消息应写到哪里？**

答案：标准错误（stderr）；默认仅在出错时输出（1.4 STDERR / CONSEQUENCES OF ERRORS）。

**15. 工具处理“文本文件”时给了二进制输入，结果？**

答案：未定义（1.4 INPUT FILES），除非工具页另有说明。

## 结语：读完后你应该带走什么

1. **遇到工具页默认值，回 1.4 查**；遇到文件语义，回 1.1.1.4 查。
2. **可移植脚本的底线**：一行 2048 字节、`expr` 嵌套 32 层、`bc` 进制 99——1.2 表里有数。
3. **工具实现形态**：特殊内置与内在实用程序之外，每个工具都必须有可执行文件形态。
4. **黑盒等价**：规范关心外部效果，不关心内部实现——这给了实现（和你的脚本）最大的自由。
