导读：XSH 卷 1. 引言

0. 导读总览

这一章是全卷的"开卷说明"，篇幅不大，却决定了你读后面两章的方式。它只回答三个问题：这一卷是干什么的（1.）、它跟 ISO C 标准是什么关系（1.1）、第 3 章里那些函数条目该怎么读（1.2）。

阅读建议：

  • 先通读一遍本章，建立"XSH 卷 = 系统接口（C 语言层）"的整体印象；
  • 之后每读一个具体函数条目，都可以回来对照 1.2 的条目格式，分清哪些小节"说了算"；
  • 遇到 CX 标记时，回看 1.1 与基础定义卷的 1.8.1 代码一节。

关于本导读：标题编号与直译一一对应；"为什么存在 / 核心机制 / 易错点 / 延伸阅读"是导读自己的组织方式，不是规范内容，也不参与编号。

1. 引言 (Introduction)

为什么存在：一句话划定全卷范围。XSH（System Interfaces）是 POSIX.1-2024 的组成卷之一，本卷描述"由符合 POSIX 的系统提供给应用程序的接口"。注意主语是接口——C 语言层的函数与头文件，而不是 shell 命令（那些在命令与工具卷 XCU），也不是术语与约定（那些在基础定义卷 XBD）。这一句定位，决定了你遇到任何函数问题时该翻哪一卷。

核心机制：本卷的内容主体是第 3 章"系统接口"：按字母顺序排列的函数与头文件条目；第 2 章"通用信息"则集中处理错误编号、目录项、通用概念等被各条目反复引用的材料。第 1 章很短，因为它的任务是"说明规则"而不是"给出内容"：读完它，你应该知道本卷与 ISO C 的关系（1.1）、条目由哪些小节组成、其中哪些是规范性的（1.2）。

易错点：

  • 把第 1 章当"内容概要"读，以为读完就了解了系统接口——真正的内容在第 3 章，第 1 章只是使用说明；
  • 把"系统接口"与"系统调用"混为一谈：XSH 描述的是 C 语言接口，其中不少（如 printf）在 ISO C 标准里就有，根本不是内核调用；
  • 忽略本卷与其它卷的分工，例如把 errno 错误编号的定义、头文件的通用约定错当成 XSH 的专属内容——它们分散在 XBD 与 XSH 第 2 章中。

延伸阅读：XSH 2. 通用信息（General Information）；XSH 3. 系统接口（System Interfaces）的条目全集；XBD 第 1 章（本卷使用的约定、术语与 CX 标记）。

1.1 与其他正式标准的关系 (Relationship to Other Formal Standards)

为什么存在：POSIX 系统接口以 C 语言为宿主，不谈清与 ISO C 标准的关系，"这个函数是 C 的还是 POSIX 的"就会永远说不清。本节就是划定这条边界：哪些内容来自 ISO C，哪些是 POSIX 的扩展。

核心机制：本卷对齐的标准是 ISO/IEC 9899:2018（ISO C，即 C17），除另有说明外，本卷与它保持一致。当某个函数或头文件在 ISO C 中有对应版本时，规范会酌情加上 CX 标记，标明 ISO C 在哪些地方被扩展；CX 标记的定义和用法见基础定义卷的 1.8.1 代码一节。规范还明确：本卷与 ISO C 之间的任何冲突"均属无意"——意思是作者意图是兼容，读者若发现冲突，应按规范编写瑕疵看待，而不是当作有意为之的差异。此外，数学函数被允许但不要求支持 IEEE Std 754-1985 与 IEEE Std 854-1987 两个浮点标准。

易错点：

  • 把 CX 当作"可选"的同义词：它只是"此处扩展了 ISO C"的标注，具体条目里哪些扩展是必选、哪些可选，要以该条目的规范性文字为准，不能只看标记；
  • 误以为本卷覆盖整个 ISO C：本卷只收录与系统接口相关的部分，其余内容以 ISO C 标准本身为准；
  • 把 IEEE 754/854 的支持当成本卷的必备要求：规范措辞是"允许（但不要求）"，移植浮点代码时不能默认所有实现都提供该支持。

延伸阅读：XBD 1.8.1 代码（CX 标记的正式定义）；XSH 3. 系统接口中带 CX 标记的具体条目。

1.2 条目的格式 (Format of Entries)

为什么存在：第 3 章有几百个条目，格式不统一就无法快速查证。本节给出条目通用模板，并明确地划出一条最重要的分界线：哪些小节是规范性的、哪些只是信息性的。

核心机制：条目由一组固定小节组成：NAME（名称）、SYNOPSIS（提要）、DESCRIPTION（说明）、RETURN VALUE（返回值）、ERRORS（错误）、EXAMPLES（示例）、APPLICATION USAGE（应用用法）、RATIONALE（理由）、FUTURE DIRECTIONS（未来方向）、SEE ALSO（参见）、CHANGE HISTORY（变更历史）。其中只有前五节中与一致性相关的部分——SYNOPSIS、DESCRIPTION、RETURN VALUE、ERRORS——是规范性的；从 EXAMPLES 往后的所有小节都明确标注为信息性（informative），供理解与参考，不增加任何要求。

几个关键语义值得细读：

  • SYNOPSIS：给出使用该函数所需的头文件（如 #include <stdio.h>）与调用形式，是"能不能用、怎么用"的第一依据；
  • RETURN VALUE 中的"成功完成"按两种情形区分：对定义了错误的函数，成功意味着执行期间未检测到任何错误；对未定义任何错误的函数，成功意味着"如果实现检查错误，则未检测到任何错误"——后半句是典型的"像检查了一样"的质量语言，允许实现干脆不检查；
  • ERRORS：给出出错时经符号 errno 返回的错误值；"未定义任何错误"意味着错误值（如果有）由实现决定。

易错点：

  • 拿 EXAMPLES 或 APPLICATION USAGE 当规范依据：它们明确是信息性的，与规范性部分冲突时以规范性材料为准（EXAMPLES 一节甚至专门写了这句话）；
  • 把"成功完成"理解为"保证不出错"：规范只承诺"未检测到错误"，错误检测不到并不等于错误不存在；
  • 无条件读取 errno：只有当函数在 ERRORS 中定义了错误时，errno 才有确定含义；对未定义错误的函数，返回值和 errno 都可能取决于实现；
  • 忽略 SYNOPSIS 中的头文件列表：漏掉 #include 是未定义行为的高发来源，头文件没列出的用法不要指望可移植；
  • 把 RATIONALE 当规范读：它记录"为什么这样定"以及标准制定者纳入或舍弃特性的原因，是理解设计意图的第一手材料，但不改变要求。

延伸阅读：XSH 3. 系统接口（全部条目的集合）；XSH 2.3 错误编号（Error Numbers，ERRORS 中符号名的权威清单）；XBD 1.8.1 代码（CX 标记）。
