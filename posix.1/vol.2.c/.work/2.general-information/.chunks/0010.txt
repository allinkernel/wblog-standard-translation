[h3_01017] [A1188][/A1188]2.9 Threads
[p_01018] This section defines functionality to support multiple flows of control, called &quot;threads&quot;, within a process. For the definition of threads, see XBD [A1189][I1190]3.388 Thread[/I1190][/A1189].
[p_01019] The specific functional areas covered by threads and their scope include:
[li_01020] Thread management: the creation, control, and termination of multiple flows of control in the same process under the assumption of a common shared address space
[li_01021] Synchronization primitives optimized for tightly coupled operation of multiple control flows in a common, shared address space
[h4_01022] [A1191][/A1191]2.9.1 Thread-Safety
[p_01023] All functions defined by this volume of POSIX.1-2024 shall be thread-safe, except that the following functions[A1192][S1193][S1194]1[/S1194][/S1193][/A1192] need not be thread-safe.
[p_01024] The [A1195][I1196]ctermid[/I1196]()[/A1195] and [A1197][I1198]tmpnam[/I1198]()[/A1197] functions need not be thread-safe if passed a null pointer argument. The [A1199][I1200]c16rtomb[/I1200]()[/A1199], [A1201][I1202]c32rtomb[/I1202]()[/A1201], [A1203][I1204]mbrlen[/I1204]()[/A1203], [A1205][I1206]mbrtoc16[/I1206]()[/A1205], [A1207][I1208]mbrtoc32[/I1208]()[/A1207], [A1209][I1210]mbrtowc[/I1210]()[/A1209], [A1211][I1212]mbsnrtowcs[/I1212]()[/A1211], [A1213][I1214]mbsrtowcs[/I1214]()[/A1213], [A1215][I1216]wcrtomb[/I1216]()[/A1215], [A1217][I1218]wcsnrtombs[/I1218]()[/A1217], and [A1219][I1220]wcsrtombs[/I1220]()[/A1219] functions need not be thread-safe if passed a null [I1221]ps[/I1221] argument. The [A1222][I1223]lgamma[/I1223]()[/A1222], [A1224][I1225]lgammaf[/I1225]()[/A1224], and [A1226][I1227]lgammal[/I1227]()[/A1226] functions shall be thread-safe [S1228][[A1229]XSI[/A1229]][/S1228] [IMG1230] except that they need not avoid data races when storing a value in the [I1231]signgam[/I1231] variable. [IMG1232] The [A1233][I1234]getc_unlocked[/I1234]()[/A1233], [A1235][I1236]getchar_unlocked[/I1236]()[/A1235], [A1237][I1238]putc_unlocked[/I1238]()[/A1237], and [A1239][I1240]putchar_unlocked[/I1240]()[/A1239] functions need not be thread-safe unless the invoking thread owns the ([B1241]FILE[/B1241] *) object accessed by the call, as is the case after a successful call to the [A1242][I1243]flockfile[/I1243]()[/A1242] or [A1244][I1245]ftrylockfile[/I1245]()[/A1244] functions. The [A1246][I1247]readdir[/I1247]()[/A1246] function need not be thread-safe if concurrent calls are made for the same directory stream.
[p_01025] Some functions that are not required to be thread-safe are nevertheless required to avoid data races with either all or some other functions, as specified on their individual reference pages.
[p_01026] Implementations shall provide internal synchronization as necessary in order to satisfy thread-safety requirements.
[p_01027] Since multi-threaded applications are not allowed to use the [I1248]environ[/I1248] variable to access or modify any environment variable while any other thread is concurrently modifying any environment variable, the [A1249][I1250]getenv[/I1250]()[/A1249] and [A1251][I1252]secure_getenv[/I1252]()[/A1251] functions and any function dependent on any environment variable are not thread-safe if another thread modifies the environment; see XSH [A1253][/A1253][A1254]exec[/A1254].
[h4_01028] [I1255][A1256][/A1256]2.9.2 Thread IDs[/I1255]
[p_01029] [I1257]Although implementations may have thread IDs that are unique in a system, applications should only assume that thread IDs are usable and unique within a single process. The effect of calling any of the functions defined in this volume of POSIX.1-2024 and passing as an argument the thread ID of a thread from another process is unspecified. The lifetime of a thread ID ends after the later of thread termination (see [A1258][I1259]3.392 Thread Termination[/I1259][/A1258] ) and the point when the thread is no longer joinable (see [A1260][I1261]3.183 Joinable Thread[/I1261][/A1260]). A conforming implementation is free to reuse a thread ID after its lifetime has ended. If an application attempts to use a thread ID whose lifetime has ended, the behavior is undefined.[/I1257]
[p_01030] If a thread is detached, its thread ID is invalid for use as an argument in a call to [A1262][I1263]pthread_detach[/I1263]()[/A1262], [A1264][I1265]pthread_join[/I1265]()[/A1264], [A1266][I1267]thrd_detach[/I1267]()[/A1266], or [A1268][I1269]thrd_join[/I1269]()[/A1268].
[h4_01031] [A1270][/A1270]2.9.3 Thread Mutexes
[p_01032] A thread that has blocked shall not prevent any unblocked thread that is eligible to use the same processing resources from eventually making forward progress in its execution. Eligibility for processing resources is determined by the scheduling policy.
[p_01033] A thread shall become the owner of a mutex, [I1271]m[/I1271], of type [B1272]pthread_mutex_t[/B1272] when one of the following occurs:
[li_01034] It calls [A1273][I1274]pthread_mutex_clocklock[/I1274]()[/A1273], [A1275][I1276]pthread_mutex_lock[/I1276]()[/A1275], [A1277][I1278]pthread_mutex_timedlock[/I1278]()[/A1277], or [A1279][I1280]pthread_mutex_trylock[/I1280]()[/A1279] with [I1281]m[/I1281] as the [I1282]mutex[/I1282] argument and the call returns zero or [EOWNERDEAD].
[li_01035] It calls [A1283][I1284]pthread_mutex_setprioceiling[/I1284]()[/A1283] with [I1285]m[/I1285] as the [I1286]mutex[/I1286] argument and the call returns [EOWNERDEAD].
[li_01036] It calls [A1287][I1288]pthread_cond_clockwait[/I1288]()[/A1287], [A1289][I1290]pthread_cond_timedwait[/I1290]()[/A1289], or [A1291][I1292]pthread_cond_wait[/I1292]()[/A1291] with [I1293]m[/I1293] as the [I1294]mutex[/I1294] argument and the call returns zero or certain error numbers (see [A1295][I1296]pthread_cond_clockwait[/I1296]()[/A1295] ).
[p_01037] The thread shall remain the owner of [I1297]m[/I1297] until one of the following occurs:
[li_01038] It executes [A1298][I1299]pthread_mutex_unlock[/I1299]()[/A1298] with [I1300]m[/I1300] as the [I1301]mutex[/I1301] argument
[li_01039] It blocks in a call to [A1302][I1303]pthread_cond_clockwait[/I1303]()[/A1302], [A1304][I1305]pthread_cond_timedwait[/I1305]()[/A1304], or [A1306][I1307]pthread_cond_wait[/I1307]()[/A1306] with [I1308]m[/I1308] as the [I1309]mutex[/I1309] argument.
[p_01040] A thread shall become the owner of a mutex, [I1310]m[/I1310], of type [B1311]mtx_t[/B1311] when one of the following occurs:
[li_01041] It calls [A1312][I1313]mtx_lock[/I1313]()[/A1312] with [I1314]m[/I1314] as the [I1315]mtx[/I1315] argument and the call returns [CODE1316].
[li_01042] It calls [A1317][I1318]mtx_trylock[/I1318]()[/A1317] with [I1319]m[/I1319] as the [I1320]mtx[/I1320] argument and the call returns [CODE1321].
[li_01043] It calls [A1322][I1323]mtx_timedlock[/I1323]()[/A1322] with [I1324]m[/I1324] as the [I1325]mtx[/I1325] argument and the call returns [CODE1326].
[li_01044] It calls [A1327][I1328]cnd_wait[/I1328]()[/A1327] with [I1329]m[/I1329] as the [I1330]mtx[/I1330] argument and the call returns [CODE1331].
[li_01045] It calls [A1332][I1333]cnd_timedwait[/I1333]()[/A1332] with [I1334]m[/I1334] as the [I1335]mtx[/I1335] argument and the call returns [CODE1336] or [CODE1337].
[p_01046] The thread shall remain the owner of [I1338]m[/I1338] until one of the following occurs:
[li_01047] It executes [A1339][I1340]mtx_unlock[/I1340]()[/A1339] with [I1341]m[/I1341] as the [I1342]mtx[/I1342] argument.
[li_01048] It blocks in a call to [A1343][I1344]cnd_wait[/I1344]()[/A1343] with [I1345]m[/I1345] as the [I1346]mtx[/I1346] argument.
[li_01049] It blocks in a call to [A1347][I1348]cnd_timedwait[/I1348]()[/A1347] with [I1349]m[/I1349] as the [I1350]mtx[/I1350] argument.
[p_01050] The implementation shall behave as if at all times there is at most one owner of any mutex.
[p_01051] A thread that becomes the owner of a mutex is said to have &quot;acquired&quot; the mutex and the mutex is said to have become &quot;locked&quot;; when a thread gives up ownership of a mutex it is said to have &quot;released&quot; the mutex and the mutex is said to have become &quot;unlocked&quot;.
[p_01052] A problem can occur if a process terminates while one of its threads holds a mutex lock. Depending on the mutex type, it might be possible for another thread to unlock the mutex and recover the state of the mutex. However, it is difficult to perform this recovery reliably.
[p_01053] Robust mutexes provide a means to enable the implementation to notify other threads in the event of a process terminating while one of its threads holds a lock on a mutex of type [B1351]pthread_mutex_t[/B1351]. The next thread that acquires the mutex is notified about the termination by the return value [EOWNERDEAD] from the locking function. The notified thread can then attempt to recover the state protected by the mutex, and if successful mark the state protected by the mutex as consistent by a call to [A1352][I1353]pthread_mutex_consistent[/I1353]()[/A1352]. If the notified thread is unable to recover the state, it can declare the state as not recoverable by a call to [A1354][I1355]pthread_mutex_unlock[/I1355]()[/A1354] without a prior call to [A1356][I1357]pthread_mutex_consistent[/I1357]()[/A1356].
[p_01054] Whether or not the state protected by a mutex can be recovered is dependent solely on the application using robust mutexes. The robust mutex support provided in the implementation provides notification only that a mutex owner has terminated while holding a lock, or that the state of the mutex is not recoverable.
[h4_01055] [A1358][/A1358]2.9.4 Thread Scheduling
[p_01056] [S1359][[A1360]TPS[/A1360]][/S1359] [IMG1361] The functionality described in this section shall be provided on implementations that support the Thread Execution Scheduling option (and the rest of this section is not further marked for this option). [IMG1362]
[h5_01057] [A1363][/A1363]Thread Scheduling Attributes
[p_01058] In support of the scheduling function, threads have attributes which are accessed through the [B1364]pthread_attr_t[/B1364] thread creation attributes object.
[p_01059] The [I1365]contentionscope[/I1365] attribute defines the scheduling contention scope of the thread to be either PTHREAD_SCOPE_PROCESS or PTHREAD_SCOPE_SYSTEM.
[p_01060] The [I1366]inheritsched[/I1366] attribute specifies whether a newly created thread is to inherit the scheduling attributes of the creating thread or to have its scheduling values set according to the other scheduling attributes in the [B1367]pthread_attr_t[/B1367] object.
[p_01061] The [I1368]schedpolicy[/I1368] attribute defines the scheduling policy for the thread. The [I1369]schedparam[/I1369] attribute defines the scheduling parameters for the thread. The interaction of threads having different policies within a process is described as part of the definition of those policies.
[p_01062] If the Thread Execution Scheduling option is defined, and the [I1370]schedpolicy[/I1370] attribute specifies one of the priority-based policies defined under this option, the [I1371]schedparam[/I1371] attribute contains the scheduling priority of the thread. A conforming implementation ensures that the priority value in [I1372]schedparam[/I1372] is in the range associated with the scheduling policy when the thread attributes object is used to create a thread, or when the scheduling attributes of a thread are dynamically modified. The meaning of the priority value in [I1373]schedparam[/I1373] is the same as that of [I1374]priority[/I1374].
[p_01063] [S1375][[A1376]TSP[/A1376]][/S1375] [IMG1377] If _POSIX_THREAD_SPORADIC_SERVER is defined, the [I1378]schedparam[/I1378] attribute supports four new members that are used for the sporadic server scheduling policy. These members are [I1379]sched_ss_low_priority[/I1379], [I1380]sched_ss_repl_period[/I1380], [I1381]sched_ss_init_budget[/I1381], and [I1382]sched_ss_max_repl[/I1382]. The meaning of these attributes is the same as in the definitions that appear under [A1383]2.8.4 Process Scheduling[/A1383]. [IMG1384]
[p_01064] When a process is created, its single thread has a scheduling policy and associated attributes equal to the policy and attributes of the process. The default scheduling contention scope value is implementation-defined. The default values of other scheduling attributes are implementation-defined.
[h5_01065] [A1385][/A1385]Thread Scheduling Contention Scope
[p_01066] The scheduling contention scope of a thread defines the set of threads with which the thread competes for use of the processing resources. The scheduling operation selects at most one thread to execute on each processor at any point in time and the thread's scheduling attributes (for example, [I1386]priority[/I1386]), whether under process scheduling contention scope or system scheduling contention scope, are the parameters used to determine the scheduling decision.
[p_01067] The scheduling contention scope, in the context of scheduling a mixed scope environment, affects threads as follows:
[li_01068] A thread created with PTHREAD_SCOPE_SYSTEM scheduling contention scope contends for resources with all other threads in the same scheduling allocation domain relative to their system scheduling attributes. The system scheduling attributes of a thread created with PTHREAD_SCOPE_SYSTEM scheduling contention scope are the scheduling attributes with which the thread was created. The system scheduling attributes of a thread created with PTHREAD_SCOPE_PROCESS scheduling contention scope are the implementation-defined mapping into system attribute space of the scheduling attributes with which the thread was created.
[li_01069] Threads created with PTHREAD_SCOPE_PROCESS scheduling contention scope contend directly with other threads within their process that were created with PTHREAD_SCOPE_PROCESS scheduling contention scope. The contention is resolved based on the threads' scheduling attributes and policies. It is unspecified how such threads are scheduled relative to threads in other processes or threads with PTHREAD_SCOPE_SYSTEM scheduling contention scope.
[li_01070] Conforming implementations shall support the PTHREAD_SCOPE_PROCESS scheduling contention scope, the PTHREAD_SCOPE_SYSTEM scheduling contention scope, or both.
[h5_01071] [A1387][/A1387]Scheduling Allocation Domain
[p_01072] Implementations shall support scheduling allocation domains containing one or more processors. It should be noted that the presence of multiple processors does not automatically indicate a scheduling allocation domain size greater than one. Conforming implementations on multi-processors may map all or any subset of the CPUs to one or multiple scheduling allocation domains, and could define these scheduling allocation domains on a per-thread, per-process, or per-system basis, depending on the types of applications intended to be supported by the implementation. The scheduling allocation domain is independent of scheduling contention scope, as the scheduling contention scope merely defines the set of threads with which a thread contends for processor resources, while scheduling allocation domain defines the set of processors for which it contends. The semantics of how this contention is resolved among threads for processors is determined by the scheduling policies of the threads.
[p_01073] The choice of scheduling allocation domain size and the level of application control over scheduling allocation domains is implementation-defined. Conforming implementations may change the size of scheduling allocation domains and the binding of threads to scheduling allocation domains at any time.
[p_01074] For application threads with scheduling allocation domains of size equal to one, the scheduling rules defined for SCHED_FIFO and SCHED_RR shall be used; see [A1388]Scheduling Policies[/A1388]. All threads with system scheduling contention scope, regardless of the processes in which they reside, compete for the processor according to their priorities. Threads with process scheduling contention scope compete only with other threads with process scheduling contention scope within their process.
[p_01075] For application threads with scheduling allocation domains of size greater than one, the rules defined for SCHED_FIFO, SCHED_RR, [S1389][[A1390]TSP[/A1390]][/S1389] [IMG1391] &nbsp;and SCHED_SPORADIC [IMG1392] shall be used in an implementation-defined manner. Each thread with system scheduling contention scope competes for the processors in its scheduling allocation domain in an implementation-defined manner according to its priority. Threads with process scheduling contention scope are scheduled relative to other threads within the same scheduling contention scope in the process.
[p_01076] [S1393][[A1394]TSP[/A1394]][/S1393] [IMG1395] If _POSIX_THREAD_SPORADIC_SERVER is defined, the rules defined for SCHED_SPORADIC in [A1396]Scheduling Policies[/A1396] shall be used in an implementation-defined manner for application threads whose scheduling allocation domain size is greater than one. [IMG1397]
[h5_01077] [A1398][/A1398]Scheduling Documentation
[p_01078] If _POSIX_PRIORITY_SCHEDULING is defined, then any scheduling policies beyond SCHED_OTHER, SCHED_FIFO, SCHED_RR, [S1399][[A1400]TSP[/A1400]][/S1399] [IMG1401] &nbsp;and SCHED_SPORADIC, [IMG1402] as well as the effects of the scheduling policies indicated by these other values, and the attributes required in order to support such a policy, are implementation-defined. Furthermore, the implementation shall document the effect of all processor scheduling allocation domain values supported for these policies.
[h4_01079] [A1403][/A1403]2.9.5 Thread Cancellation
[p_01080] The thread cancellation mechanism allows a thread to terminate the execution of any other thread in the process, except for threads created using [A1404][I1405]thrd_create[/I1405]()[/A1404], in a controlled manner. The target thread (that is, the one that is being canceled) is allowed to hold cancellation requests pending in a number of ways and to perform application-specific cleanup processing when the notice of cancellation is acted upon.
[p_01081] Cancellation is controlled by the cancellation control functions. Each thread maintains its own cancelability state. Cancellation may only occur at cancellation points or when the thread is asynchronously cancelable.
[p_01082] The thread cancellation mechanism described in this section depends upon programs having set [I1406]deferred[/I1406] cancelability state, which is specified as the default. Applications shall also carefully follow static lexical scoping rules in their execution behavior. For example, use of [A1407][I1408]setjmp[/I1408]()[/A1407], [I1409]return[/I1409], [I1410]goto[/I1410], and so on, to leave user-defined cancellation scopes without doing the necessary scope pop operation results in undefined behavior.
[p_01083] Use of asynchronous cancelability while holding resources which potentially need to be released may result in resource loss. Similarly, cancellation scopes may only be safely manipulated (pushed and popped) when the thread is in the [I1411]deferred[/I1411] or [I1412]disabled[/I1412] cancelability states.
[h5_01084] [A1413][/A1413]2.9.5.1 Cancelability States
[p_01085] The cancelability state of a thread determines the action taken upon receipt of a cancellation request. The thread may control cancellation in a number of ways.
[p_01086] Each thread maintains its own cancelability state, which may be encoded in two bits:
[li_01087] Cancelability-Enable: When cancelability is PTHREAD_CANCEL_DISABLE (as defined in the Base Definitions volume of POSIX.1-2024, [A1414][I1415]&lt;pthread.h&gt;[/I1415][/A1414]), cancellation requests against the target thread are held pending. By default, cancelability is set to PTHREAD_CANCEL_ENABLE (as defined in [A1416][I1417]&lt;pthread.h&gt;[/I1417][/A1416]).
[li_01088] Cancelability Type: When cancelability is enabled and the cancelability type is PTHREAD_CANCEL_ASYNCHRONOUS (as defined in [A1418][I1419]&lt;pthread.h&gt;[/I1419][/A1418]), new or pending cancellation requests may be acted upon at any time. When cancelability is enabled and the cancelability type is PTHREAD_CANCEL_DEFERRED (as defined in [A1420][I1421]&lt;pthread.h&gt;[/I1421][/A1420]), cancellation requests are held pending until a cancellation point (see below) is reached. If cancelability is disabled, the setting of the cancelability type has no immediate effect as all cancellation requests are held pending; however, once cancelability is enabled again the new type is in effect. The cancelability type is PTHREAD_CANCEL_DEFERRED in all newly created threads including the thread in which [I1422]main[/I1422]() was first invoked.

[h5_01099] [A1430][/A1430]2.9.5.3 Thread Cancellation Cleanup Handlers
[p_01100] Each thread that was not created using [A1431][I1432]thrd_create[/I1432]()[/A1431] maintains a list of cancellation cleanup handlers. The programmer uses the [A1433][I1434]pthread_cleanup_push[/I1434]()[/A1433] and [A1435][I1436]pthread_cleanup_pop[/I1436]()[/A1435] functions to place routines on and remove routines from this list.
[p_01101] When a cancellation request is acted upon, or when a thread calls [A1437][I1438]pthread_exit[/I1438]()[/A1437], the thread first disables cancellation by setting its cancelability state to PTHREAD_CANCEL_DISABLE and its cancelability type to PTHREAD_CANCEL_DEFERRED. The cancelability state shall remain set to PTHREAD_CANCEL_DISABLE until the thread has terminated. The behavior is undefined if a cancellation cleanup handler or thread-specific data destructor routine changes the cancelability state to PTHREAD_CANCEL_ENABLE.
[p_01102] The routines in the thread's list of cancellation cleanup handlers shall be invoked one by one in LIFO sequence; that is, the last routine pushed onto the list (Last In) is the first to be invoked (First Out). When the cancellation cleanup handler for a scope is invoked, the storage for that scope remains valid. If the last cancellation cleanup handler returns, thread-specific data destructors (if any) associated with thread-specific data keys for which the thread has non-NULL values shall be run, in unspecified order, as described for [A1439][I1440]pthread_key_create[/I1440]()[/A1439] and [A1441][I1442]tss_create[/I1442]()[/A1441].
[p_01103] After all cancellation cleanup handlers and thread-specific data destructors have returned, thread execution is terminated. If the thread has terminated because of a call to [A1443][I1444]pthread_exit[/I1444]()[/A1443], the [I1445]value_ptr[/I1445] argument is made available to any threads joining with the target. If the thread has terminated by acting on a cancellation request, a status of PTHREAD_CANCELED is made available to any threads joining with the target. The symbolic constant PTHREAD_CANCELED expands to a constant expression of type ([B1446]void *[/B1446]) whose value matches no pointer to an object in memory nor the value NULL.
[p_01104] A side-effect of acting upon a cancellation request while in a condition variable wait is that the mutex is re-acquired before calling the first cancellation cleanup handler. In addition, the thread is no longer considered to be waiting for the condition and the thread shall not have consumed any pending condition signals on the condition.
[p_01105] A cancellation cleanup handler cannot exit via [A1447][I1448]longjmp[/I1448]()[/A1447] or [A1449][I1450]siglongjmp[/I1450]()[/A1449].
[h5_01106] [A1451][/A1451]2.9.5.4 Async-Cancel Safety
[p_01107] The [A1452][I1453]pthread_cancel[/I1453]()[/A1452], [A1454][I1455]pthread_setcancelstate[/I1455]()[/A1454], and [A1456][I1457]pthread_setcanceltype[/I1457]()[/A1456] functions are defined to be async-cancel safe.
[p_01108] No other functions in this volume of POSIX.1-2024 are required to be async-cancel-safe.
[p_01109] If a thread has asynchronous cancellation enabled and is cancelled during execution of a function that is not async-cancel-safe, the behavior is undefined.
[p_01110] If a thread has deferred cancellation enabled, a signal-catching function is called in that thread during execution of a function that is not async-cancel-safe, and the signal-catching function calls any function that is a cancellation point while a cancellation is pending for the thread, without first disabling cancellation, the behavior is undefined.
[h4_01111] [A1458][/A1458]2.9.6 Thread Read-Write Locks
[p_01112] Multiple readers, single writer (read-write) locks allow many threads to have simultaneous read-only access to data while allowing only one thread to have exclusive write access at any given time. They are typically used to protect data that is read more frequently than it is changed.
[p_01113] One or more readers acquire read access to the resource by performing a read lock operation on the associated read-write lock. A writer acquires exclusive write access by performing a write lock operation. Basically, all readers exclude any writers and a writer excludes all readers and any other writers.
[p_01114] A thread that has blocked on a read-write lock (for example, has not yet returned from a [A1459][I1460]pthread_rwlock_rdlock[/I1460]()[/A1459] or [A1461][I1462]pthread_rwlock_wrlock[/I1462]()[/A1461] call) shall not prevent any unblocked thread that is eligible to use the same processing resources from eventually making forward progress in its execution. Eligibility for processing resources shall be determined by the scheduling policy.
[p_01115] Read-write locks can be used to synchronize threads in the current process and other processes if they are allocated in memory that is writable and shared among the cooperating processes and have been initialized for this behavior.

[h4_01121] [A1470][/A1470]2.9.8 Use of Application-Managed Thread Stacks
[p_01122] An &quot;application-managed thread stack&quot; is a region of memory allocated by the application—for example, memory returned by the [A1471][I1472]malloc[/I1472]()[/A1471] or [A1473][I1474]mmap[/I1474]()[/A1473] functions—and designated as a stack through the act of passing the address and size of the stack, respectively, as the [I1475]stackaddr[/I1475] and [I1476]stacksize[/I1476] arguments to [A1477][I1478]pthread_attr_setstack[/I1478]()[/A1477]. Application-managed stacks allow the application to precisely control the placement and size of a stack.
[p_01123] The application grants to the implementation permanent ownership of and control over the application-managed stack when the attributes object in which the [I1479]stack[/I1479] or [I1480]stackaddr[/I1480] attribute has been set is used, either by presenting that attribute's object as the [I1481]attr[/I1481] argument in a call to [A1482][I1483]pthread_create[/I1483]()[/A1482] that completes successfully, or by storing a pointer to the attributes object in the [I1484]sigev_notify_attributes[/I1484] member of a [B1485]struct sigevent[/B1485] and passing that [B1486]struct sigevent[/B1486] to a function accepting such argument that completes successfully. The application may thereafter utilize the memory within the stack only within the normal context of stack usage within or properly synchronized with a thread that has been scheduled by the implementation with stack pointer value(s) that are within the range of that stack. In particular, the region of memory cannot be freed, nor can it be later specified as the stack for another thread.
[p_01124] When specifying an attributes object with an application-managed stack through the [I1487]sigev_notify_attributes[/I1487] member of a [B1488]struct sigevent[/B1488], the results are undefined if the requested signal is generated multiple times (as for a repeating timer).
[p_01125] Until an attributes object in which the [I1489]stack[/I1489] or [I1490]stackaddr[/I1490] attribute has been set is used, the application retains ownership of and control over the memory allocated to the stack. It may free or reuse the memory as long as it either deletes the attributes object, or before using the attributes object replaces the stack by making an additional call to [A1491][I1492]pthread_attr_setstack[/I1492]()[/A1491], that was used originally to designate the stack. There is no mechanism to retract the reference to an application-managed stack by an existing attributes object.
[p_01126] Once an attributes object with an application-managed stack has been used, that attributes object cannot be used again by a subsequent call to [A1493][I1494]pthread_create[/I1494]()[/A1493] or any function accepting a [B1495]struct sigevent[/B1495] with [I1496]sigev_notify_attributes[/I1496] containing a pointer to the attributes object, without designating an unused application-managed stack by making an additional call to [A1497][I1498]pthread_attr_setstack[/I1498]()[/A1497].
[h4_01127] [A1499][/A1499]2.9.9 Synchronization Object Copies and Alternative Mappings
[p_01128] For barriers, condition variables, mutexes, and read-write locks, [S1500][[A1501]TSH[/A1501]][/S1500] [IMG1502] &nbsp;if the process-shared attribute is set to PTHREAD_PROCESS_PRIVATE, [IMG1503] &nbsp;only the synchronization object at the address used to initialize it can be used for performing synchronization. The effect of referring to another mapping of the same object when locking, unlocking, or destroying the object is undefined. [S1504][[A1505]TSH[/A1505]][/S1504] [IMG1506] &nbsp;If the process-shared attribute is set to PTHREAD_PROCESS_SHARED, only the synchronization object itself can be used for performing synchronization; however, it need not be referenced at the address used to initalize it (that is, another mapping of the same object can be used). [IMG1507] &nbsp;The effect of referring to a copy of the object when locking, unlocking, or destroying it is undefined.
[p_01129] For spin locks, the above requirements shall apply as if spin locks have a process-shared attribute that is set from the [I1508]pshared[/I1508] argument to [A1509][I1510]pthread_spin_init[/I1510]()[/A1509]. For semaphores, the above requirements shall apply as if semaphores have a process-shared attribute that is set to PTHREAD_PROCESS_PRIVATE if the [I1511]pshared[/I1511] argument to [A1512][I1513]sem_init[/I1513]()[/A1512] is zero and set to PTHREAD_PROCESS_SHARED if [I1514]pshared[/I1514] is non-zero.
[p_01130] For ISO C functions declared in [A1515][I1516]&lt;threads.h&gt;[/I1516][/A1515], the above requirements shall apply as if condition variables of type [B1517]cnd_t[/B1517] and mutexes of type [B1518]mtx_t[/B1518] have a process-shared attribute that is set to PTHREAD_PROCESS_PRIVATE.
