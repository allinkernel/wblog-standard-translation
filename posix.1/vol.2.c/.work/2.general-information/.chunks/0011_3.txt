[p_01258] The SO_ACCEPTCONN option is used only on [A1661][I1662]getsockopt[/I1662]()[/A1661]. When this option is specified, [A1663][I1664]getsockopt[/I1664]()[/A1663] shall report whether socket listening is enabled for the socket. A value of zero shall indicate that socket listening is disabled; non-zero that it is enabled. SO_ACCEPTCONN has no default value.
[p_01259] The SO_BROADCAST option requests permission to send broadcast datagrams on the socket. Support for SO_BROADCAST is protocol-specific. The default for SO_BROADCAST is that the ability to send broadcast datagrams on a socket is disabled.
[p_01260] The SO_DEBUG option enables debugging in the underlying protocol modules. This can be useful for tracing the behavior of the underlying protocol modules during normal system operation. The semantics of the debug reports are implementation-defined. The default value for SO_DEBUG is for debugging to be turned off.
[p_01261] The SO_DOMAIN option is used only on [A1665][I1666]getsockopt[/I1666]()[/A1665]. When this option is specified, [A1667][I1668]getsockopt[/I1668]()[/A1667] shall return the domain of the socket (for example, AF_INET6). SO_DOMAIN has no default value.
[p_01262] The SO_DONTROUTE option requests that outgoing messages bypass the standard routing facilities. The destination needs to be on a directly-connected network, and messages are directed to the appropriate network interface according to the destination address. It is protocol-specific whether this option has any effect and how the outgoing network interface is chosen. Support for this option with each protocol is implementation-defined.
[p_01263] The SO_ERROR option is used only on [A1669][I1670]getsockopt[/I1670]()[/A1669]. When this option is specified, [A1671][I1672]getsockopt[/I1672]()[/A1671] shall return any pending error on the socket and clear the error status. It shall return a value of 0 if there is no pending error. SO_ERROR may be used to check for asynchronous errors on connected connectionless-mode sockets or for other types of asynchronous errors. SO_ERROR has no default value.
[p_01264] The SO_KEEPALIVE option enables the periodic transmission of messages on a connected socket. The behavior of this option is protocol-specific. On a connection-mode socket for which a connection has been established, if SO_KEEPALIVE is enabled and the connected socket fails to respond to the keep-alive messages, the connection shall be broken. The default value for SO_KEEPALIVE is zero, specifying that this capability is turned off.
[p_01265] The SO_LINGER option controls the action of the interface when unsent messages are queued on a socket and a [A1673][I1674]close[/I1674]()[/A1673] is performed. The details of this option are protocol-specific. If SO_LINGER is enabled, the system shall block the calling thread during [A1675][I1676]close[/I1676]()[/A1675] until it can transmit the data or until the end of the interval indicated by the [I1677]l_linger[/I1677] member, whichever comes first. If SO_LINGER is not specified, and [A1678][I1679]close[/I1679]()[/A1678] is issued, the system handles the call in a way that allows the calling thread to continue as quickly as possible. The default value for SO_LINGER is zero, or off, for the [I1680]l_onoff[/I1680] element of the option value and zero seconds for the linger time specified by the [I1681]l_linger[/I1681] element.
[p_01266] The SO_OOBINLINE option is valid only on protocols that support out-of-band data. The SO_OOBINLINE option requests that out-of-band data be placed in the normal data input queue as received; it is then accessible using the [A1682][I1683]read[/I1683]()[/A1682] or [A1684][I1685]recv[/I1685]()[/A1684] functions without the MSG_OOB flag set. The default for SO_OOBINLINE is off; that is, for out-of-band data not to be placed in the normal data input queue.
[p_01267] The SO_PROTOCOL option is used only on [A1686][I1687]getsockopt[/I1687]()[/A1686]. When this option is specified, [A1688][I1689]getsockopt[/I1689]()[/A1688] shall return the socket protocol (for example, IPPROTO_TCP). SO_PROTOCOL has no default value.
[p_01268] The SO_RCVBUF option requests that the buffer space allocated for receive operations on this socket be set to the value, in bytes, of the option value. Applications may wish to increase buffer size for high volume connections, or may decrease buffer size to limit the possible backlog of incoming data. The default value for the SO_RCVBUF option value is implementation-defined, and may vary by protocol.
[p_01269] The SO_RCVLOWAT option sets the minimum number of bytes to process for socket input operations. In general, receive calls block until any (non-zero) amount of data is received, then return the smaller of the amount available or the amount requested. The default value for SO_RCVLOWAT is 1, and does not affect the general case. If SO_RCVLOWAT is set to a larger value, blocking receive calls normally wait until they have received the smaller of the low water mark value or the requested amount. Receive calls may still return less than the low water mark if an error occurs, a signal is caught, or the type of data next in the receive queue is different from that returned (for example, out-of-band data). As mentioned previously, the default value for SO_RCVLOWAT is 1 byte. It is implementation-defined whether the SO_RCVLOWAT option can be set.
[p_01270] The SO_RCVTIMEO option is an option to set a timeout value for input operations. It accepts a [B1690]timeval[/B1690] structure with the number of seconds and microseconds specifying the limit on how long to wait for an input operation to complete. If a receive operation has blocked for this much time without receiving additional data, it shall return with a partial count or [I1691]errno[/I1691] shall be set to [EAGAIN] or [EWOULDBLOCK] if no data were received. The default for this option is the value zero, which indicates that a receive operation will not time out. It is implementation-defined whether the SO_RCVTIMEO option can be set.
[p_01271] The SO_REUSEADDR option indicates that the rules used in validating addresses supplied in a [A1692][I1693]bind[/I1693]()[/A1692] should allow reuse of local addresses. Operation of this option is protocol-specific. The default value for SO_REUSEADDR is off; that is, reuse of local addresses is not permitted.
[p_01272] The SO_SNDBUF option requests that the buffer space allocated for send operations on this socket be set to the value, in bytes, of the option value. The default value for the SO_SNDBUF option value is implementation-defined, and may vary by protocol.
[p_01273] The SO_SNDLOWAT option sets the minimum number of bytes to process for socket output operations. Most output operations process all of the data supplied by the call, delivering data to the protocol for transmission and blocking as necessary for flow control. Non-blocking output operations process as much data as permitted subject to flow control without blocking, but process no data if flow control does not allow the smaller of the send low water mark value or the entire request to be processed. A [A1694][I1695]select[/I1695]()[/A1694] operation testing the ability to write to a socket shall return true only if the send low water mark could be processed. The default value for SO_SNDLOWAT is implementation-defined and protocol-specific. It is implementation-defined whether the SO_SNDLOWAT option can be set.
[p_01274] The SO_SNDTIMEO option is an option to set a timeout value for the amount of time that an output function shall block because flow control prevents data from being sent. As noted in [A1696]Socket-Level Options[/A1696], the option value is a [B1697]timeval[/B1697] structure with the number of seconds and microseconds specifying the limit on how long to wait for an output operation to complete. If a send operation has blocked for this much time, it shall return with a partial count or [I1698]errno[/I1698] set to [EAGAIN] or [EWOULDBLOCK] if no data were sent. The default for this option is the value zero, which indicates that a send operation will not time out. It is implementation-defined whether the SO_SNDTIMEO option can be set.
[p_01275] The SO_TYPE option is used only on [A1699][I1700]getsockopt[/I1700]()[/A1699]. When this option is specified, [A1701][I1702]getsockopt[/I1702]()[/A1701] shall return the type of the socket (for example, SOCK_STREAM). This option is useful to servers that inherit sockets on start-up. SO_TYPE has no default value.
[h4_01276] [A1703][/A1703]2.10.17 Use of Sockets for Local UNIX Connections
[p_01277] Support for UNIX domain sockets is mandatory.
[p_01278] UNIX domain sockets provide process-to-process communication in a single system.
[h5_01279] [A1704][/A1704]2.10.17.1 Headers
[p_01280] The symbolic constant AF_UNIX defined in the [A1705][I1706]&lt;sys/socket.h&gt;[/I1706][/A1705] header is used to identify the UNIX domain address family. The [A1707][I1708]&lt;sys/un.h&gt;[/I1708][/A1707] header contains other definitions used in connection with UNIX domain sockets. See XBD [A1709][I1710]14. Headers[/I1710][/A1709].
[p_01281] The [B1711]sockaddr_storage[/B1711] structure defined in [A1712][I1713]&lt;sys/socket.h&gt;[/I1713][/A1712] shall be large enough to accommodate a [B1714]sockaddr_un[/B1714] structure (see the [A1715][I1716]&lt;sys/un.h&gt;[/I1716][/A1715] header defined in XBD [A1717][I1718]14. Headers[/I1718][/A1717]) and shall be aligned at an appropriate boundary so that pointers to it can be cast as pointers to [B1719]sockaddr_un[/B1719] structures and used to access the fields of those structures without alignment problems. When a [B1720]sockaddr_storage[/B1720] structure is cast as a [B1721]sockaddr_un[/B1721] structure, the [I1722]ss_family[/I1722] field maps onto the [I1723]sun_family[/I1723] field.

[h4_01298] [A1754][/A1754]2.10.20 Use of Sockets over Internet Protocols Based on IPv6
[p_01299] [S1755][[A1756]IP6[/A1756]][/S1755] [IMG1757] This section describes extensions to support sockets over Internet protocols based on IPv6. The functionality described in this section shall be provided on implementations that support the IPV6 option (and the rest of this section is not further shaded for this option). [IMG1758]
[p_01300] IPv6 is described in RFC&nbsp;8200.
[p_01301] To enable smooth transition from IPv4 to IPv6, the features defined in this section may, in certain circumstances, also be used in connection with IPv4; see [A1759]2.10.20.2 Compatibility with IPv4[/A1759].
[h5_01302] [A1760][/A1760]2.10.20.1 Addressing
[p_01303] IPv6 overcomes the addressing limitations of earlier versions by using 128-bit addresses instead of 32-bit addresses. The IPv6 address architecture is described in RFC&nbsp;4291.
[p_01304] There are three kinds of IPv6 address:
[dt_01305] Unicast
[p_01306] A unicast address can be global, link-local (designed for use on a single link), or site-local (designed for systems not connected to the Internet). Link-local and site-local addresses need not be globally unique.
[dt_01307] Anycast
[p_01308] An anycast address is similar to a unicast address; the nodes to which an anycast address is assigned need to be explicitly configured to know that it is an anycast address.
[dt_01309] Multicast
[p_01310] An application can send multicast datagrams by simply specifying an IPv6 multicast address in the [I1761]address[/I1761] argument of [A1762][I1763]sendto[/I1763]()[/A1762]. To receive multicast datagrams, an application needs to join the multicast group (using [A1764][I1765]setsockopt[/I1765]()[/A1764] with IPV6_JOIN_GROUP) and bind to the socket the UDP port on which datagrams are to be received. Some applications should also bind the multicast group address to the socket, to prevent other datagrams destined to that port from being delivered to the socket.
