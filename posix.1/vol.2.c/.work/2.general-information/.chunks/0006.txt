[h3_00752] [A544][/A544]2.5 Standard I/O Streams
[p_00753] A stream is associated with an external file (which may be a physical device) [S545][[A546]CX[/A546]][/S545] [IMG547] &nbsp;or memory buffer [IMG548] &nbsp;by &quot;opening&quot; a file [S549][[A550]CX[/A550]][/S549] [IMG551] &nbsp;or buffer. [IMG552] This may involve &quot;creating&quot; a new file. Creating an existing file causes its former contents to be discarded if necessary. If a file can support positioning requests (such as a disk file, as opposed to a terminal), then a &quot;file position indicator&quot; associated with the stream is positioned at the start (byte number 0) of the file, unless the file is opened with append mode, in which case it is implementation-defined whether the file position indicator is initially positioned at the beginning or end of the file. The file position indicator is maintained by subsequent reads, writes, and positioning requests, to facilitate an orderly progression through the file.
[p_00754] The wide-character input functions shall read characters from the stream and convert them to wide characters as if they were read by successive calls to the [A553][I554]fgetwc[/I554]()[/A553] function. Each conversion shall occur as if by a call to the [A555][I556]mbrtowc[/I556]()[/A555] function, with the conversion state described by the stream's own [B557]mbstate_t[/B557] object (see [A558]2.5.2 Stream Orientation and Encoding Rules[/A558]). The byte input functions shall read characters from the stream as if by successive calls to the [A559][I560]fgetc[/I560]()[/A559] function.
[p_00755] The wide-character output functions shall convert wide characters to characters and write them to the stream as if they were written by successive calls to the [A561][I562]fputwc[/I562]()[/A561] function. Each conversion shall occur as if by a call to the [A563][I564]wcrtomb[/I564]()[/A563] function, with the conversion state described by the stream's own [B565]mbstate_t[/B565] object (see [A566]2.5.2 Stream Orientation and Encoding Rules[/A566]). The byte output functions shall write characters to the stream as if by successive calls to the [A567][I568]fputc[/I568]()[/A567] function.
[p_00756] The [A569][I570]perror[/I570]()[/A569], [A571][I572]psiginfo[/I572]()[/A571], and [A573][I574]psignal[/I574]()[/A573] functions shall behave as described above for the byte output functions if the stream is already byte-oriented, and shall behave as described above for the wide-character output functions if the stream is already wide-oriented. If the stream has no orientation, they shall behave as described for the byte output functions except that they shall not change the orientation of the stream.
[p_00757] Functions other than [A575][I576]perror[/I576]()[/A575], [A577][I578]psiginfo[/I578]()[/A577], and [A579][I580]psignal[/I580]()[/A579] that write to streams but are neither wide-character output nor byte output functions ([A581][I582]getopt[/I582]()[/A581] and [A583][I584]wordexp[/I584]()[/A583]), shall behave as described above for the byte output functions, except that if the stream has no orientation, it is unspecified whether they set the stream to byte orientation or leave it with no orientation.
[p_00758] When a stream is &quot;unbuffered&quot;, bytes are intended to appear from the source or at the destination as soon as possible; otherwise, bytes may be accumulated and transmitted as a block. When a stream is &quot;fully buffered&quot;, bytes are intended to be transmitted as a block when a buffer is filled. When a stream is &quot;line buffered&quot;, bytes are intended to be transmitted as a block when a &lt;newline&gt; byte is encountered. Furthermore, bytes are intended to be transmitted as a block when a buffer is filled, when input is requested on an unbuffered stream, or when input is requested on a line-buffered stream that requires the transmission of bytes. Support for these characteristics is implementation-defined, and may be affected via [A585][I586]setbuf[/I586]()[/A585] and [A587][I588]setvbuf[/I588]()[/A587].
[p_00759] A file may be disassociated from a controlling stream by &quot;closing&quot; the file. Output streams are flushed (any unwritten buffer contents are transmitted) before the stream is disassociated from the file. The value of a pointer to a [B589]FILE[/B589] object is unspecified after the associated file is closed (including the standard streams).
[p_00760] A file may be subsequently reopened, by the same or another program execution, and its contents reclaimed or modified (if it can be repositioned at its start). If the [I590]main[/I590]() function returns to its original caller, or if the [A591][I592]exit[/I592]()[/A591] function is called, all open files are closed (hence all output streams are flushed) before program termination. Other paths to program termination, such as calling [A593][I594]abort[/I594]()[/A593], need not close all files properly.
[p_00761] The address of the [B595]FILE[/B595] object used to control a stream may be significant; a copy of a [B596]FILE[/B596] object need not necessarily serve in place of the original.
[p_00762] At program start-up, three streams shall be predefined and already open: [I597]stdin[/I597] (standard input, for conventional input) for reading, [I598]stdout[/I598] (standard output, for conventional output) for writing, and [I599]stderr[/I599] (standard error, for diagnostic output) for writing. When opened, [I600]stderr[/I600] shall not be fully buffered; [I601]stdin[/I601] and [I602]stdout[/I602] shall be fully buffered if and only if [S603][[A604]CX[/A604]][/S603] [IMG605] &nbsp;the file descriptor associated with the stream is determined not to be associated with an interactive device. [IMG606]
[p_00763] Each stream shall have an associated lock that is used to prevent data races when multiple threads of execution access a stream, and to restrict the interleaving of stream operations performed by multiple threads. Only one thread can hold this lock at a time. The lock shall be reentrant: a single thread can hold the lock multiple times at a given time. All functions that read, write, position, or query the position of a stream, [S607][[A608]CX[/A608]][/S607] [IMG609] &nbsp;except those with names ending [I610]_unlocked[/I610], [IMG611] &nbsp;shall lock the stream [S612][[A613]CX[/A613]][/S612] [IMG614] &nbsp;as if by a call to [A615][I616]flockfile[/I616]()[/A615] [IMG617] &nbsp;before accessing it and release the lock [S618][[A619]CX[/A619]][/S618] [IMG620] &nbsp;as if by a call to [A621][I622]funlockfile[/I622]()[/A621] [IMG623] &nbsp;when the access is complete.
[p_00764] [S624][[A625]CX[/A625]][/S624] [IMG626] If the lock is not immediately available, the function shall wait for it to become available, except in the following circumstances. If the stream is line buffered and is open for writing or for update, and the reason the function is attempting to lock the stream is because it is going to request input on another stream that is unbuffered, or is line buffered and requires the transmission of characters from the host environment (see above), then the function shall attempt to determine whether a deadlock situation exists. If a deadlock situation is found to exist, the function shall fail. If the function is able to establish that a deadlock situation does not exist, it shall wait for the lock to become available. If the function does not establish whether or not a deadlock situation exists, it shall continue as if it had already locked the stream, found its buffer to be empty, and released the lock. [IMG627]
[p_00765] [S628][[A629]CX[/A629]][/S628] [IMG630] A stream associated with a memory buffer shall have the same operations for text files that a stream associated with an external file would have. In addition, the stream orientation shall be determined in exactly the same fashion.
[p_00766] Input and output operations on a stream associated with a memory buffer by a call to [A631][I632]fmemopen[/I632]()[/A631] shall be constrained by the implementation to take place within the bounds of the memory buffer. In the case of a stream opened by [A633][I634]open_memstream[/I634]()[/A633] or [A635][I636]open_wmemstream[/I636]()[/A635], the memory area shall grow dynamically to accommodate write operations as necessary. For output, if the stream is fully buffered or line buffered, data shall be moved from the stream's internal buffer, or a buffer provided by [A637][I638]setvbuf[/I638]()[/A637], to the memory buffer during a flush or close operation. For input, it is unspecified whether a buffer provided by [A639][I640]setvbuf[/I640]()[/A639] is used or whether read operations read directly from the memory buffer provided to or allocated by [A641][I642]fmemopen[/I642]()[/A641].
[p_00767] When a standard I/O stream has an associated memory buffer (whether allocated internally, supplied to [A643][I644]setvbuf[/I644]()[/A643], or supplied to [A645][I646]fmemopen[/I646]()[/A645]), the behavior is undefined if that buffer overlaps with the destination buffer passed to a call that reads from the stream or with the source buffer passed to a call that writes to the stream. [IMG647]
[h4_00768] [A648][/A648]2.5.1 Interaction of File Descriptors and Standard I/O Streams
[p_00769] [S649][[A650]CX[/A650]][/S649] [IMG651] This section describes the interaction of file descriptors and standard I/O streams. The functionality described in this section is an extension to the ISO&nbsp;C standard (and the rest of this section is not further CX shaded). [IMG652]
[p_00770] An open file description may be accessed through a file descriptor, which is created using functions such as [A653][I654]open[/I654]()[/A653] or [A655][I656]pipe[/I656]()[/A655], or through a stream, which is created using functions such as [A657][I658]fopen[/I658]()[/A657] or [A659][I660]popen[/I660]()[/A659]. Either a file descriptor or a stream is called a &quot;handle&quot; on the open file description to which it refers; an open file description may have several handles.
[p_00771] Handles can be created or destroyed by explicit user action, without affecting the underlying open file description. Some of the ways to create them include [A661][I662]fcntl[/I662]()[/A661], [A663][I664]dup[/I664]()[/A663], [A665][I666]fdopen[/I666]()[/A665], [A667][I668]fileno[/I668]()[/A667], and [A669][I670]fork[/I670]()[/A669]. They can be destroyed by at least [A671][I672]fclose[/I672]()[/A671], [A673][I674]close[/I674]()[/A673], and the [I675][A676]exec[/A676][/I675] functions.
[p_00772] A file descriptor that is never used in an operation that could affect the file offset (for example, [A677][I678]read[/I678]()[/A677], [A679][I680]write[/I680]()[/A679], or [A681][I682]lseek[/I682]()[/A681]) is not considered a handle for this discussion, but could give rise to one (for example, as a consequence of [A683][I684]fdopen[/I684]()[/A683], [A685][I686]dup[/I686]()[/A685], or [A687][I688]fork[/I688]()[/A687]). This exception does not include the file descriptor underlying a stream, whether created with [A689][I690]fopen[/I690]()[/A689] or [A691][I692]fdopen[/I692]()[/A691], so long as it is not used directly by the application to affect the file offset. The [A693][I694]read[/I694]()[/A693] and [A695][I696]write[/I696]()[/A695] functions implicitly affect the file offset; [A697][I698]lseek[/I698]()[/A697] explicitly affects it.
[p_00773] The result of function calls involving any one handle (the &quot;active handle&quot;) is defined elsewhere in this volume of POSIX.1-2024, but if two or more handles are used, and any one of them is a stream, the application shall ensure that their actions are coordinated as described below. If this is not done, the result is undefined.
[p_00774] A handle which is a stream is considered to be closed when either an [A699][I700]fclose[/I700]()[/A699], or [A701][I702]freopen[/I702]()[/A701] with non-null filename, is executed on it (for [A703][I704]freopen[/I704]()[/A703] with a null filename, it is implementation-defined whether a new handle is created or the existing one reused), or when the process owning that stream terminates with [A705][I706]exit[/I706]()[/A705], [A707][I708]abort[/I708]()[/A707], or due to a signal. Several functions close file descriptors, including [A709][I710]close[/I710]()[/A709], [A711][I712]dup2[/I712]()[/A711], [A713][I714]_exit[/I714]()[/A713], the [I715][A716]exec[/A716][/I715] functions when FD_CLOEXEC is set on a file descriptor, [A717][I718]fork[/I718]()[/A717] when FD_CLOFORK is set on a file descriptor, and [A719][I720]posix_spawn[/I720]()[/A719] when either FD_CLOEXEC or FD_CLOFORK is set.
[p_00775] For a handle to become the active handle, the application shall ensure that the actions below are performed between the last use of the handle (the current active handle) and the first use of the second handle (the future active handle). The second handle then becomes the active handle. All activity by the application affecting the file offset on the first handle shall be suspended until it again becomes the active file handle. (If a stream function has as an underlying function one that affects the file offset, the stream function shall be considered to affect the file offset.)
[p_00776] The handles need not be in the same process for these rules to apply.
[p_00777] Note that after a [A721][I722]fork[/I722]()[/A721], two handles exist where one existed before. The application shall ensure that, if both handles can ever be accessed, they are both in a state where the other could become the active handle first. The application shall prepare for a [A723][I724]fork[/I724]()[/A723] exactly as if it were a change of active handle. (If the only action performed by one of the processes is one of the [I725][A726]exec[/A726][/I725] functions or [A727][I728]_exit[/I728]()[/A727] (not [A729][I730]exit[/I730]()[/A729]), the handle is never accessed in that process.)
[p_00778] For the first handle, the first applicable condition below applies. After the actions required below are taken, if the handle is still open, the application can close it.
[li_00779] If it is a file descriptor, no action is required.
[li_00780] If the only further action to be performed on any handle to this open file descriptor is to close it, no action need be taken.
[li_00781] If it is a stream which is unbuffered, no action need be taken.
[blockquote_00782] [PRE731]
[p_00783] was the most recent operation on that stream), no action need be taken.
[li_00784] If it is a stream which is open for writing or appending (but not also open for reading), the application shall either perform an [A732][I733]fflush[/I733]()[/A732], or the stream shall be closed.
[li_00785] If the stream is open for reading and it is at the end of the file ([A734][I735]feof[/I735]()[/A734] is true), no action need be taken.
[li_00786] If the stream is open with a mode that allows reading and the underlying open file description refers to a device that is capable of seeking, the application shall either perform an [A736][I737]fflush[/I737]()[/A736], or the stream shall be closed.
[p_00787] For the second handle:
[li_00788] If any previous active handle has been used by a function that explicitly changed the file offset, except as required above for the first handle, the application shall perform an [A738][I739]lseek[/I739]()[/A738] or [A740][I741]fseek[/I741]()[/A740] (as appropriate to the type of handle) to an appropriate location.
[p_00789] If the active handle ceases to be accessible before the requirements on the first handle, above, have been met, the state of the open file description becomes undefined. This might occur during functions such as a [A742][I743]fork[/I743]()[/A742] or [A744][I745]_exit[/I745]()[/A744].
[p_00790] The [I746][A747]exec[/A747][/I746] functions make inaccessible all streams that are open at the time they are called, independent of which streams or file descriptors may be available to the new process image.
[p_00791] When these rules are followed, regardless of the sequence of handles used, no data shall be lost or duplicated when writing, and all data shall be written in order, except as requested by seeks. It is implementation-defined whether, and under what conditions, all input is seen exactly once.
[p_00792] Each function that operates on a stream is said to have zero or more &quot;underlying functions&quot;. This means that the stream function shares certain traits with the underlying functions, but does not require that there be any relation between the implementations of the stream function and its underlying functions.
[h4_00793] [A748][/A748]2.5.2 Stream Orientation and Encoding Rules
[p_00794] The definition of a stream includes an &quot;orientation&quot;. After a stream is associated with an external file, but before any operations are performed on it, the stream is without orientation. Once a wide-character input/output function has been applied to a stream without orientation, the stream shall become &quot;wide-oriented&quot;. Similarly, once a byte input/output function has been applied to a stream without orientation, the stream shall become &quot;byte-oriented&quot;. Only a call to the [A749][I750]freopen[/I750]()[/A749] function or the [A751][I752]fwide[/I752]()[/A751] function can otherwise alter the orientation of a stream.
[p_00795] A successful call to [A753][I754]freopen[/I754]()[/A753] shall remove any orientation. The three predefined streams [I755]standard input[/I755], [I756]standard output[/I756], and [I757]standard error[/I757] shall be unoriented at program start-up.
[p_00796] Byte input/output functions cannot be applied to a wide-oriented stream, and wide-character input/output functions cannot be applied to a byte-oriented stream. The remaining stream operations shall not affect and shall not be affected by a stream's orientation, except for the following additional restriction:
[li_00797] For wide-oriented streams, after a successful call to a file-positioning function that leaves the file position indicator prior to the end-of-file, a wide-character output function can overwrite a partial character; any file contents beyond the byte(s) written are henceforth undefined.
[p_00798] Each wide-oriented stream [S758][[A759]CX[/A759]][/S758] [IMG760] &nbsp;that was not opened with [A761][I762]open_wmemstream[/I762]()[/A761] [IMG763] has an associated [B764]mbstate_t[/B764] object that stores the current parse state of the stream. A successful call to [A765][I766]fgetpos[/I766]()[/A765] shall store a representation of the value of this [B767]mbstate_t[/B767] object as part of the value of the [B768]fpos_t[/B768] object. A later successful call to [A769][I770]fsetpos[/I770]()[/A769] using the same stored [B771]fpos_t[/B771] value shall restore the value of the associated [B772]mbstate_t[/B772] object as well as the position within the controlled stream.
[p_00799] Implementations that support multiple encoding rules associate an encoding rule with the stream. The encoding rule shall be determined by the setting of the [I773]LC_CTYPE[/I773] category in the current locale at the time when the stream becomes wide-oriented. As with the stream's orientation, the encoding rule associated with a stream cannot be changed once it has been set, except by a successful call to [A774][I775]freopen[/I775]()[/A774] which clears the encoding rule and resets the orientation to unoriented.
[p_00800] Although wide-oriented streams are conceptually sequences of wide characters, the external file associated with a wide-oriented stream [S776][[A777]CX[/A777]][/S776] [IMG778] &nbsp;that was not opened with [A779][I780]open_wmemstream[/I780]()[/A779] [IMG781] is a sequence of (possibly multi-byte) characters generalized as follows:
[li_00801] Multi-byte encodings within files may contain embedded null bytes (unlike multi-byte encodings valid for use internal to the program).
[li_00802] A file need not begin nor end in the initial shift state.
[p_00803] Moreover, the encodings used for characters may differ among files. Both the nature and choice of such encodings are implementation-defined.
[p_00804] [S782][[A783]CX[/A783]][/S782] [IMG784] On streams that were not opened with [A785][I786]open_wmemstream[/I786]()[/A785], [IMG787] the wide-character input functions read characters from the stream and convert them to wide characters as if they were read by successive calls to the [A788][I789]fgetwc[/I789]()[/A788] function. Each conversion shall occur as if by a call to the [A790][I791]mbrtowc[/I791]()[/A790] function, with the conversion state described by the stream's own [B792]mbstate_t[/B792] object, [S793][[A794]CX[/A794]][/S793] [IMG795] &nbsp;except the encoding rule associated with the stream is used instead of the encoding rule implied by the [I796]LC_CTYPE[/I796] category of the current locale. [IMG797]
[p_00805] [S798][[A799]CX[/A799]][/S798] [IMG800] On streams that were not opened with [A801][I802]open_wmemstream[/I802]()[/A801], [IMG803] the wide-character output functions convert wide characters to (possibly multi-byte) characters and write them to the stream as if they were written by successive calls to the [A804][I805]fputwc[/I805]()[/A804] function. Each conversion shall occur as if by a call to the [A806][I807]wcrtomb[/I807]()[/A806] function, with the conversion state described by the stream's own [B808]mbstate_t[/B808] object, [S809][[A810]CX[/A810]][/S809] [IMG811] &nbsp;except the encoding rule associated with the stream is used instead of the encoding rule implied by the [I812]LC_CTYPE[/I812] category of the current locale. [IMG813]
[p_00806] An &quot;encoding error&quot; shall occur if the character sequence presented to the underlying [A814][I815]mbrtowc[/I815]()[/A814] function does not form a valid (generalized) character, or if the code value passed to the underlying [A816][I817]wcrtomb[/I817]()[/A816] function does not correspond to a valid (generalized) character. The wide-character input/output functions and the byte input/output functions store the value of the macro [EILSEQ] in [I818]errno[/I818] if and only if an encoding error occurs.
