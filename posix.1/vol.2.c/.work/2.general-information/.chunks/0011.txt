[h3_01131] [A1519][/A1519]2.10 Sockets
[p_01132] A socket is an endpoint for communication using the facilities described in this section. A socket is created with a specific socket type, described in [A1520]2.10.6 Socket Types[/A1520], and is associated with a specific protocol, detailed in [A1521]2.10.3 Protocols[/A1521]. A socket is accessed via a file descriptor obtained when the socket is created.
[h4_01133] [A1522][/A1522]2.10.1 Address Families
[p_01134] All network protocols are associated with a specific address family. An address family provides basic services to the protocol implementation to allow it to function within a specific network environment. These services may include packet fragmentation and reassembly, routing, addressing, and basic transport. An address family is normally comprised of a number of protocols, one per socket type. Each protocol is characterized by an abstract socket type. It is not required that an address family support all socket types. An address family may contain multiple protocols supporting the same socket abstraction.
[p_01135] [A1523]2.10.17 Use of Sockets for Local UNIX Connections[/A1523], [A1524]2.10.19 Use of Sockets over Internet Protocols Based on IPv4[/A1524], and [A1525]2.10.20 Use of Sockets over Internet Protocols Based on IPv6[/A1525], respectively, describe the use of sockets for local UNIX connections, for Internet protocols based on IPv4, and for Internet protocols based on IPv6.
[h4_01136] [A1526][/A1526]2.10.2 Addressing
[p_01137] An address family defines the format of a socket address. All network addresses are described using a general structure, called a [B1527]sockaddr[/B1527], as defined in the Base Definitions volume of POSIX.1-2024, [A1528][I1529]&lt;sys/socket.h&gt;[/I1529][/A1528]. However, each address family imposes finer and more specific structure, generally defining a structure with fields specific to the address family. The field [I1530]sa_family[/I1530] in the [B1531]sockaddr[/B1531] structure contains the address family identifier, specifying the format of the [I1532]sa_data[/I1532] area. The size of the [I1533]sa_data[/I1533] area is unspecified.
[h4_01138] [A1534][/A1534]2.10.3 Protocols
[p_01139] A protocol supports one of the socket abstractions detailed in [A1535]2.10.6 Socket Types[/A1535]. Selecting a protocol involves specifying the address family, socket type, and protocol number to the [A1536][I1537]socket[/I1537]()[/A1536] function. Certain semantics of the basic socket abstractions are protocol-specific. All protocols are expected to support the basic model for their particular socket type, but may, in addition, provide non-standard facilities or extensions to a mechanism.
[h4_01140] [A1538][/A1538]2.10.4 Routing
[p_01141] Sockets provides packet routing facilities. A routing information database is maintained, which is used in selecting the appropriate network interface when transmitting packets.
[h4_01142] [A1539][/A1539]2.10.5 Interfaces
[p_01143] Each network interface in a system corresponds to a path through which messages can be sent and received. A network interface usually has a hardware device associated with it, though certain interfaces such as the loopback interface, do not.
[h4_01144] [A1540][/A1540]2.10.6 Socket Types
[p_01145] A socket is created with a specific type, which defines the communication semantics and which allows the selection of an appropriate communication protocol. Four types are defined: SOCK_DGRAM, [S1541][[A1542]RS[/A1542]][/S1541] [IMG1543] &nbsp;SOCK_RAW, [IMG1544] SOCK_SEQPACKET, and SOCK_STREAM. Implementations may specify additional socket types.
[p_01146] The SOCK_STREAM socket type provides reliable, sequenced, full-duplex octet streams between the socket and a peer to which the socket is connected. A socket of type SOCK_STREAM needs to be in a connected state before any data can be sent or received. Record boundaries are not maintained; data sent on a stream socket using output operations of one size can be received using input operations of smaller or larger sizes without loss of data. Data may be buffered; successful return from an output function does not imply that the data has been delivered to the peer or even transmitted from the local system. If data cannot be successfully transmitted within a given time then the connection is considered broken, and subsequent operations shall fail. A SIGPIPE signal is raised if a thread attempts to send data on a broken stream (one that is no longer connected), except that the signal is suppressed if the MSG_NOSIGNAL flag is used in calls to [A1545][I1546]send[/I1546]()[/A1545], [A1547][I1548]sendto[/I1548]()[/A1547], and [A1549][I1550]sendmsg[/I1550]()[/A1549]. Support for an out-of-band data transmission facility is protocol-specific.
[p_01147] The SOCK_SEQPACKET socket type is similar to the SOCK_STREAM type, and is also connection-oriented. The only difference between these types is that record boundaries are maintained using the SOCK_SEQPACKET type. A record can be sent using one or more output operations and received using one or more input operations, but a single operation never transfers parts of more than one record. Record boundaries are visible to the receiver via the MSG_EOR flag in the received message flags returned by the [A1551][I1552]recvmsg[/I1552]()[/A1551] function. It is protocol-specific whether a maximum record size is imposed.
[p_01148] The SOCK_DGRAM socket type supports connectionless data transfer which is not necessarily acknowledged or reliable. Datagrams can be sent to the address specified (possibly multicast or broadcast) in each output operation, and incoming datagrams can be received from multiple sources. The source address of each datagram is available when receiving the datagram. An application can also pre-specify a peer address, in which case calls to output functions that do not specify a peer address shall send to the pre-specified peer. If a peer has been specified, only datagrams from that peer shall be received. A datagram shall be sent in a single output operation, and needs to be received in a single input operation. The maximum size of a datagram is protocol-specific; with some protocols, the limit is implementation-defined. Output datagrams may be buffered within the system; thus, a successful return from an output function does not guarantee that a datagram is actually sent or received. However, implementations should attempt to detect any errors possible before the return of an output function, reporting any error by an unsuccessful return value.
[p_01149] [S1553][[A1554]RS[/A1554]][/S1553] [IMG1555] The SOCK_RAW socket type is similar to the SOCK_DGRAM type. It differs in that it is normally used with communication providers that underlie those used for the other socket types. For this reason, the creation of a socket with type SOCK_RAW shall require appropriate privileges. The format of datagrams sent and received with this socket type generally include specific protocol headers, and the formats are protocol-specific and implementation-defined. [IMG1556]
[h4_01150] [A1557][/A1557]2.10.7 Socket I/O Mode
[p_01151] The I/O mode of a socket is described by the O_NONBLOCK file status flag which pertains to the open file description for the socket. This flag is initially off when a socket is created, but may be set and cleared by the use of the F_SETFL command of the [A1558][I1559]fcntl[/I1559]()[/A1558] function.
[p_01152] When the O_NONBLOCK flag is set, certain functions that would normally block until they are complete shall return immediately.
[p_01153] The [A1560][I1561]bind[/I1561]()[/A1560] function initiates an address assignment and shall return without blocking when O_NONBLOCK is set; if the socket address cannot be assigned immediately, [A1562][I1563]bind[/I1563]()[/A1562] shall return the [EINPROGRESS] error to indicate that the assignment was initiated successfully, but that it has not yet completed.
[p_01154] The [A1564][I1565]connect[/I1565]()[/A1564] function initiates a connection and shall return without blocking when O_NONBLOCK is set; it shall return the error [EINPROGRESS] to indicate that the connection was initiated successfully, but that it has not yet completed.
[p_01155] Data transfer operations (the [A1566][I1567]read[/I1567]()[/A1566], [A1568][I1569]write[/I1569]()[/A1568], [A1570][I1571]send[/I1571]()[/A1570], and [A1572][I1573]recv[/I1573]()[/A1572] functions) shall complete immediately, transfer only as much as is available, and then return without blocking, or return an error indicating that no transfer could be made without blocking.
[h4_01156] [A1574][/A1574]2.10.8 Socket Owner
[p_01157] The owner of a socket is unset when a socket is created. The owner may be set to a process ID or process group ID using the F_SETOWN command of the [A1575][I1576]fcntl[/I1576]()[/A1575] function.
[h4_01158] [A1577][/A1577]2.10.9 Socket Queue Limits
[p_01159] The transmit and receive queue sizes for a socket are set when the socket is created. The default sizes used are both protocol-specific and implementation-defined. The sizes may be changed using the [A1578][I1579]setsockopt[/I1579]()[/A1578] function.
[h4_01160] [A1580][/A1580]2.10.10 Pending Error
[p_01161] Errors may occur asynchronously, and be reported to the socket in response to input from the network protocol. The socket stores the pending error to be reported to a user of the socket at the next opportunity. The error is returned in response to a subsequent [A1581][I1582]send[/I1582]()[/A1581], [A1583][I1584]recv[/I1584]()[/A1583], or [A1585][I1586]getsockopt[/I1586]()[/A1585] operation on the socket, and the pending error is then cleared.
[h4_01162] [A1587][/A1587]2.10.11 Socket Receive Queue
[p_01163] A socket has a receive queue that buffers data when it is received by the system until it is removed by a receive call. Depending on the type of the socket and the communication provider, the receive queue may also contain ancillary data such as the addressing and other protocol data associated with the normal data in the queue, and may contain out-of-band or expedited data. The limit on the queue size includes any normal, out-of-band data, datagram source addresses, and ancillary data in the queue. The description in this section applies to all sockets, even though some elements cannot be present in some instances.
[p_01164] The contents of a receive buffer are logically structured as a series of data segments with associated ancillary data and other information. A data segment may contain normal data or out-of-band data, but never both. A data segment may complete a record if the protocol supports records (always true for types SOCK_SEQPACKET and SOCK_DGRAM). A record may be stored as more than one segment; the complete record might never be present in the receive buffer at one time, as a portion might already have been returned to the application, and another portion might not yet have been received from the communications provider. A data segment may contain ancillary protocol data, which is logically associated with the segment. Ancillary data is received as if it were queued along with the first normal data octet in the segment (if any). A segment may contain ancillary data only, with no normal or out-of-band data. For the purposes of this section, a datagram is considered to be a data segment that terminates a record, and that includes a source address as a special type of ancillary data. Data segments are placed into the queue as data is delivered to the socket by the protocol. Normal data segments are placed at the end of the queue as they are delivered. If a new segment contains the same type of data as the preceding segment and includes no ancillary data, and if the preceding segment does not terminate a record, the segments are logically merged into a single segment.
[p_01165] The receive queue is logically terminated if an end-of-file indication has been received or a connection has been terminated. A segment shall be considered to be terminated if another segment follows it in the queue, if the segment completes a record, or if an end-of-file or other connection termination has been reported. The last segment in the receive queue shall also be considered to be terminated while the socket has a pending error to be reported.
[p_01166] A receive operation shall never return data or ancillary data from more than one segment.
[h4_01167] [A1588][/A1588]2.10.12 Socket Out-of-Band Data State
[p_01168] The handling of received out-of-band data is protocol-specific. Out-of-band data may be placed in the socket receive queue, either at the end of the queue or before all normal data in the queue. In this case, out-of-band data is returned to an application program by a normal receive call. Out-of-band data may also be queued separately rather than being placed in the socket receive queue, in which case it shall be returned only in response to a receive call that requests out-of-band data. It is protocol-specific whether an out-of-band data mark is placed in the receive queue to demarcate data preceding the out-of-band data and following the out-of-band data. An out-of-band data mark is logically an empty data segment that cannot be merged with other segments in the queue. An out-of-band data mark is never returned in response to an input operation. The [A1589][I1590]sockatmark[/I1590]()[/A1589] function can be used to test whether an out-of-band data mark is the first element in the queue. If an out-of-band data mark is the first element in the queue when an input function is called without the MSG_PEEK option, the mark is removed from the queue and the following data (if any) is processed as if the mark had not been present.
[h4_01169] [A1591][/A1591]2.10.13 Connection Indication Queue
[p_01170] Sockets that are used to accept incoming connections maintain a queue of outstanding connection indications. This queue is a list of connections that are awaiting acceptance by the application; see [A1592][I1593]listen[/I1593]()[/A1592].
[h4_01171] [A1594][/A1594]2.10.14 Signals
[p_01172] One category of event at the socket interface is the generation of signals. These signals report protocol events or process errors relating to the state of the socket. The generation or delivery of a signal does not change the state of the socket, although the generation of the signal may have been caused by a state change.
[p_01173] The SIGPIPE signal shall be sent to a thread that attempts to send data on a socket that is no longer able to send (one that is no longer connected), except that the signal is suppressed if the MSG_NOSIGNAL flag is used in calls to [A1595][I1596]send[/I1596]()[/A1595], [A1597][I1598]sendto[/I1598]()[/A1597], and [A1599][I1600]sendmsg[/I1600]()[/A1599]. Regardless of whether the generation of the signal is suppressed, the send operation shall fail with the [EPIPE] error.
[p_01174] If a socket has an owner, the SIGURG signal is sent to the owner of the socket when it is notified of expedited or out-of-band data. The socket state at this time is protocol-dependent, and the status of the socket is specified in [A1601]2.10.17 Use of Sockets for Local UNIX Connections[/A1601], [A1602]2.10.19 Use of Sockets over Internet Protocols Based on IPv4[/A1602], and [A1603]2.10.20 Use of Sockets over Internet Protocols Based on IPv6[/A1603] . Depending on the protocol, the expedited data may or may not have arrived at the time of signal generation.
[h4_01175] [A1604][/A1604]2.10.15 Asynchronous Errors
[p_01176] If any of the following conditions occur asynchronously for a socket, the corresponding value listed below shall become the pending error for the socket:
[dt_01177] [ECONNABORTED]
[dd_01178] The connection was aborted locally.
[dt_01179] [ECONNREFUSED]
[dd_01180] For a connection-mode socket attempting a non-blocking connection, the attempt to connect was forcefully rejected. For a connectionless-mode socket, an attempt to deliver a datagram was forcefully rejected.
[dt_01181] [ECONNRESET]
[dd_01182] The peer has aborted the connection.
[dt_01183] [EHOSTUNREACH]
[dd_01184] The destination host is not reachable.
[dt_01185] [EMSGSIZE]
[dd_01186] For a connectionless-mode socket, the size of a previously sent datagram prevented delivery.
[dt_01187] [ENETDOWN]
[dd_01188] The local network connection is not operational.
[dt_01189] [ENETRESET]
[dd_01190] The connection was aborted by the network.
[dt_01191] [ENETUNREACH]
[dd_01192] The destination network is not reachable.
[h4_01193] [A1605][/A1605]2.10.16 Use of Options
[p_01194] There are a number of socket options which either specialize the behavior of a socket or provide useful information. These options may be set at different protocol levels and are always present at the uppermost &quot;socket&quot; level.
[p_01195] Socket options are manipulated by two functions, [A1606][I1607]getsockopt[/I1607]()[/A1606] and [A1608][I1609]setsockopt[/I1609]()[/A1608]. These functions allow an application program to customize the behavior and characteristics of a socket to provide the desired effect.
[p_01196] All of the options usable with [A1610][I1611]setsockopt[/I1611]()[/A1610] have defaults. For each option where a default value is listed as implementation-defined, the implementation also controls whether a socket created by [A1612][I1613]accept[/I1613]()[/A1612] or [A1614][I1615]accept4[/I1615]()[/A1614] starts with the option reset to the original default value, or inherited as the value previously customized on the original listening socket. The type and meaning of these values is defined by the protocol level to which they apply. Instead of using the default values, an application program may choose to customize one or more of the options. However, in the bulk of cases, the default values are sufficient for the application.
[p_01197] Some of the options are used to enable or disable certain behavior within the protocol modules (for example, turn on debugging) while others may be used to set protocol-specific information (for example, IP time-to-live on all the application's outgoing packets). As each of the options is introduced, its effect on the underlying protocol modules is described.

[p_01258] The SO_ACCEPTCONN option is used only on [A1661][I1662]getsockopt[/I1662]()[/A1661]. When this option is specified, [A1663][I1664]getsockopt[/I1664]()[/A1663] shall report whether socket listening is enabled for the socket. A value of zero shall indicate that socket listening is disabled; non-zero that it is enabled. SO_ACCEPTCONN has no default value.
[p_01259] The SO_BROADCAST option requests permission to send broadcast datagrams on the socket. Support for SO_BROADCAST is protocol-specific. The default for SO_BROADCAST is that the ability to send broadcast datagrams on a socket is disabled.
[p_01260] The SO_DEBUG option enables debugging in the underlying protocol modules. This can be useful for tracing the behavior of the underlying protocol modules during normal system operation. The semantics of the debug reports are implementation-defined. The default value for SO_DEBUG is for debugging to be turned off.
[p_01261] The SO_DOMAIN option is used only on [A1665][I1666]getsockopt[/I1666]()[/A1665]. When this option is specified, [A1667][I1668]getsockopt[/I1668]()[/A1667] shall return the domain of the socket (for example, AF_INET6). SO_DOMAIN has no default value.
[p_01262] The SO_DONTROUTE option requests that outgoing messages bypass the standard routing facilities. The destination needs to be on a directly-connected network, and messages are directed to the appropriate network interface according to the destination address. It is protocol-specific whether this option has any effect and how the outgoing network interface is chosen. Support for this option with each protocol is implementation-defined.
[p_01263] The SO_ERROR option is used only on [A1669][I1670]getsockopt[/I1670]()[/A1669]. When this option is specified, [A1671][I1672]getsockopt[/I1672]()[/A1671] shall return any pending error on the socket and clear the error status. It shall return a value of 0 if there is no pending error. SO_ERROR may be used to check for asynchronous errors on connected connectionless-mode sockets or for other types of asynchronous errors. SO_ERROR has no default value.
[p_01264] The SO_KEEPALIVE option enables the periodic transmission of messages on a connected socket. The behavior of this option is protocol-specific. On a connection-mode socket for which a connection has been established, if SO_KEEPALIVE is enabled and the connected socket fails to respond to the keep-alive messages, the connection shall be broken. The default value for SO_KEEPALIVE is zero, specifying that this capability is turned off.
[p_01265] The SO_LINGER option controls the action of the interface when unsent messages are queued on a socket and a [A1673][I1674]close[/I1674]()[/A1673] is performed. The details of this option are protocol-specific. If SO_LINGER is enabled, the system shall block the calling thread during [A1675][I1676]close[/I1676]()[/A1675] until it can transmit the data or until the end of the interval indicated by the [I1677]l_linger[/I1677] member, whichever comes first. If SO_LINGER is not specified, and [A1678][I1679]close[/I1679]()[/A1678] is issued, the system handles the call in a way that allows the calling thread to continue as quickly as possible. The default value for SO_LINGER is zero, or off, for the [I1680]l_onoff[/I1680] element of the option value and zero seconds for the linger time specified by the [I1681]l_linger[/I1681] element.
[p_01266] The SO_OOBINLINE option is valid only on protocols that support out-of-band data. The SO_OOBINLINE option requests that out-of-band data be placed in the normal data input queue as received; it is then accessible using the [A1682][I1683]read[/I1683]()[/A1682] or [A1684][I1685]recv[/I1685]()[/A1684] functions without the MSG_OOB flag set. The default for SO_OOBINLINE is off; that is, for out-of-band data not to be placed in the normal data input queue.
[p_01267] The SO_PROTOCOL option is used only on [A1686][I1687]getsockopt[/I1687]()[/A1686]. When this option is specified, [A1688][I1689]getsockopt[/I1689]()[/A1688] shall return the socket protocol (for example, IPPROTO_TCP). SO_PROTOCOL has no default value.
[p_01268] The SO_RCVBUF option requests that the buffer space allocated for receive operations on this socket be set to the value, in bytes, of the option value. Applications may wish to increase buffer size for high volume connections, or may decrease buffer size to limit the possible backlog of incoming data. The default value for the SO_RCVBUF option value is implementation-defined, and may vary by protocol.
[p_01269] The SO_RCVLOWAT option sets the minimum number of bytes to process for socket input operations. In general, receive calls block until any (non-zero) amount of data is received, then return the smaller of the amount available or the amount requested. The default value for SO_RCVLOWAT is 1, and does not affect the general case. If SO_RCVLOWAT is set to a larger value, blocking receive calls normally wait until they have received the smaller of the low water mark value or the requested amount. Receive calls may still return less than the low water mark if an error occurs, a signal is caught, or the type of data next in the receive queue is different from that returned (for example, out-of-band data). As mentioned previously, the default value for SO_RCVLOWAT is 1 byte. It is implementation-defined whether the SO_RCVLOWAT option can be set.
[p_01270] The SO_RCVTIMEO option is an option to set a timeout value for input operations. It accepts a [B1690]timeval[/B1690] structure with the number of seconds and microseconds specifying the limit on how long to wait for an input operation to complete. If a receive operation has blocked for this much time without receiving additional data, it shall return with a partial count or [I1691]errno[/I1691] shall be set to [EAGAIN] or [EWOULDBLOCK] if no data were received. The default for this option is the value zero, which indicates that a receive operation will not time out. It is implementation-defined whether the SO_RCVTIMEO option can be set.
[p_01271] The SO_REUSEADDR option indicates that the rules used in validating addresses supplied in a [A1692][I1693]bind[/I1693]()[/A1692] should allow reuse of local addresses. Operation of this option is protocol-specific. The default value for SO_REUSEADDR is off; that is, reuse of local addresses is not permitted.
[p_01272] The SO_SNDBUF option requests that the buffer space allocated for send operations on this socket be set to the value, in bytes, of the option value. The default value for the SO_SNDBUF option value is implementation-defined, and may vary by protocol.
[p_01273] The SO_SNDLOWAT option sets the minimum number of bytes to process for socket output operations. Most output operations process all of the data supplied by the call, delivering data to the protocol for transmission and blocking as necessary for flow control. Non-blocking output operations process as much data as permitted subject to flow control without blocking, but process no data if flow control does not allow the smaller of the send low water mark value or the entire request to be processed. A [A1694][I1695]select[/I1695]()[/A1694] operation testing the ability to write to a socket shall return true only if the send low water mark could be processed. The default value for SO_SNDLOWAT is implementation-defined and protocol-specific. It is implementation-defined whether the SO_SNDLOWAT option can be set.
[p_01274] The SO_SNDTIMEO option is an option to set a timeout value for the amount of time that an output function shall block because flow control prevents data from being sent. As noted in [A1696]Socket-Level Options[/A1696], the option value is a [B1697]timeval[/B1697] structure with the number of seconds and microseconds specifying the limit on how long to wait for an output operation to complete. If a send operation has blocked for this much time, it shall return with a partial count or [I1698]errno[/I1698] set to [EAGAIN] or [EWOULDBLOCK] if no data were sent. The default for this option is the value zero, which indicates that a send operation will not time out. It is implementation-defined whether the SO_SNDTIMEO option can be set.
[p_01275] The SO_TYPE option is used only on [A1699][I1700]getsockopt[/I1700]()[/A1699]. When this option is specified, [A1701][I1702]getsockopt[/I1702]()[/A1701] shall return the type of the socket (for example, SOCK_STREAM). This option is useful to servers that inherit sockets on start-up. SO_TYPE has no default value.

[h4_01298] [A1754][/A1754]2.10.20 Use of Sockets over Internet Protocols Based on IPv6
[p_01299] [S1755][[A1756]IP6[/A1756]][/S1755] [IMG1757] This section describes extensions to support sockets over Internet protocols based on IPv6. The functionality described in this section shall be provided on implementations that support the IPV6 option (and the rest of this section is not further shaded for this option). [IMG1758]
[p_01300] IPv6 is described in RFC&nbsp;8200.
[p_01301] To enable smooth transition from IPv4 to IPv6, the features defined in this section may, in certain circumstances, also be used in connection with IPv4; see [A1759]2.10.20.2 Compatibility with IPv4[/A1759].
[h5_01302] [A1760][/A1760]2.10.20.1 Addressing
[p_01303] IPv6 overcomes the addressing limitations of earlier versions by using 128-bit addresses instead of 32-bit addresses. The IPv6 address architecture is described in RFC&nbsp;4291.
[p_01304] There are three kinds of IPv6 address:
[dt_01305] Unicast
[p_01306] A unicast address can be global, link-local (designed for use on a single link), or site-local (designed for systems not connected to the Internet). Link-local and site-local addresses need not be globally unique.
[dt_01307] Anycast
[p_01308] An anycast address is similar to a unicast address; the nodes to which an anycast address is assigned need to be explicitly configured to know that it is an anycast address.
[dt_01309] Multicast
[p_01310] An application can send multicast datagrams by simply specifying an IPv6 multicast address in the [I1761]address[/I1761] argument of [A1762][I1763]sendto[/I1763]()[/A1762]. To receive multicast datagrams, an application needs to join the multicast group (using [A1764][I1765]setsockopt[/I1765]()[/A1764] with IPV6_JOIN_GROUP) and bind to the socket the UDP port on which datagrams are to be received. Some applications should also bind the multicast group address to the socket, to prevent other datagrams destined to that port from being delivered to the socket.
[p_01311] A multicast address can be global, node-local, link-local, site-local, or organization-local.
[p_01312] The following special IPv6 addresses are defined:
[dt_01313] Unspecified
[dd_01314] An address that is not assigned to any interface and is used to indicate the absence of an address.
[dt_01315] Loopback
[dd_01316] A unicast address that is not assigned to any interface and can be used by a node to send packets to itself.
[p_01317] Two sets of IPv6 addresses are defined to correspond to IPv4 addresses:
[dt_01318] IPv4-compatible addresses
[dd_01319] These are assigned to nodes that support IPv6 and can be used when traffic is &quot;tunneled&quot; through IPv4.
[dt_01320] IPv4-mapped addresses
[dd_01321] These are used to represent IPv4 addresses in IPv6 address format; see [A1766]2.10.20.2 Compatibility with IPv4[/A1766].
[p_01322] The unspecified address and the loopback address shall not be treated as IPv4-compatible addresses.
[h5_01323] [A1767][/A1767]2.10.20.2 Compatibility with IPv4
[p_01324] The API provides the ability for IPv6 applications to interoperate with applications using IPv4, by using IPv4-mapped IPv6 addresses. These addresses can be generated automatically by the [A1768][I1769]getaddrinfo[/I1769]()[/A1768] function when the specified host has only IPv4 addresses.
[p_01325] Applications can use AF_INET6 sockets to open TCP connections to IPv4 nodes, or send UDP packets to IPv4 nodes, by simply encoding the destination's IPv4 address as an IPv4-mapped IPv6 address, and passing that address, within a [B1770]sockaddr_in6[/B1770] structure, in the [A1771][I1772]connect[/I1772]()[/A1771], [A1773][I1774]sendto[/I1774]()[/A1773], or [A1775][I1776]sendmsg[/I1776]()[/A1775] function. When applications use AF_INET6 sockets to accept TCP connections from IPv4 nodes, or receive UDP packets from IPv4 nodes, the system shall return the peer's address to the application in the [A1777][I1778]accept[/I1778]()[/A1777], [A1779][I1780]accept4[/I1780]()[/A1779], [A1781][I1782]recvfrom[/I1782]()[/A1781], [A1783][I1784]recvmsg[/I1784]()[/A1783], or [A1785][I1786]getpeername[/I1786]()[/A1785] function using a [B1787]sockaddr_in6[/B1787] structure encoded this way. If a node has an IPv4 address, then the implementation shall allow applications to communicate using that address via an AF_INET6 socket. In such a case, the address shall be represented at the API by the corresponding IPv4-mapped IPv6 address. Also, the implementation may allow an AF_INET6 socket bound to [B1788]in6addr_any[/B1788] to receive inbound connections and packets destined to one of the node's IPv4 addresses.
[p_01326] An application can use AF_INET6 sockets to bind to a node's IPv4 address by specifying the address as an IPv4-mapped IPv6 address in a [B1789]sockaddr_in6[/B1789] structure in the [A1790][I1791]bind[/I1791]()[/A1790] function. For an AF_INET6 socket bound to a node's IPv4 address, the system shall return the address in the [A1792][I1793]getsockname[/I1793]()[/A1792] function as an IPv4-mapped IPv6 address in a [B1794]sockaddr_in6[/B1794] structure.
[h5_01327] [A1795][/A1795]2.10.20.3 Interface Identification
[p_01328] Each local interface is assigned a unique positive integer as a numeric index. Indexes start at 1; zero is not used. There may be gaps so that there is no current interface for a particular positive index. Each interface also has a unique implementation-defined name.
[h5_01329] [A1796][/A1796]2.10.20.4 Options
[p_01330] The following options apply at the IPPROTO_IPV6 level:

[dt_01334] IPV6_LEAVE_GROUP

[p_01336] The parameter type of this option is a pointer to an [B1802]ipv6_mreq[/B1802] structure.
[dt_01337] IPV6_MULTICAST_HOPS
[p_01338] The parameter type of this option is a pointer to an [B1803]int[/B1803]. (Default value: 1)
[dt_01339] IPV6_MULTICAST_IF
[p_01340] The parameter type of this option is a pointer to an [B1804]unsigned int[/B1804]. (Default value: 0)
[dt_01341] IPV6_MULTICAST_LOOP
[p_01342] The parameter type of this option is a pointer to an [B1805]unsigned int[/B1805] which is used as a Boolean value. (Default value: 1)
[dt_01343] IPV6_UNICAST_HOPS
[p_01344] The parameter type of this option is a pointer to an [B1806]int[/B1806]. (Default value: Unspecified)
[dt_01345] IPV6_V6ONLY
