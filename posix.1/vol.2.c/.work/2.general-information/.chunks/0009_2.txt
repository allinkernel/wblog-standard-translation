[h5_00908] [A994][/A994]2.8.3.4 Typed Memory Objects
[p_00909] [S995][[A996]TYM[/A996]][/S995] [IMG997] The functionality described in this section shall be provided on implementations that support the Typed Memory Objects option (and the rest of this section is not further marked for this option). [IMG998]
[p_00910] Implementations may support the Typed Memory Objects option independently of support for memory mapped files or shared memory objects. Typed memory objects are implementation-configurable named storage pools accessible from one or more processors in a system, each via one or more ports, such as backplane buses, LANs, I/O channels, and so on. Each valid combination of a storage pool and a port is identified through a name that is defined at system configuration time, in an implementation-defined manner; the name may be independent of the file system. Using this name, a typed memory object can be opened and mapped into process address space. For a given storage pool and port, it is necessary to support both dynamic allocation from the pool as well as mapping at an application-supplied offset within the pool; when dynamic allocation has been performed, subsequent deallocation shall be supported. Lastly, accessing typed memory objects from different ports requires a method for obtaining the offset and length of contiguous storage of a region of typed memory (dynamically allocated or not); this allows typed memory to be shared among processes and/or processors while being accessed from the desired port.
[h4_00911] [A999][/A999]2.8.4 Process Scheduling
[p_00912] [S1000][[A1001]PS[/A1001]][/S1000] [IMG1002] The functionality described in this section shall be provided on implementations that support the Process Scheduling option (and the rest of this section is not further marked for this option). [IMG1003]
[h5_00913] [A1004][/A1004]Scheduling Policies
[p_00914] The scheduling semantics described in this volume of POSIX.1-2024 are defined in terms of a conceptual model that contains a set of thread lists. No implementation structures are necessarily implied by the use of this conceptual model. It is assumed that no time elapses during operations described using this model, and therefore no simultaneous operations are possible. This model discusses only processor scheduling for runnable threads, but it should be noted that greatly enhanced predictability of realtime applications results if the sequencing of other resources takes processor scheduling policy into account.
[p_00915] There is, conceptually, one thread list for each priority. A runnable thread shall be on the thread list for that thread's priority. Multiple scheduling policies shall be provided. Each non-empty thread list is ordered, contains a head as one end of its order, and a tail as the other. The purpose of a scheduling policy is to define the allowable operations on this set of lists (for example, moving threads between and within lists).
[p_00916] The POSIX model treats a &quot;process&quot; as an aggregation of system resources, including one or more threads that may be scheduled by the operating system on the processor(s) it controls. Although a process has its own set of scheduling attributes, these have an indirect effect (if any) on the scheduling behavior of individual threads as described below.
[p_00917] Each thread shall be controlled by an associated scheduling policy and priority. These parameters may be specified by explicit application execution of the [A1005][I1006]pthread_setschedparam[/I1006]()[/A1005] function. Additionally, the scheduling parameters of a thread (but not its scheduling policy) may be changed by application execution of the [A1007][I1008]pthread_setschedprio[/I1008]()[/A1007] function.
[p_00918] Each process shall be controlled by an associated scheduling policy and priority. These parameters may be specified by explicit application execution of the [A1009][I1010]sched_setscheduler[/I1010]()[/A1009] or [A1011][I1012]sched_setparam[/I1012]()[/A1011] functions.
[p_00919] The effect of the process scheduling attributes on individual threads in the process is dependent on the scheduling contention scope of the threads (see [A1013]2.9.4 Thread Scheduling[/A1013]):
[li_00920] For threads with system scheduling contention scope, the process scheduling attributes shall have no effect on the scheduling attributes or behavior either of the thread or an underlying kernel scheduling entity dedicated to that thread.
[li_00921] For threads with process scheduling contention scope, the process scheduling attributes shall have no effect on the scheduling attributes of the thread. However, any underlying kernel scheduling entity used by these threads shall at all times behave as specified by the scheduling attributes of the containing process, and this behavior may affect the scheduling behavior of the process contention scope threads. For example, a process contention scope thread with scheduling policy SCHED_FIFO and the system maximum priority [I1014]H[/I1014] (the value returned by [I1015]sched_get_priority_max[/I1015](SCHED_FIFO)) in a process with scheduling policy SCHED_RR and system minimum priority [I1016]L[/I1016] (the value returned by [I1017]sched_get_priority_min[/I1017](SCHED_RR)) shall be subject to timeslicing and to preemption by any thread with an effective priority higher than [I1018]L[/I1018].
[p_00922] Associated with each policy is a priority range. Each policy definition shall specify the minimum priority range for that policy. The priority ranges for each policy may but need not overlap the priority ranges of other policies.
[p_00923] A conforming implementation shall select the thread that is defined as being at the head of the highest priority non-empty thread list to become a running thread, regardless of its associated policy. This thread is then removed from its thread list.
[p_00924] Four scheduling policies are specifically required. Other implementation-defined scheduling policies may be defined. The following symbols are defined in the Base Definitions volume of POSIX.1-2024, [A1019][I1020]&lt;sched.h&gt;[/I1020][/A1019]:
[dt_00925] SCHED_FIFO
[dd_00926] First in, first out (FIFO) scheduling policy.
[dt_00927] SCHED_RR
[dd_00928] Round robin scheduling policy.
[dt_00929] SCHED_SPORADIC
[dd_00930] [S1021][[A1022]SS[/A1022]][/S1021] [IMG1023] Sporadic server scheduling policy. [IMG1024]
[dt_00931] SCHED_OTHER
[dd_00932] Another scheduling policy.
[p_00933] The values of these symbols shall be distinct.
[h5_00934] [A1025][/A1025]SCHED_FIFO
[p_00935] Conforming implementations shall include a scheduling policy called the FIFO scheduling policy.
[p_00936] Threads scheduled under this policy are chosen from a thread list that is ordered by the time its threads have been on the list without being executed; generally, the head of the list is the thread that has been on the list the longest time, and the tail is the thread that has been on the list the shortest time.
[p_00937] Under the SCHED_FIFO policy, the modification of the definitional thread lists is as follows:
[li_00938] When a running thread becomes a preempted thread, it becomes the head of the thread list for its priority.
[li_00939] When a blocked thread becomes a runnable thread, it becomes the tail of the thread list for its priority.
[li_00940] When a running thread calls the [A1026][I1027]sched_setscheduler[/I1027]()[/A1026] function, the process specified in the function call is modified to the specified policy and the priority specified by the [I1028]param[/I1028] argument.
[li_00941] When a running thread calls the [A1029][I1030]sched_setparam[/I1030]()[/A1029] function, the priority of the process specified in the function call is modified to the priority specified by the [I1031]param[/I1031] argument.
[li_00942] When a running thread calls the [A1032][I1033]pthread_setschedparam[/I1033]()[/A1032] function, the thread specified in the function call is modified to the specified policy and the priority specified by the [I1034]param[/I1034] argument.
[li_00943] When a running thread calls the [A1035][I1036]pthread_setschedprio[/I1036]()[/A1035] function, the thread specified in the function call is modified to the priority specified by the [I1037]prio[/I1037] argument.
[li_00944] If a thread whose policy or priority has been modified other than by [A1038][I1039]pthread_setschedprio[/I1039]()[/A1038] is a running thread or is runnable, it then becomes the tail of the thread list for its new priority.
[li_00945] If a thread whose priority has been modified by [A1040][I1041]pthread_setschedprio[/I1041]()[/A1040] is a running thread or is runnable, the effect on its position in the thread list depends on the direction of the modification, as follows:  If the priority is raised, the thread becomes the tail of the thread list. If the priority is unchanged, the thread does not change position in the thread list. If the priority is lowered, the thread becomes the head of the thread list.
[li_00946] When a running thread issues the [A1042][I1043]sched_yield[/I1043]()[/A1042] or [A1044][I1045]thrd_yield[/I1045]()[/A1044] function, the thread becomes the tail of the thread list for its priority.
[li_00947] At no other time is the position of a thread with this scheduling policy within the thread lists affected.
[p_00948] While a thread is executing at a temporarily elevated priority as a consequence of owning a mutex initialized with the PTHREAD_PRIO_INHERIT or PTHREAD_PRIO_PROTECT protocol (see [A1046][I1047]pthread_mutexattr_getprotocol[/I1047]()[/A1046]), the effects of the above requirements on thread priority shall apply only to the thread's normal priority, not to its elevated priority, and those of the above requirements that describe the thread being placed on any thread list as a result of a priority change shall not apply. Likewise, when such a thread reverts to its normal priority as a consequence of unlocking such a mutex, those of the above requirements that describe the thread being placed on any thread list as a result of a priority change shall not apply.
[p_00949] For this policy, valid priorities shall be within the range returned by the [A1048][I1049]sched_get_priority_max[/I1049]()[/A1048] and [A1050][I1051]sched_get_priority_min[/I1051]()[/A1050] functions when SCHED_FIFO is provided as the parameter. Conforming implementations shall provide a priority range of at least 32 priorities for this policy.
[h5_00950] [A1052][/A1052]SCHED_RR
[p_00951] Conforming implementations shall include a scheduling policy called the &quot;round robin&quot; scheduling policy. This policy shall be identical to the SCHED_FIFO policy with the additional condition that when the implementation detects that a running thread has been executing as a running thread for a time period of the length returned by the [A1053][I1054]sched_rr_get_interval[/I1054]()[/A1053] function or longer, the thread shall become the tail of its thread list and the head of that thread list shall be removed and made a running thread.
[p_00952] The effect of this policy is to ensure that if there are multiple SCHED_RR threads at the same priority, one of them does not monopolize the processor. An application should not rely only on the use of SCHED_RR to ensure application progress among multiple threads if the application includes threads using the SCHED_FIFO policy at the same or higher priority levels or SCHED_RR threads at a higher priority level.
[p_00953] A thread under this policy that is preempted and subsequently resumes execution as a running thread completes the unexpired portion of its round robin interval time period.
[p_00954] For this policy, valid priorities shall be within the range returned by the [A1055][I1056]sched_get_priority_max[/I1056]()[/A1055] and [A1057][I1058]sched_get_priority_min[/I1058]()[/A1057] functions when SCHED_RR is provided as the parameter. Conforming implementations shall provide a priority range of at least 32 priorities for this policy.
[h5_00955] [A1059][/A1059]SCHED_SPORADIC
[p_00956] [S1060][[A1061]SS|TSP[/A1061]][/S1060] [IMG1062] The functionality described in this section shall be provided on implementations that support the Process Sporadic Server or Thread Sporadic Server options (and the rest of this section is not further marked for these options). [IMG1063]
[p_00957] If _POSIX_SPORADIC_SERVER or _POSIX_THREAD_SPORADIC_SERVER is defined, the implementation shall include a scheduling policy identified by the value SCHED_SPORADIC.
[p_00958] The sporadic server policy is based primarily on two time parameters: the replenishment period and the available execution capacity. The replenishment period is given by the [I1064]sched_ss_repl_period[/I1064] member of the [B1065]sched_param[/B1065] structure. The available execution capacity is initialized to the value given by the [I1066]sched_ss_init_budget[/I1066] member of the same parameter. The sporadic server policy is identical to the SCHED_FIFO policy with some additional conditions that cause the thread's assigned priority to be switched between the values specified by the [I1067]sched_priority[/I1067] and [I1068]sched_ss_low_priority[/I1068] members of the [B1069]sched_param[/B1069] structure.
[p_00959] The priority assigned to a thread using the sporadic server scheduling policy is determined in the following manner: if the available execution capacity is greater than zero and the number of pending replenishment operations is strictly less than [I1070]sched_ss_max_repl[/I1070], the thread is assigned the priority specified by [I1071]sched_priority[/I1071]; otherwise, the assigned priority shall be [I1072]sched_ss_low_priority[/I1072]. If the value of [I1073]sched_priority[/I1073] is less than or equal to the value of [I1074]sched_ss_low_priority[/I1074], the results are undefined. When active, the thread shall belong to the thread list corresponding to its assigned priority level, according to the mentioned priority assignment. The modification of the available execution capacity and, consequently of the assigned priority, is done as follows:
[li_00960] When the thread at the head of the [I1075]sched_priority[/I1075] list becomes a running thread, its execution time shall be limited to at most its available execution capacity, plus the resolution of the execution time clock used for this scheduling policy. This resolution shall be implementation-defined.
[li_00961] Each time the thread is inserted at the tail of the list associated with [I1076]sched_priority[/I1076]—because as a blocked thread it became runnable with priority [I1077]sched_priority[/I1077] or because a replenishment operation was performed—the time at which this operation is done is posted as the [I1078]activation_time[/I1078].
[li_00962] When the running thread with assigned priority equal to [I1079]sched_priority[/I1079] becomes a preempted thread, it becomes the head of the thread list for its priority, and the execution time consumed is subtracted from the available execution capacity. If the available execution capacity would become negative by this operation, it shall be set to zero.
[li_00963] When the running thread with assigned priority equal to [I1080]sched_priority[/I1080] becomes a blocked thread, the execution time consumed is subtracted from the available execution capacity, and a replenishment operation is scheduled, as described in 6 and 7. If the available execution capacity would become negative by this operation, it shall be set to zero.
[li_00964] When the running thread with assigned priority equal to [I1081]sched_priority[/I1081] reaches the limit imposed on its execution time, it becomes the tail of the thread list for [I1082]sched_ss_low_priority[/I1082], the execution time consumed is subtracted from the available execution capacity (which becomes zero), and a replenishment operation is scheduled, as described in 6 and 7.
[li_00965] Each time a replenishment operation is scheduled, the amount of execution capacity to be replenished, [I1083]replenish_amount[/I1083], is set equal to the execution time consumed by the thread since the [I1084]activation_time[/I1084]. The replenishment is scheduled to occur at [I1085]activation_time[/I1085] plus [I1086]sched_ss_repl_period[/I1086]. If the scheduled time obtained is before the current time, the replenishment operation is carried out immediately. Several replenishment operations can be pending at the same time, each of which shall be serviced at its respective scheduled time. With the above rules, the number of replenishment operations simultaneously pending for a given thread that is scheduled under the sporadic server policy shall not be greater than [I1087]sched_ss_max_repl[/I1087].
