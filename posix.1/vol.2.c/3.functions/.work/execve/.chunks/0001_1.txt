[h4_00005] [A4][/A4]DESCRIPTION
[p_00006] The [I5]exec[/I5] family of functions shall replace the current process image with a new process image. The new image shall be constructed from a regular, executable file called the [I6]new process image file[/I6]. There shall be no return from a successful [I7]exec[/I7], because the calling process image is overlaid by the new process image.
[p_00007] The [I8]fexecve[/I8]() function shall be equivalent to the [I9]execve[/I9]() function except that the file to be executed is determined by the file descriptor [I10]fd[/I10] instead of a pathname. The file offset of [I11]fd[/I11] is ignored.

[p_00011] Applications can change the entire environment in a single operation by assigning the [I19]environ[/I19] variable to point to an array of character pointers to the new environment strings. After assigning a new value to [I20]environ[/I20], applications should not rely on the new environment strings remaining part of the environment, as a call to [A21][I22]getenv[/I22]()[/A21], [A23][I24]secure_getenv[/I24]()[/A23], [S25][[A26]XSI[/A26]][/S25] [IMG27] [A28][I29]putenv[/I29]()[/A28], [IMG30] [A31][I32]setenv[/I32]()[/A31], [A33][I34]unsetenv[/I34]()[/A33], or any function that is dependent on an environment variable may, on noticing that [I35]environ[/I35] has changed, copy the environment strings to a new array and assign [I36]environ[/I36] to point to it.
[p_00012] Any application that directly modifies the pointers to which the [I37]environ[/I37] variable points has undefined behavior.
[p_00013] Conforming multi-threaded applications shall not use the [I38]environ[/I38] variable to access or modify any environment variable while any other thread is concurrently modifying any environment variable. A call to any function dependent on any environment variable shall be considered a use of the [I39]environ[/I39] variable to access that environment variable.
[p_00014] The arguments specified by a program with one of the [I40]exec[/I40] functions shall be passed on to the new process image in the corresponding [I41]main[/I41]() arguments.
[p_00015] For the [I42]execl[/I42](), [I43]execle[/I43](), [I44]execv[/I44](), and [I45]execve[/I45]() functions, the argument [I46]path[/I46] points to a pathname that identifies the new process image file.
[p_00016] For the [I47]execlp[/I47]() and [I48]execvp[/I48]() functions, the argument [I49]file[/I49] is used to construct a pathname that identifies the new process image file. If the [I50]file[/I50] argument contains a &lt;slash&gt; character, the [I51]file[/I51] argument shall be used as the pathname for this file. Otherwise, the path prefix for this file is obtained by a search of the directories passed as the environment variable [I52]PATH[/I52] (see XBD [A53][I54]8. Environment Variables[/I54][/A53]). If this environment variable is not present, the results of the search are implementation-defined.

[p_00023] The number of bytes available for the new process' combined argument and environment lists is {ARG_MAX}. It is implementation-defined whether null terminators, pointers, and/or any alignment bytes are included in this total.

For any file descriptor that is closed for this reason, process-owned file locks that the calling process owns on the file associated with the file descriptor shall be unlocked as a result of the close, as described in [A90][I91]close[/I91]()[/A90]. File locks that are not unlocked by closing of file descriptors remain unchanged.

If a standard utility or a conforming application is executed with file descriptor 0 not open for reading or with file descriptor 1 or 2 not open for writing, the environment in which the utility or application is executed shall be deemed non-conforming, and consequently the utility or application might not behave as described in this standard.
[p_00026] Directory streams open in the calling process image shall be closed in the new process image.

[h4_00082] [A230][/A230]ERRORS
[p_00083] The [I231]exec[/I231] functions shall fail if:
[dt_00084] [E2BIG]
[dd_00085] The number of bytes used by the new process image's argument list and environment list is greater than the system-imposed limit of {ARG_MAX} bytes.
[dt_00086] [EACCES]
[dd_00087] The new process image file is not a regular file and the implementation does not support execution of files of its type.
[dt_00088] [EINVAL]
[dd_00089] The new process image file has appropriate privileges and has a recognized executable binary format, but the system does not support execution of a file with this format.
[p_00090] The [I232]exec[/I232] functions, except for [I233]fexecve[/I233](), shall fail if:
[dt_00091] [EACCES]
[dd_00092] Search permission is denied for a directory listed in the new process image file's path prefix, or the new process image file denies execution permission.
[dt_00093] [ELOOP]
[dd_00094] A loop exists in symbolic links encountered during resolution of the [I234]path[/I234] or [I235]file[/I235] argument.
[dt_00095] [ENAMETOOLONG]
[dd_00096] The length of a component of a pathname is longer than {NAME_MAX}.
[dt_00097] [ENOENT]
[dd_00098] A component of [I236]path[/I236] or [I237]file[/I237] does not name an existing file or [I238]path[/I238] or [I239]file[/I239] is an empty string.
[dt_00099] [ENOTDIR]
[dd_00100] A component of the new process image file's path prefix names an existing file that is neither a directory nor a symbolic link to a directory, or the new process image file's pathname contains at least one non-&lt;slash&gt; character and ends with one or more trailing &lt;slash&gt; characters and the last pathname component names an existing file that is neither a directory nor a symbolic link to a directory.
[p_00101] The [I240]exec[/I240] functions, except for [I241]execlp[/I241]() and [I242]execvp[/I242](), shall fail if:
[dt_00102] [ENOEXEC]
[dd_00103] The new process image file has the appropriate access permission but has an unrecognized format.
[p_00104] The [I243]fexecve[/I243]() function shall fail if:
[dt_00105] [EBADF]
[dd_00106] The [I244]fd[/I244] argument is not a valid file descriptor open for executing.
[p_00107] The [I245]exec[/I245] functions may fail if:
[dt_00108] [ENOMEM]
[dd_00109] The new process image requires more memory than is allowed by the hardware or system-imposed memory management constraints.
[p_00110] The [I246]exec[/I246] functions, except for [I247]fexecve[/I247](), may fail if:
[dt_00111] [ELOOP]
[dd_00112] More than {SYMLOOP_MAX} symbolic links were encountered during resolution of the [I248]path[/I248] or [I249]file[/I249] argument.
[dt_00113] [ENAMETOOLONG]
[dd_00114] The length of the [I250]path[/I250] argument or the length of the pathname constructed from the [I251]file[/I251] argument exceeds {PATH_MAX}, or pathname resolution of a symbolic link produced an intermediate result with a length that exceeds {PATH_MAX}.
[dt_00115] [ETXTBSY]
[dd_00116] The new process image file is a pure procedure (shared text) file that is currently open for writing by some process.

[h4_00130] [A280][/A280]APPLICATION USAGE
[p_00131] As the state of conversion descriptors and message catalog descriptors in the new process image is undefined, conforming applications should not rely on their use and should close them prior to calling one of the [I281]exec[/I281] functions.
[p_00132] Applications that require other than the default POSIX locale as the global locale in the new process image should call [A282][I283]setlocale[/I283]()[/A282] with the appropriate parameters.
[p_00133] When assigning a new value to the [I284]environ[/I284] variable, applications should ensure that the environment to which it will point contains at least the following:
[p_00134] Any implementation-defined variables required by the implementation to provide a conforming environment. See the _CS_V8_ENV entry in [A285][I286]&lt;unistd.h&gt;[/I286][/A285] and [A287][I288]confstr[/I288]()[/A287] for details.
[p_00135] A value for [I289]PATH[/I289] which finds conforming versions of all standard utilities before any other versions.
[p_00136] The same constraint applies to the [I290]envp[/I290] array passed to [I291]execle[/I291]() or [I292]execve[/I292](), in order to ensure that the new process image is invoked in a conforming environment.
[p_00137] Applications should not execute programs with file descriptor 0 not open for reading or with file descriptor 1 or 2 not open for writing, as this might cause the executed program to misbehave. In order not to pass on these file descriptors to an executed program, applications should not just close them but should reopen them on, for example, [B293]/dev/null[/B293]. Some implementations may reopen them automatically, but applications should not rely on this being done.
[p_00138] If an application wants to perform an integrity test of the file being executed before executing it, the file will need to be opened with read permission to perform the integrity test.
[p_00139] Since execute permission is checked by [I294]fexecve[/I294](), the file description [I295]fd[/I295] need not have been opened with the O_EXEC flag. However, if the file to be executed denies read and write permission for the process preparing to do the [I296]exec[/I296], the only way to provide the [I297]fd[/I297] to [I298]fexecve[/I298]() will be to use the O_EXEC flag when opening [I299]fd[/I299]. In this case, the application will not be able to perform an integrity test since it will not be able to read the contents of the file.
[p_00140] Note that when a file descriptor is opened with O_RDONLY, O_RDWR, or O_WRONLY mode, the file descriptor can be used to read, read and write, or write the file, respectively, even if the mode of the file changes after the file was opened. Using the O_EXEC open mode is different; [I300]fexecve[/I300]() will ignore the mode that was used when the file descriptor was opened and the [I301]exec[/I301] will fail if the mode of the file associated with [I302]fd[/I302] does not grant execute permission to the calling process at the time [I303]fexecve[/I303]() is called.
[h4_00141] [A304][/A304]RATIONALE
[p_00142] Early proposals required that the value of [I305]argc[/I305] passed to [I306]main[/I306]() be &quot;one or greater&quot;. This was driven by the same requirement in drafts of the ISO&nbsp;C standard. In fact, historical implementations have passed a value of zero when no arguments are supplied to the caller of the [I307]exec[/I307] functions. This requirement was removed from the ISO&nbsp;C standard and subsequently removed from this volume of POSIX.1-2024 as well. The wording, in particular the use of the word [I308]should[/I308], requires a Strictly Conforming POSIX Application to pass at least one argument to the [I309]exec[/I309] function, thus guaranteeing that [I310]argc[/I310] be one or greater when invoked by such an application. In fact, this is good practice, since many existing applications reference [I311]argv[/I311][0] without first checking the value of [I312]argc[/I312].
[p_00143] The requirement on a Strictly Conforming POSIX Application also states that the value passed as the first argument be a filename string associated with the process being started. Although some existing applications pass a pathname rather than a filename string in some circumstances, a filename string is more generally useful, since the common usage of [I313]argv[/I313][0] is in printing diagnostics. In some cases the filename passed is not the actual filename of the file; for example, many implementations of the [I314]login[/I314] utility use a convention of prefixing a &lt;hyphen-minus&gt; ([CODE315]) to the actual filename, which indicates to the command interpreter being invoked that it is a &quot;login shell&quot;.
[p_00144] Also, note that the [A316][I317]test[/I317][/A316] and [I318][[/I318] utilities require specific strings for the [I319]argv[/I319][0] argument to have deterministic behavior across all implementations.
[p_00145] Historically, there have been two ways that implementations can [I320]exec[/I320] shell scripts.
[p_00146] One common historical implementation is that the [I321]execl[/I321](), [I322]execv[/I322](), [I323]execle[/I323](), and [I324]execve[/I324]() functions return an [ENOEXEC] error for any file not recognizable as executable, including a shell script. When the [I325]execlp[/I325]() and [I326]execvp[/I326]() functions encounter such a file, they assume the file to be a shell script and invoke a known command interpreter to interpret such files. This is now required by POSIX.1-2024. These implementations of [I327]execvp[/I327]() and [I328]execlp[/I328]() only give the [ENOEXEC] error in the rare case of a problem with the command interpreter's executable file. Because of these implementations, the [ENOEXEC] error is not mentioned for [I329]execlp[/I329]() or [I330]execvp[/I330](), although implementations can still give it.
[p_00147] Another way that some historical implementations handle shell scripts is by recognizing the first two bytes of the file as the character string [CODE331] and using the remainder of the first line of the file as the name of the command interpreter to execute.
[p_00148] One potential source of confusion noted by the standard developers is over how the contents of a process image file affect the behavior of the [I332]exec[/I332] family of functions. The following is a description of the actions taken:
[p_00149] If the process image file is a valid executable (in a format that is executable and valid and having appropriate privileges) for this system, then the system executes the file.
[p_00150] If the process image file has appropriate privileges and is in a format that is executable but not valid for this system (such as a recognized binary for another architecture), then this is an error and [I333]errno[/I333] is set to [EINVAL] (see later RATIONALE on [EINVAL]).
