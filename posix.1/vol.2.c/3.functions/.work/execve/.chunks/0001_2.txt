[p_00154] Applications that do not require to access their arguments may use the form:
[p_00155] Some implementations provide a third argument to [I339]main[/I339]() called [I340]envp[/I340]. This is defined as a pointer to the environment. The ISO&nbsp;C standard specifies invoking [I341]main[/I341]() with two arguments, so implementations are required to support applications written this way. Since this volume of POSIX.1-2024 defines the global variable [I342]environ[/I342], which is also provided by historical implementations and can be used anywhere that [I343]envp[/I343] could be used, there is no functional need for the [I344]envp[/I344] argument. Applications should use the [A345][I346]getenv[/I346]()[/A345] function rather than accessing the environment directly via either [I347]envp[/I347] or [I348]environ[/I348]. Implementations are required to support the two-argument calling sequence, but this does not prohibit an implementation from supporting [I349]envp[/I349] as an optional third argument.
[p_00156] This volume of POSIX.1-2024 specifies that signals set to SIG_IGN remain set to SIG_IGN, and that the new process image inherits the signal mask of the thread that called [I350]exec[/I350] in the old process image. This is consistent with historical implementations, and it permits some useful functionality, such as the [A351][I352]nohup[/I352][/A351] command. However, it should be noted that many existing applications wrongly assume that they start with certain signals set to the default action and/or unblocked. In particular, applications written with a simpler signal model that does not include blocking of signals, such as the one in the ISO&nbsp;C standard, may not behave properly if invoked with some signals blocked. Therefore, it is best not to block or ignore signals across [I353]exec[/I353]s without explicit reason to do so, and especially not to block signals across [I354]exec[/I354]s of arbitrary (not closely cooperating) programs.
[p_00157] The [I355]exec[/I355] functions always save the value of the effective user ID and effective group ID of the process at the completion of the [I356]exec[/I356], whether or not the set-user-ID or the set-group-ID bit of the process image file is set.

[p_00185] The ISO&nbsp;C standard and this volume of POSIX.1-2024 do not conflict on the use of [I374]environ[/I374], but some historical implementations of [I375]environ[/I375] may cause a conflict. As long as [I376]environ[/I376] is treated in the same way as an entry point (for example, [A377][I378]fork[/I378]()[/A377]), it conforms to both standards. A library can contain [A379][I380]fork[/I380]()[/A379], but if there is a user-provided [A381][I382]fork[/I382]()[/A381], that [A383][I384]fork[/I384]()[/A383] is given precedence and no problem ensues. The situation is similar for [I385]environ[/I385]: the definition in this volume of POSIX.1-2024 is to be used if there is no user-provided [I386]environ[/I386] to take precedence. At least three implementations are known to exist that solve this problem.
[dt_00186] [E2BIG]
[dd_00187] The limit {ARG_MAX} applies not just to the size of the argument list, but to the sum of that and the size of the environment list.
[dt_00188] [EFAULT]
[dd_00189] Some historical systems return [EFAULT] rather than [ENOEXEC] when the new process image file is corrupted. They are non-conforming.
[dt_00190] [EINVAL]
[dd_00191] This error condition was added to POSIX.1-2024 to allow an implementation to detect executable files generated for different architectures, and indicate this situation to the application. Historical implementations of shells, [I387]execvp[/I387](), and [I388]execlp[/I388]() that encounter an [ENOEXEC] error will execute a shell on the assumption that the file is a shell script. This will not produce the desired effect when the file is a valid executable for a different architecture. An implementation may now choose to avoid this problem by returning [EINVAL] when a valid executable for a different architecture is encountered. Some historical implementations return [EINVAL] to indicate that the [I389]path[/I389] argument contains a character with the high order bit set. The standard developers chose to deviate from historical practice for the following reasons:  The new utilization of [EINVAL] will provide some measure of utility to the user community. Historical use of [EINVAL] is not acceptable in an internationalized operating environment.
[dt_00192] [ENAMETOOLONG]
[dd_00193] Since the file pathname may be constructed by taking elements in the [I390]PATH[/I390] variable and putting them together with the filename, the [ENAMETOOLONG] error condition could also be reached this way.
[dt_00194] [ETXTBSY]
[dd_00195] System V returns this error when the executable file is currently open for writing by some process. This volume of POSIX.1-2024 neither requires nor prohibits this behavior.
[p_00196] Other systems (such as System V) may return [EINTR] from [I391]exec[/I391]. This is not addressed by this volume of POSIX.1-2024, but implementations may have a window between the call to [I392]exec[/I392] and the time that a signal could cause one of the [I393]exec[/I393] calls to return with [EINTR].

[p_00204] The purpose of the [I400]fexecve[/I400]() function is to enable executing a file which has been verified to be the intended file. It is possible to actively check the file by reading from the file descriptor and be sure that the file is not exchanged for another between the reading and the execution. Alternatively, a function like [A401][I402]openat[/I402]()[/A401] can be used to open a file which has been found by reading the content of a directory using [A403][I404]readdir[/I404]()[/A403].
[p_00205] When [I405]execlp[/I405]() or [I406]execvp[/I406]() fall back to invoking [A407][I408]sh[/I408][/A407] because of an [ENOEXEC] condition, the standard leaves the process name (what becomes [I409]argv[/I409][0] in the resulting [A410][I411]sh[/I411][/A410] process) unspecified. Existing implementations vary on whether they pass a variation of [CODE412], or preserve the original [I413]arg0[/I413].
