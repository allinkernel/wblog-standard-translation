[h4_00001] [A1][/A1]NAME
[blockquote_00002] kill — send a signal to a process or a group of processes
[h4_00003] [A2][/A2]SYNOPSIS
[blockquote_00004] [CODE3] [CODE4]
[h4_00005] [A5][/A5]DESCRIPTION
[p_00006] The [I6]kill[/I6]() function shall send a signal to a process or a group of processes specified by [I7]pid[/I7]. The signal to be sent is specified by [I8]sig[/I8] and is either one from the list given in [A9][I10]&lt;signal.h&gt;[/I10][/A9] or 0. If [I11]sig[/I11] is 0 (the null signal), error checking is performed but no signal is actually sent. The null signal can be used to check the validity of [I12]pid[/I12].
[p_00007] For a process to have permission to send a signal to a process designated by [I13]pid[/I13], unless the sending process has appropriate privileges, the real or effective user ID of the sending process shall match the real or saved set-user-ID of the receiving process.
[p_00008] If [I14]pid[/I14] is greater than 0, [I15]sig[/I15] shall be sent to the process whose process ID is equal to [I16]pid[/I16].
[p_00009] If [I17]pid[/I17] is 0, [I18]sig[/I18] shall be sent to all processes (excluding an unspecified set of system processes) whose process group ID is equal to the process group ID of the sender, and for which the process has permission to send a signal.
[p_00010] If [I19]pid[/I19] is -1, [I20]sig[/I20] shall be sent to all processes (excluding an unspecified set of system processes) for which the process has permission to send that signal.
[p_00011] If [I21]pid[/I21] is negative, but not -1, [I22]sig[/I22] shall be sent to all processes (excluding an unspecified set of system processes) whose process group ID is equal to the absolute value of [I23]pid[/I23], and for which the process has permission to send a signal.
[p_00012] If the value of [I24]pid[/I24] causes [I25]sig[/I25] to be generated for the sending process, and if [I26]sig[/I26] is not blocked for the calling thread and if no other thread has [I27]sig[/I27] unblocked or is waiting in a [A28][I29]sigwait[/I29]()[/A28] function for [I30]sig[/I30], either [I31]sig[/I31] or at least one pending unblocked signal shall be delivered to the sending thread before [I32]kill[/I32]() returns.
[p_00013] The user ID tests described above shall not be applied when sending SIGCONT to a process that is a member of the same session as the sending process.
[p_00014] An implementation that provides extended security controls may impose further implementation-defined restrictions on the sending of signals, including the null signal. In particular, the system may deny the existence of some or all of the processes specified by [I33]pid[/I33].
[p_00015] The [I34]kill[/I34]() function is successful if the process has permission to send [I35]sig[/I35] to any of the processes specified by [I36]pid[/I36]. If [I37]kill[/I37]() fails, no signal shall be sent.
[h4_00016] [A38][/A38]RETURN VALUE
[p_00017] Upon successful completion, 0 shall be returned. Otherwise, -1 shall be returned and [I39]errno[/I39] set to indicate the error.
[h4_00018] [A40][/A40]ERRORS
[p_00019] The [I41]kill[/I41]() function shall fail if:
[dt_00020] [EINVAL]
[dd_00021] The value of the [I42]sig[/I42] argument is an invalid or unsupported signal number.
[dt_00022] [EPERM]
[dd_00023] The process does not have permission to send the signal to any receiving process.
[dt_00024] [ESRCH]
[dd_00025] No process or process group can be found corresponding to that specified by [I43]pid[/I43].

[h4_00030] [A46][/A46]RATIONALE
[p_00031] The semantics for permission checking for [I47]kill[/I47]() differed between System V and most other implementations, such as Version 7 or 4.3 BSD. The semantics chosen for this volume of POSIX.1-2024 agree with System V. Specifically, a set-user-ID process cannot protect itself against signals (or at least not against SIGKILL) unless it changes its real user ID. This choice allows the user who starts an application to send it signals even if it changes its effective user ID. The other semantics give more power to an application that wants to protect itself from the user who ran it.
[p_00032] Some implementations provide semantic extensions to the [I48]kill[/I48]() function when the absolute value of [I49]pid[/I49] is greater than some maximum, or otherwise special, value. Negative values are a flag to [I50]kill[/I50](). Since most implementations return [ESRCH] in this case, this behavior is not included in this volume of POSIX.1-2024, although a conforming implementation could provide such an extension.
[p_00033] The unspecified processes to which a signal cannot be sent may include the scheduler or [I51]init[/I51].
[p_00034] There was initially strong sentiment to specify that, if [I52]pid[/I52] specifies that a signal be sent to the calling process and that signal is not blocked, that signal would be delivered before [I53]kill[/I53]() returns. This would permit a process to call [I54]kill[/I54]() and be guaranteed that the call never return. However, historical implementations that provide only the [A55][I56]signal[/I56]()[/A55] function make only the weaker guarantee in this volume of POSIX.1-2024, because they only deliver one signal each time a process enters the kernel. Modifications to such implementations to support the [A57][I58]sigaction[/I58]()[/A57] function generally require entry to the kernel following return from a signal-catching function, in order to restore the signal mask. Such modifications have the effect of satisfying the stronger requirement, at least when [A59][I60]sigaction[/I60]()[/A59] is used, but not necessarily when [A61][I62]signal[/I62]()[/A61] is used. The standard developers considered making the stronger requirement except when [A63][I64]signal[/I64]()[/A63] is used, but felt this would be unnecessarily complex. Implementors are encouraged to meet the stronger requirement whenever possible. In practice, the weaker requirement is the same, except in the rare case when two signals arrive during a very short window. This reasoning also applies to a similar requirement for [A65][I66]sigprocmask[/I66]()[/A65].
[p_00035] In 4.2 BSD, the SIGCONT signal can be sent to any descendant process regardless of user-ID security checks. This allows a job control shell to continue a job even if processes in the job have altered their user IDs (as in the [I67]su[/I67] command). In keeping with the addition of the concept of sessions, similar functionality is provided by allowing the SIGCONT signal to be sent to any process in the same session regardless of user ID security checks. This is less restrictive than BSD in the sense that ancestor processes (in the same session) can now be the recipient. It is more restrictive than BSD in the sense that descendant processes that form new sessions are now subject to the user ID checks. A similar relaxation of security is not necessary for the other job control signals since those signals are typically sent by the terminal driver in recognition of special characters being typed; the terminal driver bypasses all security checks.
[p_00036] In secure implementations, a process may be restricted from sending a signal to a process having a different security label. In order to prevent the existence or nonexistence of a process from being used as a covert channel, such processes should appear nonexistent to the sender; that is, [ESRCH] should be returned, rather than [EPERM], if [I68]pid[/I68] refers only to such processes.
[p_00037] Historical implementations varied on the result of a [I69]kill[/I69]() with [I70]pid[/I70] indicating a zombie process. Some indicated success on such a call (subject to permission checking), while others gave an error of [ESRCH]. Since the definition of process lifetime in this volume of POSIX.1-2024 covers zombie processes, the [ESRCH] error as described is inappropriate in this case and implementations that give this error do not conform. This means that an application cannot have a parent process check for termination of a particular child by sending it the null signal with [I71]kill[/I71](), but must instead use [A72][I73]waitpid[/I73]()[/A72] or [A74][I75]waitid[/I75]()[/A74].
[p_00038] There is some belief that the name [I76]kill[/I76]() is misleading, since the function is not always intended to cause process termination. However, the name is common to all historical implementations, and any change would be in conflict with the goal of minimal changes to existing application code.
