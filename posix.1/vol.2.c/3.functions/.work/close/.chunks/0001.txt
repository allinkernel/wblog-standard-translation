[h4_00001] [A1][/A1]NAME
[blockquote_00002] close, posix_close — close a file descriptor
[h4_00003] [A2][/A2]SYNOPSIS
[p_00004] [CODE3]
[h4_00005] [A4][/A4]DESCRIPTION
[p_00006] The [I5]close[/I5]() function shall deallocate the file descriptor indicated by [I6]fildes[/I6]. To deallocate means to make the file descriptor available for return by subsequent calls to [A7][I8]open[/I8]()[/A7] or other functions that allocate file descriptors. All process-owned file locks that the calling process owns on the file associated with the file descriptor shall be unlocked.
[p_00007] If [I9]close[/I9]() is interrupted by a signal that is to be caught, then it is unspecified whether it returns -1 with [I10]errno[/I10] set to [EINTR] and [I11]fildes[/I11] remaining open, or returns -1 with [I12]errno[/I12] set to [EINPROGRESS] and [I13]fildes[/I13] being closed, or returns 0 to indicate successful completion; except that if POSIX_CLOSE_RESTART is defined as 0, then the option of returning -1 with [I14]errno[/I14] set to [EINTR] and [I15]fildes[/I15] remaining open shall not occur. If [I16]close[/I16]() returns -1 with [I17]errno[/I17] set to [EINTR], it is unspecified whether [I18]fildes[/I18] can subsequently be passed to any function except [I19]close[/I19]() or [I20]posix_close[/I20]() without error. For all other error situations (except for [EBADF] where [I21]fildes[/I21] was invalid), [I22]fildes[/I22] shall be closed. If [I23]fildes[/I23] was closed even though the close operation is incomplete, the close operation shall continue asynchronously and the process shall have no further ability to track the completion or final status of the close operation.
[p_00008] When all file descriptors associated with a pipe or FIFO special file are closed, any data remaining in the pipe or FIFO shall be discarded.
[p_00009] When all file descriptors associated with an open file description have been closed, the open file description shall be freed.
[p_00010] If the link count of the file is 0, when all file descriptors associated with the file are closed, the space occupied by the file shall be freed and the file shall no longer be accessible.
[p_00011] [S24][[A25]XSI[/A25]][/S24] [IMG26] If [I27]fildes[/I27] refers to the manager side of a pseudo-terminal, and this is the last close, a SIGHUP signal shall be sent to the controlling process, if any, for which the subsidiary side of the pseudo-terminal is the controlling terminal. It is unspecified whether closing the manager side of the pseudo-terminal flushes all queued input and output. [IMG28]
[p_00012] When there is an outstanding cancelable asynchronous I/O operation against [I29]fildes[/I29] when [I30]close[/I30]() is called, that I/O operation may be canceled. An I/O operation that is not canceled completes as if the [I31]close[/I31]() operation had not yet occurred. All operations that are not canceled shall complete as if the [I32]close[/I32]() blocked until the operations completed. The [I33]close[/I33]() operation itself need not block awaiting such I/O completion. Whether any I/O operation is canceled, and which I/O operation may be canceled upon [I34]close[/I34](), is implementation-defined.
[p_00013] If a memory mapped file [S35][[A36]SHM[/A36]][/S35] [IMG37] &nbsp;or a shared memory object [IMG38] &nbsp;remains referenced at the last close (that is, a process has it mapped), then the entire contents of the memory object shall persist until the memory object becomes unreferenced. If this is the last close of a memory mapped file [S39][[A40]SHM[/A40]][/S39] [IMG41] &nbsp;or a shared memory object [IMG42] &nbsp;and the close results in the memory object becoming unreferenced, and the memory object has been unlinked, then the memory object shall be removed.
[p_00014] When all file descriptors associated with a socket have been closed, the socket shall be destroyed. If the socket is in connection-mode, and the SO_LINGER option is set for the socket with non-zero linger time, and the socket has untransmitted data, then [I43]close[/I43]() shall block for up to the current linger interval until all data is transmitted.
[p_00015] The [I44]posix_close[/I44]() function shall be equivalent to the [I45]close[/I45]() function, except with the modifications based on the [I46]flag[/I46] argument as described below. If [I47]flag[/I47] is 0, then [I48]posix_close[/I48]() shall not return -1 with [I49]errno[/I49] set to [EINTR], which implies that [I50]fildes[/I50] will always be closed (except for [EBADF], where [I51]fildes[/I51] was invalid). If [I52]flag[/I52] includes POSIX_CLOSE_RESTART and POSIX_CLOSE_RESTART is defined as a non-zero value, and [I53]posix_close[/I53]() is interrupted by a signal that is to be caught, then [I54]posix_close[/I54]() may return -1 with [I55]errno[/I55] set to [EINTR], in which case [I56]fildes[/I56] shall be left open; however, it is unspecified whether [I57]fildes[/I57] can subsequently be passed to any function except [I58]close[/I58]() or [I59]posix_close[/I59]() without error. If [I60]flag[/I60] is invalid, [I61]posix_close[/I61]() may fail with errno set to [EINVAL], but shall otherwise behave as if [I62]flag[/I62] had been 0 and close [I63]fildes[/I63].
[h4_00016] [A64][/A64]RETURN VALUE
[p_00017] Upon successful completion, 0 shall be returned; otherwise, -1 shall be returned and [I65]errno[/I65] set to indicate the error.
[h4_00018] [A66][/A66]ERRORS
[p_00019] The [I67]close[/I67]() and [I68]posix_close[/I68]() functions shall fail if:
[dt_00020] [EBADF]
[dd_00021] The [I69]fildes[/I69] argument is not a open file descriptor.
[dt_00022] [EINPROGRESS]
[dd_00023] The function was interrupted by a signal and [I70]fildes[/I70] was closed but the close operation is continuing asynchronously.
[p_00024] The [I71]close[/I71]() and [I72]posix_close[/I72]() functions may fail if:
[dt_00025] [EINTR]
[dd_00026] The function was interrupted by a signal, POSIX_CLOSE_RESTART is defined as non-zero, and (in the case of [I73]posix_close[/I73]()) the [I74]flag[/I74] argument included POSIX_CLOSE_RESTART, in which case [I75]fildes[/I75] is still open.
[dt_00027] [EIO]
[dd_00028] An I/O error occurred while reading from or writing to the file system.
[p_00029] The [I76]posix_close[/I76]() function may fail if:
[dt_00030] [EINVAL]
[dd_00031] The value of the [I77]flag[/I77] argument is invalid.
[p_00032] The [I78]close[/I78]() and [I79]posix_close[/I79]() functions shall not return an [EAGAIN] or [EWOULDBLOCK] error. If POSIX_CLOSE_RESTART is zero, the [I80]close[/I80]() function shall not return an [EINTR] error. The [I81]posix_close[/I81]() function shall not return an [EINTR] error unless [I82]flag[/I82] includes a non-zero POSIX_CLOSE_RESTART.

[h4_00039] [A87][/A87]APPLICATION USAGE
[p_00040] An application that had used the [I88]stdio[/I88] routine [A89][I90]fopen[/I90]()[/A89] to open a file should use the corresponding [A91][I92]fclose[/I92]()[/A91] routine rather than [I93]close[/I93](). Once a file is closed, the file descriptor no longer exists, since the integer corresponding to it no longer refers to a file.
[p_00041] Implementations may use file descriptors that must be inherited into child processes for the child process to remain conforming, such as for message catalog or tracing purposes. Therefore, an application that calls [I94]close[/I94]() on an arbitrary integer risks non-conforming behavior, and [I95]close[/I95]() can only portably be used on file descriptor values that the application has obtained through explicit actions, as well as the three file descriptors corresponding to the standard file streams. In multi-threaded parent applications, the practice of calling [I96]close[/I96]() in a loop after [A97][I98]fork[/I98]()[/A97] and before an [I99][A100]exec[/A100][/I99] call in order to avoid a race condition of leaking an unintended file descriptor into a child process, is therefore unsafe, and the race should instead be combatted by opening all file descriptors with the FD_CLOEXEC bit set unless the file descriptor is intended to be inherited across [I101][A102]exec[/A102][/I101].
[p_00042] Usage of [I103]close[/I103]() on file descriptors STDIN_FILENO, STDOUT_FILENO, or STDERR_FILENO should immediately be followed by an operation to reopen these file descriptors. Unexpected behavior will result if any of these file descriptors is left in a closed state (for example, an [EBADF] error from [A104][I105]perror[/I105]()[/A104]) or if an unrelated [A106][I107]open[/I107]()[/A106] or similar call later in the application accidentally allocates a file to one of these well-known file descriptors. Furthermore, a [I108]close[/I108]() followed by a reopen operation (e.g., [A109][I110]open[/I110]()[/A109], [A111][I112]dup[/I112]()[/A111], etc.) is not atomic; [A113][I114]dup2[/I114]()[/A113] should be used to change standard file descriptors.
[h4_00043] [A115][/A115]RATIONALE
[p_00044] The use of interruptible device close routines should be discouraged to avoid problems with the implicit closes of file descriptors, such as by [I116][A117]exec[/A117][/I116], process termination, or [A118][I119]dup2[/I119]()[/A118]. This volume of POSIX.1-2024 only intends to permit such behavior by specifying the [EINTR] error condition for [I120]close[/I120]() and [I121]posix_close[/I121]() with non-zero POSIX_CLOSE_RESTART, to allow applications a portable way to resume waiting for an event associated with the close operation (for example, a tape drive rewinding) after receiving an interrupt. This standard also permits implementations to define POSIX_CLOSE_RESTART to 0 if they do not choose to provide a way to restart an interrupted close action. Although the file descriptor is left open on [EINTR], it might no longer be usable; that is, passing it to any function except [I122]close[/I122]() or [I123]posix_close[/I123]() might result in an error such as [EIO]. If an application must guarantee that data will not be lost, it is recommended that the application use [A124][I125]fsync[/I125]()[/A124] or [A126][I127]fdatasync[/I127]()[/A126] prior to the close operation, rather than leaving the close operation to deal with pending I/O and risk an interrupt.
[p_00045] Earlier versions of this standard left the state of [I128]fildes[/I128] unspecified after errors such as [EINTR] and [EIO]; and implementations differed on whether [I129]close[/I129]() left [I130]fildes[/I130] open after [EINTR]. This was unsatisfactory once threads were introduced, since multi-threaded applications need to know whether [I131]fildes[/I131] has been closed. Applications cannot blindly call [I132]close[/I132]() again, because if [I133]fildes[/I133] was closed by the first call another thread could have been allocated a file descriptor with the same value as [I134]fildes[/I134], which must not be closed by the first thread. On the other hand, the alternative of never retrying [I135]close[/I135]() would lead to a file descriptor leak in implementations where [I136]close[/I136]() did not close [I137]fildes[/I137], although such a leak may be harmless if the process is about to exit or the file descriptor is marked FD_CLOEXEC and the process is about to be replaced by [I138][A139]exec[/A139][/I138]. This standard introduced [I140]posix_close[/I140]() with a [I141]flag[/I141] argument that allows a choice between the two possible error behaviors, and leaves it unspecified which of the two behaviors is implemented by [I142]close[/I142]() (although it is guaranteed to be one of the two behaviors of [I143]posix_close[/I143](), rather than leaving things completely unspecified as in earlier versions of the standard).
[p_00046] Note that the standard requires that [I144]close[/I144]() and [I145]posix_close[/I145]() must leave [I146]fildes[/I146] open after [EINTR] (in the cases where [EINTR] is permitted) and must close the file descriptor regardless of all other errors (except [EBADF], where [I147]fildes[/I147] is already invalid). In general, portable applications should only retry a [I148]close[/I148]() after checking for [EINTR] (and on implementations where POSIX_CLOSE_RESTART is defined to be zero, this retry loop will be dead code), and risk a file descriptor leak if a retry loop is not attempted. It should also be noted that [EINTR] is only possible if [I149]close[/I149]() can be interrupted; if no signal handlers are installed, then [I150]close[/I150]() will not be interrupted. Conversely, if a single-threaded application can guarantee that no file descriptors are opened or closed in signal handlers, then a retry loop without checking for [EINTR] will be harmless (since the retry will fail with [EBADF]), but guaranteeing that no external libraries introduce the use of threading can be difficult. There are additional guarantees for applications which will only ever be used on systems where POSIX_CLOSE_RESTART is defined as 0. These observations should help in determining whether an application needs to have its [I151]close[/I151]() calls audited for replacement with [I152]posix_close[/I152]().
[p_00047] It should also be noted that the requirement for [I153]posix_close[/I153]() with a [I154]flag[/I154] of 0 to always close [I155]fildes[/I155], even if an error is reported, is similar to the requirements on [A156][I157]fclose[/I157]()[/A156] to always release the stream, even if an error is encountered while flushing data.
[p_00048] Implementations that previously always closed [I158]fildes[/I158] can meet the new requirements by translating [EINTR] to [EINPROGRESS] in [I159]close[/I159](); and may define POSIX_CLOSE_RESTART to 0 rather than having to add restart semantics. On the other hand, implementations that previously left [I160]fildes[/I160] open on [EINTR] can map that to [I161]posix_close[/I161]() with POSIX_CLOSE_RESTART, and must add the semantics of [I162]posix_close[/I162]() when [I163]flag[/I163] is 0; one possibility is by calling the original [I164]close[/I164]() implementation, checking for failure, and on [EINTR], using actions similar to [A165][I166]dup2[/I166]()[/A165] to replace the incomplete close operation with another file descriptor that can be closed immediately by another call to the original [I167]close[/I167](), all before returning to the application. Either way, [I168]close[/I168]() should always map to one of the two behaviors of [I169]posix_close[/I169](), and implementations are encouraged to keep the behavior of [I170]close[/I170]() unchanged so as not to break implementation-specific expectations of older applications that were relying on behavior not specified by older versions of this standard.
[p_00049] The standard developers considered introducing a thread-local variable that [I171]close[/I171]() would set to indicate whether it had closed [I172]fildes[/I172] when returning -1. However, this was rejected in favor of the simpler solution of tightening [I173]close[/I173]() to guarantee that [I174]fildes[/I174] is closed except for [EINTR], and exposing a choice of whether to expect [EINTR] by adding [I175]posix_close[/I175](). Additionally, while the name [I176]posix_close[/I176]() is new to this standard, it is reminiscent of at least one implementation that introduced an alternate system call named [I177]close_nocancel[/I177]() in order to allow an application to choose whether restart semantics were desired.
[p_00050] Another consideration was whether implementations might return [EAGAIN] as an extension and whether [I178]close[/I178]() should be required to leave the file descriptor open in this case, since [EAGAIN] normally implies an operation should be retried. It seemed very unlikely that any implementation would have a legitimate reason to return [EAGAIN] or [EWOULDBLOCK], and therefore this requirement would mean applications have to include code for an error case that will never be used. Therefore [I179]close[/I179]() is now forbidden from returning [EAGAIN] and [EWOULDBLOCK] errors.
[p_00051] Note that the requirement for [I180]close[/I180]() on a socket to block for up to the current linger interval is not conditional on the O_NONBLOCK setting.
[p_00052] The standard developers rejected a proposal to add [I181]closefrom[/I181]() to the standard. Because the standard permits implementations to use inherited file descriptors as a means of providing a conforming environment for the child process, it is not possible to standardize an interface that closes arbitrary file descriptors above a certain value while still guaranteeing a conforming environment.
