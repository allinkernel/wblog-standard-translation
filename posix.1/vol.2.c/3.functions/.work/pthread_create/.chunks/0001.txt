[h4_00001] [A1][/A1]NAME
[blockquote_00002] pthread_create — thread creation
[h4_00003] [A2][/A2]SYNOPSIS
[p_00004] [CODE3]
[h4_00005] [A4][/A4]DESCRIPTION
[p_00006] The [I5]pthread_create[/I5]() function shall create a new thread, with attributes specified by [I6]attr[/I6], within a process. If [I7]attr[/I7] is NULL, the default attributes shall be used. If the attributes specified by [I8]attr[/I8] are modified later, the thread's attributes shall not be affected. Upon successful completion, [I9]pthread_create[/I9]() shall store the ID of the created thread in the location referenced by [I10]thread[/I10].
[p_00007] The thread is created executing [I11]start_routine[/I11] with [I12]arg[/I12] as its sole argument. If the [I13]start_routine[/I13] returns, the effect shall be as if there was an implicit call to [A14][I15]pthread_exit[/I15]()[/A14] using the return value of [I16]start_routine[/I16] as the exit status. Note that the thread in which [I17]main[/I17]() was originally invoked differs from this. When it returns from [I18]main[/I18](), the effect shall be as if there was an implicit call to [A19][I20]exit[/I20]()[/A19] using the return value of [I21]main[/I21]() as the exit status.
[p_00008] The signal state of the new thread shall be initialized as follows:
[p_00009] The signal mask shall be inherited from the creating thread.
[p_00010] The set of signals pending for the new thread shall be empty.
[p_00011] The thread-local current locale [S22][[A23]XSI[/A23]][/S22] [IMG24] &nbsp;and the alternate stack [IMG25] &nbsp;shall not be inherited.
[p_00012] The floating-point environment shall be inherited from the creating thread.
[p_00013] If [I26]pthread_create[/I26]() fails, no new thread is created and the contents of the location referenced by [I27]thread[/I27] are undefined.
[p_00014] [S28][[A29]TCT[/A29]][/S28] [IMG30] If _POSIX_THREAD_CPUTIME is defined, the new thread shall have a CPU-time clock accessible, and the initial value of this clock shall be set to zero. [IMG31]
[p_00015] The behavior is undefined if the value specified by the [I32]attr[/I32] argument to [I33]pthread_create[/I33]() does not refer to an initialized thread attributes object.
[h4_00016] [A34][/A34]RETURN VALUE
[p_00017] If successful, the [I35]pthread_create[/I35]() function shall return zero; otherwise, an error number shall be returned to indicate the error.
[h4_00018] [A36][/A36]ERRORS
[p_00019] The [I37]pthread_create[/I37]() function shall fail if:
[dt_00020] [EAGAIN]
[dd_00021] The system lacked the necessary resources to create another thread, or the system-imposed limit on the total number of threads in a process {PTHREAD_THREADS_MAX} would be exceeded.
[dt_00022] [EPERM]
[dd_00023] The caller does not have appropriate privileges to set the required scheduling parameters or scheduling policy.
[p_00024] The [I38]pthread_create[/I38]() function shall not return an error code of [EINTR].
[h4_00025] [A39][/A39]EXAMPLES
[p_00026] None.
[h4_00027] [A40][/A40]APPLICATION USAGE
[p_00028] There is no requirement on the implementation that the ID of the created thread be available before the newly created thread starts executing. The calling thread can obtain the ID of the created thread through the [I41]thread[/I41] argument of the [I42]pthread_create[/I42]() function, and the newly created thread can obtain its ID by a call to [A43][I44]pthread_self[/I44]()[/A43].
[h4_00029] [A45][/A45]RATIONALE
[p_00030] A suggested alternative to [I46]pthread_create[/I46]() would be to define two separate operations: create and start. Some applications would find such behavior more natural. Ada, in particular, separates the &quot;creation&quot; of a task from its &quot;activation&quot;.
[p_00031] Splitting the operation was rejected by the standard developers for many reasons:
[p_00032] The number of calls required to start a thread would increase from one to two and thus place an additional burden on applications that do not require the additional synchronization. The second call, however, could be avoided by the additional complication of a start-up state attribute.
[p_00033] An extra state would be introduced: &quot;created but not started&quot;. This would require the standard to specify the behavior of the thread operations when the target has not yet started executing.
[p_00034] For those applications that require such behavior, it is possible to simulate the two separate steps with the facilities that are currently provided. The [I47]start_routine[/I47]() can synchronize by waiting on a condition variable that is signaled by the start operation.
[p_00035] An Ada implementor can choose to create the thread at either of two points in the Ada program: when the task object is created, or when the task is activated (generally at a &quot;begin&quot;). If the first approach is adopted, the [I48]start_routine[/I48]() needs to wait on a condition variable to receive the order to begin &quot;activation&quot;. The second approach requires no such condition variable or extra synchronization. In either approach, a separate Ada task control block would need to be created when the task object is created to hold rendezvous queues, and so on.
[p_00036] An extension of the preceding model would be to allow the state of the thread to be modified between the create and start. This would allow the thread attributes object to be eliminated. This has been rejected because:
[p_00037] All state in the thread attributes object has to be able to be set for the thread. This would require the definition of functions to modify thread attributes. There would be no reduction in the number of function calls required to set up the thread. In fact, for an application that creates all threads using identical attributes, the number of function calls required to set up the threads would be dramatically increased. Use of a thread attributes object permits the application to make one set of attribute setting function calls. Otherwise, the set of attribute setting function calls needs to be made for each thread creation.
[p_00038] Depending on the implementation architecture, functions to set thread state would require kernel calls, or for other implementation reasons would not be able to be implemented as macros, thereby increasing the cost of thread creation.
[p_00039] The ability for applications to segregate threads by class would be lost.
[p_00040] Another suggested alternative uses a model similar to that for process creation, such as &quot;thread fork&quot;. The fork semantics would provide more flexibility and the &quot;create&quot; function can be implemented simply by doing a thread fork followed immediately by a call to the desired &quot;start routine&quot; for the thread. This alternative has these problems:
[p_00041] For many implementations, the entire stack of the calling thread would need to be duplicated, since in many architectures there is no way to determine the size of the calling frame.
[p_00042] Efficiency is reduced since at least some part of the stack has to be copied, even though in most cases the thread never needs the copied context, since it merely calls the desired start routine.
[p_00043] If an implementation detects that the value specified by the [I49]attr[/I49] argument to [I50]pthread_create[/I50]() does not refer to an initialized thread attributes object, it is recommended that the function should fail and report an [EINVAL] error.

[p_00055] The thread CPU-time clock semantics are added for alignment with IEEE&nbsp;Std&nbsp;1003.1d-1999.
[p_00056] The [B66]restrict[/B66] keyword is added to the [I67]pthread_create[/I67]() prototype for alignment with the ISO/IEC&nbsp;9899:1999 standard.
[p_00057] The DESCRIPTION is updated to make it explicit that the floating-point environment is inherited from the creating thread.
[p_00058] IEEE&nbsp;Std&nbsp;1003.1-2001/Cor&nbsp;1-2002, item XSH/TC1/D6/44 is applied, adding text that the alternate stack is not inherited.
[p_00059] IEEE&nbsp;Std&nbsp;1003.1-2001/Cor&nbsp;2-2004, item XSH/TC2/D6/93 is applied, updating the ERRORS section to remove the mandatory [EINVAL] error (&quot;The value specified by [I68]attr[/I68] is invalid&quot;), and adding the optional [EINVAL] error (&quot;The attributes specified by [I69]attr[/I69] are invalid&quot;).
[p_00060] IEEE&nbsp;Std&nbsp;1003.1-2001/Cor&nbsp;2-2004, item XSH/TC2/D6/94 is applied, adding the APPLICATION USAGE section.
