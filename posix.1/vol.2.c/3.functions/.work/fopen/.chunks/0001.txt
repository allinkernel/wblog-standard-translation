[blockquote_00002] fopen — open a stream
[h4_00003] [A2][/A2]SYNOPSIS

[h4_00005] [A4][/A4]DESCRIPTION
[p_00006] The [I5]fopen[/I5]() function shall open the file whose pathname is the string pointed to by [I6]pathname[/I6], and associates a stream with it.
[p_00007] The [I7]mode[/I7] argument points to a character string. The behavior is unspecified if any character occurs more than once in the string. If the string begins with one of the following characters, then the file shall be opened in the indicated mode. Otherwise, the behavior is undefined.
[dt_00008] [CODE8]
[dd_00009] Open file for reading.
[dt_00010] [CODE9]
[dd_00011] Truncate to zero length or create file for writing.
[dt_00012] [CODE10]
[dd_00013] Append; open or create file for writing at end-of-file.
[p_00014] The remainder of the string can contain any of the following characters, [S11][[A12]CX[/A12]][/S11] [IMG13] &nbsp;in any order, [IMG14] and further affect how the file is opened:
[dt_00015] [CODE15]
[dd_00016] [S16][[A17]CX[/A17]][/S16] [IMG18] This character shall have no effect, but is allowed for ISO&nbsp;C standard conformance. [IMG19]
[dt_00017] [CODE20]
[dd_00018] [S21][[A22]CX[/A22]][/S21] [IMG23] The underlying file descriptor shall have the FD_CLOEXEC flag atomically set. [IMG24]
[dt_00019] [CODE25]
[dd_00020] If the first character of [I26]mode[/I26] is [CODE27] [S28][[A29]CX[/A29]][/S28] [IMG30] &nbsp;or [CODE31], [IMG32] then the function shall fail if the file already exists, or cannot be created; if the file does not exist and can be created, it shall be created with [S33][[A34]CX[/A34]][/S33] [IMG35] &nbsp;an implementation-defined form of [IMG36] &nbsp;exclusive (also known as non-shared) access,  [S37][[A38]CX[/A38]][/S37] [IMG39] if supported by the underlying file system, provided the resulting file permissions are the same as they would be without the [CODE40] modifier. If the first character of mode is [CODE41], the effect is implementation-defined. [IMG42]   [B43]Note:[/B43] The ISO&nbsp;C standard requires exclusive access &quot;to the extent that the underlying file system supports exclusive access&quot;, but does not define what it means by this. Taken at face value—that systems must do whatever they are capable of, at the file system level, in order to exclude access by others—this would require POSIX.1 systems to set the file permissions in a way that prevents access by other users and groups. Consequently, this volume of POSIX.1-2024 does not defer to the ISO&nbsp;C standard as regards the &quot;exclusive access&quot; requirement.
[dt_00021] [CODE44]
[dd_00022] The file shall be opened for update (both reading and writing), rather than just reading or just writing.
[p_00023] Opening a file with read mode ([CODE45] as the first character in the [I46]mode[/I46] argument) shall fail if the file does not exist or cannot be read.
[p_00024] Opening a file with append mode ([CODE47] as the first character in the [I48]mode[/I48] argument) shall cause all subsequent writes to the file to be forced to the then current end-of-file, regardless of intervening calls to [A49][I50]fseek[/I50]()[/A49].
[p_00025] When a file is opened with update mode ([CODE51] in the [I52]mode[/I52] argument), both input and output can be performed on the associated stream. However, the application shall ensure that output is not directly followed by input without an intervening call to [A53][I54]fflush[/I54]()[/A53] or to a file positioning function ([A55][I56]fseek[/I56]()[/A55], [A57][I58]fsetpos[/I58]()[/A57], or [A59][I60]rewind[/I60]()[/A59]), and input is not directly followed by output without an intervening call to a file positioning function, unless the input operation encounters end-of-file.
[p_00026] When opened, a stream is fully buffered if and only if it can be determined not to refer to an interactive device. The error and end-of-file indicators for the stream shall be cleared.

[h4_00105] [A239][/A239]EXAMPLES
[h5_00106] [A240][/A240]Opening a File
[p_00107] The following example tries to open the file named [B241]file[/B241] for reading. The [I242]fopen[/I242]() function returns a file pointer that is used in subsequent [A243][I244]fgets[/I244]()[/A243] and [A245][I246]fclose[/I246]()[/A245] calls. If the program cannot open the file, it just ignores it.
[h4_00108] [A247][/A247]APPLICATION USAGE
[p_00109] If an application needs to create a file in a way that fails if the file already exists, and either requires that it does not have exclusive access to the file or does not need exclusive access, it should use [A248][I249]open[/I249]()[/A248] with the O_CREAT and O_EXCL flags instead of using [I250]fopen[/I250]() with an [CODE251] in the mode. A stream can then be created, if needed, by calling [A252][I253]fdopen[/I253]()[/A252] on the file descriptor returned by [A254][I255]open[/I255]()[/A254].
[h4_00110] [A256][/A256]RATIONALE
[p_00111] The [CODE257] mode character is provided as a convenience to avoid a data race in multi-threaded applications. Without it, a file descriptor is leaked into a child process created by one thread in the window between another thread creating a file descriptor with [I258]fopen[/I258]() and then using [A259][I260]fileno[/I260]()[/A259] and [A261][I262]fcntl[/I262]()[/A261] to set the FD_CLOEXEC flag. It is also possible to avoid the race by using [A263][I264]open[/I264]()[/A263] with O_CLOEXEC followed by [A265][I266]fdopen[/I266]()[/A265], however, there is no safe alternative for the [A267][I268]freopen[/I268]()[/A267] function, and consistency dictates that the [CODE269] modifier should be standardized for all functions that accept [I270]mode[/I270] strings.
[p_00112] The ISO&nbsp;C standard only recognizes the [CODE271], [CODE272], and [CODE273] characters in certain positions of the [I274]mode[/I274] string, leaving other arrangements as unspecified, and only permits [CODE275] in [I276]mode[/I276] strings beginning with [CODE277]. This standard specifically requires support for all characters other than the first in the [I278]mode[/I278] string to be recognized in any order. Thus, [CODE279] and [CODE280] behave the same, and while [CODE281] is unspecified in the ISO&nbsp;C standard, this standard requires it to have the same behavior as [CODE282]. This standard also requires that [CODE283] work for [I284]mode[/I284] strings beginning with [CODE285], as well as having implementation-defined behavior for [I286]mode[/I286] strings beginning with [CODE287]. Therefore, while [A288][I289]open[/I289]()[/A288] has undefined behavior if O_EXCL is specified without O_CREAT, the same is not true of [I290]fopen[/I290]().
[p_00113] When [CODE291] is in mode, the ISO&nbsp;C standard requires that the file is created with exclusive access to the extent that the underlying system supports exclusive access. Although POSIX.1 does not specify any method of enabling exclusive access, it allows for the existence of an implementation-specific flag, or flags, that enable it. Note that they should be file creation flags if a file is being created, not file access mode flags (that is, ones that are included in O_ACCMODE) or file status flags, so that they do not affect the value returned by [A292][I293]fcntl[/I293]()[/A292] with F_GETFL. On implementations that have such flags, if support for them is file system dependent and exclusive access is requested when using [I294]fopen[/I294]() to create a file on a file system that does not support it, the flags must not be used if they would cause [I295]fopen[/I295]() to fail.
[p_00114] Some implementations support mandatory file locking as a means of enabling exclusive access to a file. Locks are set in the normal way, but instead of only preventing others from setting conflicting locks they prevent others from accessing the contents of the locked part of the file in a way that conflicts with the lock. However, unless the implementation has a way of setting a whole-file write lock on file creation, this does not satisfy the requirement in the ISO&nbsp;C standard that the file is &quot;created with exclusive access to the extent that the underlying system supports exclusive access&quot;. (Having [I296]fopen[/I296]() create the file and set a lock on the file as two separate operations is not the same, and it would introduce a race condition whereby another process could open the file and write to it (or set a lock) in between the two operations.) However, on all implementations that support mandatory file locking, its use is discouraged; therefore, it is recommended that implementations which support mandatory file locking do not add a means of creating a file with a whole-file exclusive lock set, so that [I297]fopen[/I297]() is not required to enable mandatory file locking in order to conform to the ISO&nbsp;C standard. An implementation that has a means of creating a file with a whole-file exclusive lock set would need to provide a way to change the behavior of [I298]fopen[/I298]() depending on whether the calling process is executing in a POSIX.1 conforming environment or an ISO C conforming environment.
[p_00115] The typical implementation-defined behavior for mode [CODE299] is to ignore the [CODE300], but the standard developers did not wish to mandate this behavior. For example, an implementation could allow shared access for reading; that is, disallow a file that has been opened this way from also being opened for writing.
[p_00116] Implementations are encouraged to have [I301]fopen[/I301]() and [A302][I303]freopen[/I303]()[/A302] report an [EILSEQ] error if [I304]mode[/I304] begins with [CODE305] or [CODE306], the file did not previously exist, and the last component of [I307]pathname[/I307] contains any bytes that have the encoded value of a &lt;newline&gt; character.
