[h4_00005] [A4][/A4]DESCRIPTION
[p_00006] If [I5]command[/I5] is a null pointer, the [I6]system[/I6]() function shall determine whether the host environment has a command processor. If [I7]command[/I7] is not a null pointer, the [I8]system[/I8]() function shall pass the string pointed to by [I9]command[/I9] to that command processor to be executed in an implementation-defined manner; this might then cause the program calling [I10]system[/I10]() to behave in a non-conforming manner or to terminate.
[p_00007] [S11][[A12]CX[/A12]][/S11] [IMG13] The [I14]system[/I14]() function shall behave as if a child process were created using [A15][I16]fork[/I16]()[/A15], and the child process invoked the [A17][I18]sh[/I18][/A17] utility using [A19][I20]execl[/I20]()[/A19] as follows:
[p_00008] where &lt;[I21]shell path[/I21]&gt; is an unspecified pathname for the [A22][I23]sh[/I23][/A22] utility. It is implementation-defined whether the handlers registered with [A24][I25]pthread_atfork[/I25]()[/A24] are called as part of the creation of the child process.
[p_00009] The [I26]system[/I26]() function shall ignore the SIGINT and SIGQUIT signals, and shall block the SIGCHLD signal, while waiting for the command to terminate. If this might cause the application to miss a signal that would have killed it, then the application should examine the return value from [I27]system[/I27]() and take whatever action is appropriate to the application if the command terminated due to receipt of a signal.
[p_00010] The [I28]system[/I28]() function shall not affect the termination status of any child of the calling processes other than the process or processes it itself creates.
[p_00011] The [I29]system[/I29]() function shall not return until the child process has terminated.
[p_00012] If concurrent calls to [I30]system[/I30]() are made from multiple threads, it is unspecified whether:
[p_00013] each call saves and restores the dispositions of the SIGINT and SIGQUIT signals independently, or
[p_00014] in a set of concurrent calls the dispositions in effect after the last call returns are those that were in effect on entry to the first call.
[p_00015] If a thread is cancelled while it is in a call to [I31]system[/I31](), it is unspecified whether the child process is terminated and waited for, or is left running. [IMG32]
[h4_00016] [A33][/A33]RETURN VALUE
[p_00017] If [I34]command[/I34] is a null pointer, [I35]system[/I35]() shall return non-zero to indicate that a command processor is available, or zero if none is available. [S36][[A37]CX[/A37]][/S36] [IMG38] The [I39]system[/I39]() function shall always return non-zero when [I40]command[/I40] is NULL. [IMG41]
[p_00018] [S42][[A43]CX[/A43]][/S42] [IMG44] If [I45]command[/I45] is not a null pointer, [I46]system[/I46]() shall return the termination status of the command language interpreter in the format specified by [A47][I48]waitpid[/I48]()[/A47]. The termination status shall be as defined for the [A49][I50]sh[/I50][/A49] utility; otherwise, the termination status is unspecified. If some error prevents the command language interpreter from executing after the child process is created, the return value from [I51]system[/I51]() shall be as if the command language interpreter had terminated using [I52]exit[/I52](127) or [I53]_exit[/I53](127). If a child process cannot be created, or if the termination status for the command language interpreter cannot be obtained, [I54]system[/I54]() shall return -1 and set [I55]errno[/I55] to indicate the error. [IMG56]

[h4_00026] [A73][/A73]APPLICATION USAGE
[p_00027] If the return value of [I74]system[/I74]() is not -1, its value can be decoded through the use of the macros described in [A75][I76]&lt;sys/wait.h&gt;[/I76][/A75]. For convenience, these macros are also provided in [A77][I78]&lt;stdlib.h&gt;[/I78][/A77].
[p_00028] Note that, while [I79]system[/I79]() must ignore SIGINT and SIGQUIT and block SIGCHLD while waiting for the child to terminate, the handling of signals in the executed command is as specified by [A80][I81]fork[/I81]()[/A80] and [I82][A83]exec[/A83][/I82]. For example, if SIGINT is being caught or is set to SIG_DFL when [I84]system[/I84]() is called, then the child is started with SIGINT handling set to SIG_DFL.
[p_00029] Ignoring SIGINT and SIGQUIT in the parent process prevents coordination problems (two processes reading from the same terminal, for example) when the executed command ignores or catches one of the signals. It is also usually the correct action when the user has given a command to the application to be executed synchronously (as in the [CODE85] command in many interactive applications). In either case, the signal should be delivered only to the child process, not to the application itself. There is one situation where ignoring the signals might have less than the desired effect. This is when the application uses [I86]system[/I86]() to perform some task invisible to the user. If the user typed the interrupt character ([CODE87], for example) while [I88]system[/I88]() is being used in this way, one would expect the application to be killed, but only the executed command is killed. Applications that use [I89]system[/I89]() in this way should carefully check the return status from [I90]system[/I90]() to see if the executed command was successful, and should take appropriate action when the command fails.
[p_00030] Blocking SIGCHLD while waiting for the child to terminate prevents the application from catching the signal and obtaining status from [I91]system[/I91]()'s child process before [I92]system[/I92]() can get the status itself.
[p_00031] The context in which the utility is ultimately executed may differ from that in which [I93]system[/I93]() was called. For example, file descriptors that have the FD_CLOEXEC or FD_CLOFORK flag set are closed, and the process ID and parent process ID are different. Also, if the executed utility changes its environment variables or its current working directory, that change is not reflected in the caller's context.
[p_00032] There is no defined way for an application to find the specific path for the shell. However, [A94][I95]confstr[/I95]()[/A94] can provide a value for [I96]PATH[/I96] that is guaranteed to find the [A97][I98]sh[/I98][/A97] utility.
[p_00033] Although [I99]system[/I99]() is required to be thread-safe, it is recommended that concurrent calls from multiple threads are avoided, since [I100]system[/I100]() is not required to coordinate the saving and restoring of the dispositions of the SIGINT and SIGQUIT signals across a set of overlapping calls, and therefore the signals might end up being set to ignored after the last call returns. Applications should also avoid cancelling a thread while it is in a call to [I101]system[/I101]() as the child process may be left running in that event. In addition, if another thread alters the disposition of the SIGCHLD signal, a call to [A102][I103]signal[/I103]()[/A102] may produce unexpected results.
[h4_00034] [A104][/A104]RATIONALE
[p_00035] The [I105]system[/I105]() function should not be used by programs that have set user (or group) ID privileges. The [A106][I107]fork[/I107]()[/A106] and [I108][A109]exec[/A109][/I108] family of functions (except [A110][I111]execlp[/I111]()[/A110] and [A112][I113]execvp[/I113]()[/A112]), should be used instead. This prevents any unforeseen manipulation of the environment of the user that could cause execution of commands not anticipated by the calling program.
[p_00036] There are three levels of specification for the [I114]system[/I114]() function. The ISO&nbsp;C standard gives the most basic. It requires that the function exists, and defines a way for an application to query whether a command language interpreter exists. It says nothing about the command language or the environment in which the command is interpreted.
[p_00037] POSIX.1-2024 places additional restrictions on [I115]system[/I115](). It requires that if there is a command language interpreter, the environment must be as specified by [A116][I117]fork[/I117]()[/A116] and [I118][A119]exec[/A119][/I118]. This ensures, for example, that close-on-[I120]exec[/I120] works, that process-owned file locks are not inherited, and that the process ID is different. It also specifies the return value from [I121]system[/I121]() when the command line can be run, thus giving the application some information about the command's completion status.
[p_00038] Finally, POSIX.1-2024 requires the command to be interpreted as in the shell command language defined in the Shell and Utilities volume of POSIX.1-2024.
[p_00039] Note that, [I122]system[/I122](NULL) is required to return non-zero, indicating that there is a command language interpreter. At first glance, this would seem to conflict with the ISO&nbsp;C standard which allows [I123]system[/I123](NULL) to return zero. There is no conflict, however. A system must have a command language interpreter, and is non-conforming if none is present. It is therefore permissible for the [I124]system[/I124]() function on such a system to implement the behavior specified by the ISO&nbsp;C standard as long as it is understood that the implementation does not conform to POSIX.1-2024 if [I125]system[/I125](NULL) returns zero.
[p_00040] It was explicitly decided that when [I126]command[/I126] is NULL, [I127]system[/I127]() should not be required to check to make sure that the command language interpreter actually exists with the correct mode, that there are enough processes to execute it, and so on. The call [I128]system[/I128](NULL) could, theoretically, check for such problems as too many existing child processes, and return zero. However, it would be inappropriate to return zero due to such a (presumably) transient condition. If some condition exists that is not under the control of this application and that would cause any [I129]system[/I129]() call to fail, that system has been rendered non-conforming.
[p_00041] Early drafts required, or allowed, [I130]system[/I130]() to return with [I131]errno[/I131] set to [EINTR] if it was interrupted with a signal. This error return was removed, and a requirement that [I132]system[/I132]() not return until the child has terminated was added. This means that if a [A133][I134]waitpid[/I134]()[/A133] call in [I135]system[/I135]() exits with [I136]errno[/I136] set to [EINTR], [I137]system[/I137]() must reissue the [A138][I139]waitpid[/I139]()[/A138]. This change was made for two reasons:
[p_00042] There is no way for an application to clean up if [I140]system[/I140]() returns [EINTR], short of calling [A141][I142]wait[/I142]()[/A141], and that could have the undesirable effect of returning the status of children other than the one started by [I143]system[/I143]().
[p_00043] While it might require a change in some historical implementations, those implementations already have to be changed because they use [A144][I145]wait[/I145]()[/A144] instead of [A146][I147]waitpid[/I147]()[/A146].
[p_00044] Note that if the application is catching SIGCHLD signals, it will receive such a signal before a successful [I148]system[/I148]() call returns.
[p_00045] To conform to POSIX.1-2024, [I149]system[/I149]() must use [A150][I151]waitpid[/I151]()[/A150], or some similar function, instead of [A152][I153]wait[/I153]()[/A152].

[p_00048] Earlier versions of this standard did not require [I156]system[/I156]() to be thread-safe because it alters the process-wide disposition of the SIGINT and SIGQUIT signals. It is now required to be thread-safe to align with the ISO&nbsp;C standard, which (since the introduction of threads in 2011) requires that it avoids data races. However, the function is not required to coordinate the saving and restoring of the dispositions of the SIGINT and SIGQUIT signals across a set of overlapping calls, and the above example does not do so. The example also does not terminate and wait for the child process if the calling thread is cancelled, and so would leak a process ID in that event.
[p_00049] One reviewer suggested that an implementation of [I157]system[/I157]() might want to use an environment variable such as [I158]SHELL[/I158] to determine which command interpreter to use. The supposed implementation would use the default command interpreter if the one specified by the environment variable was not available. This would allow a user, when using an application that prompts for command lines to be processed using [I159]system[/I159](), to specify a different command interpreter. Such an implementation is discouraged. If the alternate command interpreter did not follow the command line syntax specified in the Shell and Utilities volume of POSIX.1-2024, then changing [I160]SHELL[/I160] would render [I161]system[/I161]() non-conforming. This would affect applications that expected the specified behavior from [I162]system[/I162](), and since the Shell and Utilities volume of POSIX.1-2024 does not mention that [I163]SHELL[/I163] affects [I164]system[/I164](), the application would not know that it needed to unset [I165]SHELL .[/I165]
[p_00050] Earlier versions of this standard required the [I166]command[/I166] string to be passed as the next argument after [CODE167] (omitting [CODE168]). This meant that portable applications needed to take care not to pass a command string beginning with &lt;hyphen-minus&gt; ([CODE169]) or &lt;plus-sign&gt; ([CODE170]), as it would then be interpreted as containing options. Now that implementations are required to pass the [CODE171], applications no longer need to do this.
