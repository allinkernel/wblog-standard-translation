[p_00153] In the last line of the example, after processing three characters, nine bytes have been output. The fourth character must then be examined to determine whether it converts to one byte or more. If it converts to more than one byte, the output is only nine bytes. Since there is no fourth character in the array, the behavior is undefined.
[h4_00154] [A578][/A578]APPLICATION USAGE
[p_00155] If the application calling [I579]fprintf[/I579]() has any objects of type [B580]wint_t[/B580] or [B581]wchar_t[/B581], it must also include the [A582][I583]&lt;wchar.h&gt;[/I583][/A582] header to have these objects defined.
[p_00156] The space allocated by a successful call to [I584]asprintf[/I584]() should be subsequently freed by a call to [A585][I586]free[/I586]()[/A585].
[h4_00157] [A587][/A587]RATIONALE
[p_00158] If an implementation detects that there are insufficient arguments for the format, it is recommended that the function should fail and report an [EINVAL] error.
[p_00159] The behavior specified for the [CODE588] conversion differs slightly from the specification in the ISO&nbsp;C standard, in that printing the null wide character produces a null byte instead of 0 bytes of output as would be required by a strict reading of the ISO&nbsp;C standard's direction to behave as if applying the [CODE589] specifier to a [B590]wchar_t[/B590] array whose first element is the null wide character. Requiring a multi-byte output for every possible wide character, including the null character, matches historical practice, and provides consistency with [CODE591] in [I592]fprintf[/I592]() and with both [CODE593] and [CODE594] in [A595][I596]fwprintf[/I596]()[/A595]. It is anticipated that a future edition of the ISO&nbsp;C standard will change to match the behavior specified here.
