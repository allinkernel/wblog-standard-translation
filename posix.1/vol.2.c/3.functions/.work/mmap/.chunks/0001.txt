[h4_00001] [A1][/A1]NAME
[blockquote_00002] mmap — map pages of memory
[h4_00003] [A2][/A2]SYNOPSIS
[p_00004] [CODE3]
[h4_00005] [A4][/A4]DESCRIPTION
[p_00006] The [I5]mmap[/I5]() function shall establish a mapping between an address space of a process and a memory object.
[p_00007] The [I6]mmap[/I6]() function shall be supported for the following memory objects:
[p_00008] Regular files
[p_00009] Anonymous memory objects
[p_00010] [S7][[A8]SHM[/A8]][/S7] [IMG9] Shared memory objects [IMG10]
[p_00011] [S11][[A12]TYM[/A12]][/S11] [IMG13] Typed memory objects [IMG14]
[p_00012] Support for any other type of file is unspecified.
[p_00013] The format of the call is as follows:
[p_00014] The [I15]mmap[/I15]() function shall establish a mapping between the address space of the process at an address [I16]pa[/I16] for [I17]len[/I17] bytes to the memory object represented by the file descriptor [I18]fildes[/I18] at offset [I19]off[/I19] for [I20]len[/I20] bytes, or to an anonymous memory object of [I21]len[/I21] bytes. The value of [I22]pa[/I22] is an implementation-defined function of the parameter [I23]addr[/I23] and the values of [I24]flags[/I24], further described below. A successful [I25]mmap[/I25]() call shall return [I26]pa[/I26] as its result. The address range starting at [I27]pa[/I27] and continuing for [I28]len[/I28] bytes shall be legitimate for the possible (not necessarily current) address space of the process. The range of bytes starting at [I29]off[/I29] and continuing for [I30]len[/I30] bytes shall be legitimate for the possible (not necessarily current) offsets in the memory object represented by [I31]fildes[/I31].
[p_00015] [S32][[A33]TYM[/A33]][/S32] [IMG34] If [I35]fildes[/I35] represents a typed memory object opened with either the POSIX_TYPED_MEM_ALLOCATE flag or the POSIX_TYPED_MEM_ALLOCATE_CONTIG flag, the memory object to be mapped shall be that portion of the typed memory object allocated by the implementation as specified below. In this case, if [I36]off[/I36] is non-zero, the behavior of [I37]mmap[/I37]() is undefined. If [I38]fildes[/I38] refers to a valid typed memory object that is not accessible from the calling process, [I39]mmap[/I39]() shall fail. [IMG40]
[p_00016] The mapping established by [I41]mmap[/I41]() shall replace any previous mappings for those whole pages containing any part of the address space of the process starting at [I42]pa[/I42] and continuing for [I43]len[/I43] bytes.
[p_00017] If the size of the mapped file changes after the call to [I44]mmap[/I44]() as a result of some other operation on the mapped file, the effect of references to portions of the mapped region that correspond to added or removed portions of the file is unspecified.
[p_00018] If [I45]len[/I45] is zero, [I46]mmap[/I46]() shall fail and no mapping shall be established.
[p_00019] The parameter [I47]prot[/I47] determines whether read, write, execute, or some combination of accesses are permitted to the data being mapped. The [I48]prot[/I48] shall be either PROT_NONE or the bitwise-inclusive OR of one or more of the other flags in the following table, defined in the [A49][I50]&lt;sys/mman.h&gt;[/I50][/A49] header.
[td_00020] ctx="行 1: PROT_READ" PROT_READ
[td_00021] ctx="列头: Description" Data can be read.
[td_00022] ctx="行 2: PROT_WRITE" PROT_WRITE
[td_00023] ctx="列头: Description" Data can be written.
[td_00024] ctx="行 3: PROT_EXEC" PROT_EXEC
[td_00025] ctx="列头: Description" Data can be executed.
[td_00026] ctx="行 4: PROT_NONE" PROT_NONE
[td_00027] ctx="列头: Description" Data cannot be accessed.
[p_00028] If an implementation cannot support the combination of access types specified by [I51]prot[/I51], the call to [I52]mmap[/I52]() shall fail.
[p_00029] An implementation may permit accesses other than those specified by [I53]prot[/I53]; however, the implementation shall not permit a write to succeed where PROT_WRITE has not been set and shall not permit any access where PROT_NONE alone has been set. The implementation shall support at least the following values of [I54]prot[/I54]: PROT_NONE, PROT_READ, PROT_WRITE, and the bitwise-inclusive OR of PROT_READ and PROT_WRITE. The file descriptor [I55]fildes[/I55] shall have been opened with read permission, regardless of the protection options specified. If PROT_WRITE is specified, the application shall ensure that it has opened the file descriptor [I56]fildes[/I56] with write permission unless MAP_PRIVATE is specified in the [I57]flags[/I57] parameter as described below.
[p_00030] The parameter [I58]flags[/I58] provides other information about the handling of the mapped data. The value of [I59]flags[/I59] is the bitwise-inclusive OR of these options, defined in [A60][I61]&lt;sys/mman.h&gt;[/I61][/A60]:
[td_00031] ctx="行 1: MAP_ANON" MAP_ANON
[td_00032] ctx="列头: Description" Synonym for MAP_ANONYMOUS.
[td_00033] ctx="行 2: MAP_ANONYMOUS" MAP_ANONYMOUS
[td_00034] ctx="列头: Description" Map anonymous memory.
[td_00035] ctx="行 3: MAP_SHARED" MAP_SHARED
[td_00036] ctx="列头: Description" Changes are shared.
[td_00037] ctx="行 4: MAP_PRIVATE" MAP_PRIVATE
[td_00038] ctx="列头: Description" Changes are private.
[td_00039] ctx="行 5: MAP_FIXED" MAP_FIXED
[td_00040] ctx="列头: Description" Interpret [I62]addr[/I62] exactly.
[p_00041] It is implementation-defined whether MAP_FIXED shall be supported. [S63][[A64]XSI[/A64]][/S63] [IMG65] &nbsp;MAP_FIXED shall be supported on XSI-conformant systems. [IMG66]
[p_00042] MAP_SHARED and MAP_PRIVATE describe the disposition of write references to the memory object. If MAP_SHARED is specified, write references shall change the underlying object. If MAP_PRIVATE is specified, modifications to the mapped data by the calling process shall be visible only to the calling process and shall not change the underlying object. It is unspecified whether modifications to the underlying object done after the MAP_PRIVATE mapping is established are visible through the MAP_PRIVATE mapping. Either MAP_SHARED or MAP_PRIVATE can be specified, but not both. The mapping type is retained across [A67][I68]fork[/I68]()[/A67].
[p_00043] The state of synchronization objects such as mutexes, semaphores, barriers, and conditional variables placed in shared memory mapped with MAP_SHARED becomes undefined when the last region in any process containing the synchronization object is unmapped.
[p_00044] [S69][[A70]TYM[/A70]][/S69] [IMG71] When [I72]fildes[/I72] represents a typed memory object opened with either the POSIX_TYPED_MEM_ALLOCATE flag or the POSIX_TYPED_MEM_ALLOCATE_CONTIG flag, [I73]mmap[/I73]() shall, if there are enough resources available, map [I74]len[/I74] bytes allocated from the corresponding typed memory object which were not previously allocated to any process in any processor that may access that typed memory object. If there are not enough resources available, the function shall fail. If [I75]fildes[/I75] represents a typed memory object opened with the POSIX_TYPED_MEM_ALLOCATE_CONTIG flag, these allocated bytes shall be contiguous within the typed memory object. If [I76]fildes[/I76] represents a typed memory object opened with the POSIX_TYPED_MEM_ALLOCATE flag, these allocated bytes may be composed of non-contiguous fragments within the typed memory object. If [I77]fildes[/I77] represents a typed memory object opened with neither the POSIX_TYPED_MEM_ALLOCATE_CONTIG flag nor the POSIX_TYPED_MEM_ALLOCATE flag, [I78]len[/I78] bytes starting at offset [I79]off[/I79] within the typed memory object are mapped, exactly as when mapping a file or shared memory object. In this case, if two processes map an area of typed memory using the same [I80]off[/I80] and [I81]len[/I81] values and using file descriptors that refer to the same memory pool (either from the same port or from a different port), both processes shall map the same region of storage. [IMG82]
[p_00045] When MAP_FIXED is set in the [I83]flags[/I83] argument, the implementation is informed that the value of [I84]pa[/I84] shall be [I85]addr[/I85], exactly. If MAP_FIXED is set, [I86]mmap[/I86]() may return MAP_FAILED and set [I87]errno[/I87] to [EINVAL]. If a MAP_FIXED request is successful, then any previous mappings [S88][[A89]ML|MLR[/A89]][/S88] [IMG90] &nbsp;or memory locks [IMG91] &nbsp;for those whole pages containing any part of the address range [[I92]pa[/I92],[I93]pa[/I93]+[I94]len[/I94]) shall be removed, as if by an appropriate call to [A95][I96]munmap[/I96]()[/A95], before the new mapping is established.
[p_00046] When MAP_FIXED is not set, the implementation uses [I97]addr[/I97] in an implementation-defined manner to arrive at [I98]pa[/I98]. The [I99]pa[/I99] so chosen shall be an area of the address space that the implementation deems suitable for a mapping of [I100]len[/I100] bytes to the file. All implementations interpret an [I101]addr[/I101] value of 0 as granting the implementation complete freedom in selecting [I102]pa[/I102], subject to constraints described below. A non-zero value of [I103]addr[/I103] is taken to be a suggestion of a process address near which the mapping should be placed. When the implementation selects a value for [I104]pa[/I104], it never places a mapping at address 0, nor does it replace any extant mapping.
[p_00047] If MAP_FIXED is specified and [I105]addr[/I105] is non-zero, it shall have the same remainder as the [I106]off[/I106] parameter, modulo the page size as returned by [A107][I108]sysconf[/I108]()[/A107] when passed _SC_PAGESIZE or _SC_PAGE_SIZE. The implementation may require that off is a multiple of the page size. If MAP_FIXED is specified, the implementation may require that [I109]addr[/I109] is a multiple of the page size. The system performs mapping operations over whole pages. Thus, while the parameter [I110]len[/I110] need not meet a size or alignment constraint, the system shall include, in any mapping operation, any partial page specified by the address range starting at [I111]pa[/I111] and continuing for [I112]len[/I112] bytes.
[p_00048] If MAP_ANONYMOUS (or its synonym MAP_ANON) is specified, [I113]fildes[/I113] is -1, and [I114]off[/I114] is 0, then [I115]mmap[/I115]() shall ignore [I116]fildes[/I116] and instead establish a mapping to a new anonymous memory object of size [I117]len[/I117]. The effect of specifying MAP_ANONYMOUS (or MAP_ANON) with other values of [I118]fildes[/I118] or [I119]off[/I119] is unspecified. Anonymous memory objects shall be initialized to all bits zero.
[p_00049] The system shall always zero-fill any partial page at the end of an object. Further, the system shall never write out any modified portions of the last page of an object which are beyond its end. References within the address range starting at [I120]pa[/I120] and continuing for [I121]len[/I121] bytes to whole pages following the end of an object shall result in delivery of a SIGBUS signal.
[p_00050] An implementation may generate SIGBUS signals when a reference would cause an error in the mapped object, such as out-of-space condition.
[p_00051] The [I122]mmap[/I122]() function shall add an extra reference to the file associated with the file descriptor [I123]fildes[/I123] which is not removed by a subsequent [A124][I125]close[/I125]()[/A124] on that file descriptor. This reference shall be removed when there are no more mappings to the file.
[p_00052] The last data access timestamp of the mapped file may be marked for update at any time between the [I126]mmap[/I126]() call and the corresponding [A127][I128]munmap[/I128]()[/A127] call. The initial read or write reference to a mapped region shall cause the file's last data access timestamp to be marked for update if it has not already been marked for update.
[p_00053] The last data modification and last file status change timestamps of a file that is mapped with MAP_SHARED and PROT_WRITE shall be marked for update at some point in the interval between a write reference to the mapped region and the next call to [A129][I130]msync[/I130]()[/A129] with MS_ASYNC or MS_SYNC for that portion of the file by any process. If there is no such call and if the underlying file is modified as a result of a write reference, then these timestamps shall be marked for update at some time after the write reference.
[p_00054] There may be implementation-defined limits on the number of memory regions that can be mapped (per process or per system).
[p_00055] [S131][[A132]XSI[/A132]][/S131] [IMG133] If such a limit is imposed, whether the number of memory regions that can be mapped by a process is decreased by the use of [A134][I135]shmat[/I135]()[/A134] is implementation-defined. [IMG136]
[p_00056] If [I137]mmap[/I137]() fails for reasons other than [EBADF], [EINVAL], or [ENOTSUP], some of the mappings in the address range starting at [I138]addr[/I138] and continuing for [I139]len[/I139] bytes may have been unmapped.
[h4_00057] [A140][/A140]RETURN VALUE
[p_00058] Upon successful completion, the [I141]mmap[/I141]() function shall return the address at which the mapping was placed ([I142]pa[/I142]); otherwise, it shall return a value of MAP_FAILED and set [I143]errno[/I143] to indicate the error. The symbol MAP_FAILED is defined in the [A144][I145]&lt;sys/mman.h&gt;[/I145][/A144] header. No successful return from [I146]mmap[/I146]() shall return the value MAP_FAILED.

[h4_00097] [A201][/A201]APPLICATION USAGE
[p_00098] Use of [I202]mmap[/I202]() may reduce the amount of memory available to other memory allocation functions.
[p_00099] Use of MAP_FIXED may result in unspecified behavior in further use of [A203][I204]malloc[/I204]()[/A203] and [A205][I206]shmat[/I206]()[/A205]. The use of MAP_FIXED is discouraged, as it may prevent an implementation from making the most effective use of resources. Most implementations require that [I207]off[/I207] and [I208]addr[/I208] are multiples of the page size as returned by [A209][I210]sysconf[/I210]()[/A209].
[p_00100] The application must ensure correct synchronization when using [I211]mmap[/I211]() in conjunction with any other file access method, such as [A212][I213]read[/I213]()[/A212] and [A214][I215]write[/I215]()[/A214], standard input/output, and [A216][I217]shmat[/I217]()[/A216].
[p_00101] The [I218]mmap[/I218]() function allows access to resources via address space manipulations, instead of [A219][I220]read[/I220]()[/A219]/[A221][I222]write[/I222]()[/A221]. Once a file is mapped, all a process has to do to access it is use the data at the address to which the file was mapped. [h4_00103] [A224][/A224]RATIONALE
[p_00104] After considering several other alternatives, it was decided to adopt the [I225]mmap[/I225]() definition found in SVR4 for mapping memory objects into process address spaces. The SVR4 definition is minimal, in that it describes only what has been built, and what appears to be necessary for a general and portable mapping facility.
[p_00105] Note that while [I226]mmap[/I226]() was first designed for mapping files, it is actually a general-purpose mapping facility. It can be used to map any appropriate object, such as memory, files, devices, and so on, into the address space of a process.
[p_00106] When a mapping is established, it is possible that the implementation may need to map more than is requested into the address space of the process because of hardware requirements. An application, however, cannot count on this behavior. Implementations that do not use a paged architecture may simply allocate a common memory region and return the address of it; such implementations probably do not allocate any more than is necessary. References past the end of the requested area are unspecified.
[p_00107] If an application requests a mapping that overlaps existing mappings in the process, it might be desirable that an implementation detect this and inform the application. However, if the program specifies a fixed address mapping (which requires some implementation knowledge to determine a suitable address, if the function is supported at all), then the program is presumed to be successfully managing its own address space and should be trusted when it asks to map over existing data structures. Furthermore, it is also desirable to make as few system calls as possible, and it might be considered onerous to require an [A227][I228]munmap[/I228]()[/A227] before an [I229]mmap[/I229]() to the same address range. This volume of POSIX.1-2024 specifies that the new mapping replaces any existing mappings (implying an automatic [A230][I231]munmap[/I231]()[/A230] on the address range), following existing practice in this regard. The standard developers also considered whether there should be a way for new mappings to overlay existing mappings, but found no existing practice for this.
[p_00108] It is not expected that all hardware implementations are able to support all combinations of permissions at all addresses. Implementations are required to disallow write access to mappings without write permission and to disallow access to mappings without any access permission. Other than these restrictions, implementations may allow access types other than those requested by the application. For example, if the application requests only PROT_WRITE, the implementation may also allow read access. A call to [I232]mmap[/I232]() fails if the implementation cannot support allowing all the access requested by the application. For example, some implementations cannot support a request for both write access and execute access simultaneously. All implementations must support requests for no access, read access, write access, and both read and write access. Strictly conforming code must only rely on the required checks. These restrictions allow for portability across a wide range of hardware.
[p_00109] The MAP_FIXED address treatment is likely to fail for non-page-aligned values and for certain architecture-dependent address ranges. Conforming implementations cannot count on being able to choose address values for MAP_FIXED without utilizing non-portable, implementation-defined knowledge. Nonetheless, MAP_FIXED is provided as a standard interface conforming to existing practice for utilizing such knowledge when it is available.
[p_00110] Similarly, in order to allow implementations that do not support virtual addresses, support for directly specifying any mapping addresses via MAP_FIXED is not required and thus a conforming application may not count on it.
[p_00111] The MAP_PRIVATE function can be implemented efficiently when memory protection hardware is available. When such hardware is not available, implementations can implement such &quot;mappings&quot; by simply making a real copy of the relevant data into process private memory, though this tends to behave similarly to [A233][I234]read[/I234]()[/A233].
[p_00112] The function has been defined to allow for many different models of using shared memory. However, all uses are not equally portable across all machine architectures. In particular, the [I235]mmap[/I235]() function allows the system as well as the application to specify the address at which to map a specific region of a memory object. The most portable way to use the function is always to let the system choose the address, specifying NULL as the value for the argument [I236]addr[/I236] and not to specify MAP_FIXED.
[p_00113] If it is intended that a particular region of a memory object be mapped at the same address in a group of processes (on machines where this is even possible), then MAP_FIXED can be used to pass in the desired mapping address. The system can still be used to choose the desired address if the first such mapping is made without specifying MAP_FIXED, and then the resulting mapping address can be passed to subsequent processes for them to pass in via MAP_FIXED. The availability of a specific address range cannot be guaranteed, in general.
[p_00114] The [I237]mmap[/I237]() function can be used to map a region of memory that is larger than the current size of the object. Memory access within the mapping but beyond the current end of the underlying objects may result in SIGBUS signals being sent to the process. The reason for this is that the size of the object can be manipulated by other processes and can change at any moment. The implementation should tell the application that a memory reference is outside the object where this can be detected; otherwise, written data may be lost and read data may not reflect actual data in the object.
[p_00115] Note that references beyond the end of the object do not extend the object as the new end cannot be determined precisely by most virtual memory hardware. Instead, the size can be directly manipulated by [A238][I239]ftruncate[/I239]()[/A238].
[p_00116] Process memory locking does apply to shared memory regions, and the MCL_FUTURE argument to [A240][I241]mlockall[/I241]()[/A240] can be relied upon to cause new shared memory regions to be automatically locked.
[p_00117] Existing implementations of [I242]mmap[/I242]() return the value -1 when unsuccessful. Since the casting of this value to type [B243]void *[/B243] cannot be guaranteed by the ISO&nbsp;C standard to be distinct from a successful value, this volume of POSIX.1-2024 defines the symbol MAP_FAILED, which a conforming implementation does not return as the result of a successful call.
[p_00118] Some historical implementations only supported MAP_ANON, some only supported MAP_ANONYMOUS, and some supported both spellings. This standard includes both spellings partly for application compatibility and partly because neither spelling was clearly more popular than the other at the time this feature was considered for standardization.
