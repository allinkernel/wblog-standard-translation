[h4_00001] [A1][/A1]NAME
[blockquote_00002] accept, accept4 — accept a new connection on a socket
[h4_00003] [A2][/A2]SYNOPSIS
[p_00004] [CODE3]
[h4_00005] [A4][/A4]DESCRIPTION
[p_00006] The [I5]accept[/I5]() function shall extract the first connection on the queue of pending connections, create a new socket with the same socket type protocol and address family as the specified socket, and allocate a new file descriptor for that socket. The file descriptor shall be allocated as described in [A6][I7]2.6 File Descriptor Allocation[/I7][/A6].
[p_00007] The [I8]accept[/I8]() function takes the following arguments:
[dt_00008] [I9]socket[/I9]
[dd_00009] Specifies a socket that was created with [A10][I11]socket[/I11]()[/A10], has been bound to an address with [A12][I13]bind[/I13]()[/A12], and has issued a successful call to [A14][I15]listen[/I15]()[/A14].
[dt_00010] [I16]address[/I16]
[dd_00011] Either a null pointer, or a pointer to a [B17]sockaddr[/B17] structure where the address of the connecting socket shall be returned.
[dt_00012] [I18]address_len[/I18]
[dd_00013] Either a null pointer, if [I19]address[/I19] is a null pointer, or a pointer to a [B20]socklen_t[/B20] object which on input specifies the length of the supplied [B21]sockaddr[/B21] structure, and on output specifies the length of the address of the connecting socket.
[p_00014] If [I22]address[/I22] is not a null pointer, the address of the peer for the accepted connection shall be stored in the [B23]sockaddr[/B23] structure pointed to by [I24]address[/I24], and the length of this address shall be stored in the object pointed to by [I25]address_len[/I25].
[p_00015] If the actual length of the address is greater than the length of the supplied [B26]sockaddr[/B26] structure, the stored address shall be truncated.
[p_00016] If the protocol permits connections by unbound clients, and the peer is not bound, then the value stored in the object pointed to by [I27]address[/I27] is unspecified.
[p_00017] If the listen queue is empty of connection requests and O_NONBLOCK is not set on the file descriptor for the socket, [I28]accept[/I28]() shall block until a connection is present. If the [A29][I30]listen[/I30]()[/A29] queue is empty of connection requests and O_NONBLOCK is set on the file descriptor for the socket, [I31]accept[/I31]() shall fail and set [I32]errno[/I32] to [EAGAIN] or [EWOULDBLOCK].
[p_00018] The accepted socket cannot itself accept more connections. The original socket remains open and can accept more connections.
[p_00019] If O_NONBLOCK is set on the file description for [I33]socket[/I33], it is implementation-defined whether O_NONBLOCK will be set on the file description created by [I34]accept[/I34](). FD_CLOEXEC and FD_CLOFORK for the new file descriptor shall be clear, regardless of how they are currently set for [I35]socket[/I35].
[p_00020] It is implementation-defined which socket options, if any, on the accepted socket will have a default value determined by a value previously customized by [A36][I37]setsockopt[/I37]()[/A36] on [I38]socket[/I38], rather than the default value used for other new sockets.
[p_00021] The [I39]accept4[/I39]() function shall be equivalent to the [I40]accept[/I40]() function, except that the state of O_NONBLOCK on the new file description, and FD_CLOEXEC and FD_CLOFORK on the returned file descriptor shall be determined solely by the [I41]flag[/I41] argument, which can be constructed from a bitwise-inclusive OR of flags from the following list:
[dt_00022] SOCK_CLOEXEC
[dd_00023] Atomically set the FD_CLOEXEC flag on the new file descriptor.
[dt_00024] SOCK_CLOFORK
[dd_00025] Atomically set the FD_CLOFORK flag on the new file descriptor.
[dt_00026] SOCK_NONBLOCK
[dd_00027] Set the O_NONBLOCK file status flag on the new file description.
[p_00028] Implementations may define additional flags.
[h4_00029] [A42][/A42]RETURN VALUE
[p_00030] Upon successful completion, [I43]accept[/I43]() and [I44]accept4[/I44]() shall return the non-negative file descriptor of the accepted socket. Otherwise, -1 shall be returned, [I45]errno[/I45] shall be set to indicate the error, and any object pointed to by [I46]address_len[/I46] shall remain unchanged.
[h4_00031] [A47][/A47]ERRORS
[p_00032] The [I48]accept[/I48]() and [I49]accept4[/I49]() functions shall fail if:
[dt_00033] [EAGAIN] or [EWOULDBLOCK]
[dd_00034] O_NONBLOCK is set for the socket file descriptor and no connections are present to be accepted.
[dt_00035] [EBADF]
[dd_00036] The [I50]socket[/I50] argument is not a valid file descriptor.
[dt_00037] [ECONNABORTED]
[dd_00038] A connection has been aborted.
[dt_00039] [EINTR]
[dd_00040] The [I51]accept[/I51]() function was interrupted by a signal that was caught before a valid connection arrived.
[dt_00041] [EINVAL]
[dd_00042] The [I52]socket[/I52] is not accepting connections.
[dt_00043] [EMFILE]
[dd_00044] All file descriptors available to the process are currently open.
[dt_00045] [ENFILE]
[dd_00046] The maximum number of file descriptors in the system are already open.
[dt_00047] [ENOBUFS]
[dd_00048] No buffer space is available.
[dt_00049] [ENOMEM]
[dd_00050] There was insufficient memory available to complete the operation.
[dt_00051] [ENOTSOCK]
[dd_00052] The [I53]socket[/I53] argument does not refer to a socket.
[dt_00053] [EOPNOTSUPP]
[dd_00054] The socket type of the specified socket does not support accepting connections.
[p_00055] The [I54]accept[/I54]() and [I55]accept4[/I55]() functions may fail if:
[dt_00056] [EPROTO]
[dd_00057] A protocol error has occurred.
[p_00058] The [I56]accept4[/I56]() function may fail if:
[dt_00059] [EINVAL]
[dd_00060] The value of the [I57]flag[/I57] argument is invalid.
[h4_00061] [A58][/A58]EXAMPLES
[p_00062] None.
[h4_00063] [A59][/A59]APPLICATION USAGE
[p_00064] When a connection is available, [A60][I61]select[/I61]()[/A60] indicates that the file descriptor for the socket is ready for reading.
[p_00065] Many socket options are described as having implementation-defined default values, which may differ according to the protocol in use by the socket. Existing practice differs on whether socket options such as SO_SNDBUF that were customized on the original listening socket will impact the corresponding option on the newly returned socket. Implementations are permitted to allow inheritance of customized settings where it makes sense, although the most portable approach for applications is to limit [A62][I63]setsockopt[/I63]()[/A62] customizations to only the accepted socket.
[p_00066] For AF_UNIX sockets, it is recommended that [I64]address[/I64] points to a buffer of length greater than [CODE65] which has been initialized with null bytes. That way, even if the implementation supports the use of all bytes of [I66]sun_path[/I66] without a terminating null byte, the larger buffer guarantees that the [I67]sun_path[/I67] member can then be passed to other interfaces that expect a null-terminated string. If no truncation occurred based on the input value of [I68]address_len[/I68], it is unspecified whether the returned [I69]address_len[/I69] will be [CODE70], or merely a value at least as large as [CODE71] plus the number of non-null bytes stored in [I72]sun_path[/I72].
[h4_00067] [A73][/A73]RATIONALE
[p_00068] The SOCK_CLOEXEC and SOCK_CLOFORK flags of [I74]accept4[/I74]() are necessary to avoid a data race in multi-threaded applications. Without SOCK_CLOFORK, a file descriptor is leaked into a child process created by one thread in the window between another thread creating a file descriptor with [I75]accept[/I75]() and then using [A76][I77]fcntl[/I77]()[/A76] to set the FD_CLOFORK flag. Without SOCK_CLOEXEC, a file descriptor intentionally inherited by child processes is similarly leaked into an executed program if FD_CLOEXEC is not set atomically.
[p_00069] Two designs often used for network servers are multi-threaded servers with a pre-created pool of worker threads, where the thread that accepts the connection request hands over the new file descriptor to a worker thread for servicing, and pre-fork servers with a pre-created pool of worker processes, where the process that accepts the connection request passes the new file descriptor (for example via [A78][I79]sendmsg[/I79]()[/A78]) to a worker process. In both of these designs, [I80]accept4[/I80]() should be used with the SOCK_CLOFORK flag set. Simpler designs are also sometimes used that do not pre-create a pool. For a multi-threaded server that creates a thread to handle each request, SOCK_CLOFORK should still be used. For a forking server that creates a child to service each request, clearly SOCK_CLOFORK cannot be used if the child is to inherit the file descriptor to be serviced, and therefore this type of server needs to use an alternative method of indicating the end of communications, for example using [A81][I82]shutdown[/I82]()[/A81], to ensure the client sees end-of-file, rather than just closing the socket. Such child processes should set FD_CLOFORK on the inherited file descriptor before they attempt to start any additional child processes to avoid leakage into those children.
[p_00070] The SOCK_NONBLOCK flag is for convenience in avoiding additional [A83][I84]fcntl[/I84]()[/A83] calls, as well as providing specific control over the O_NONBLOCK flag, since traditional implementations of [I85]accept[/I85]() differ on whether O_NONBLOCK is inherited from the [I86]socket[/I86] argument.
