[blockquote_00002] signal — signal management

[h4_00005] [A4][/A4]DESCRIPTION
[p_00006] The [I5]signal[/I5]() function chooses one of three ways in which receipt of the signal number [I6]sig[/I6] is to be subsequently handled. If the value of [I7]func[/I7] is SIG_DFL, default handling for that signal shall occur. If the value of [I8]func[/I8] is SIG_IGN, the signal shall be ignored. Otherwise, the application shall ensure that [I9]func[/I9] points to a function to be called when that signal occurs. An invocation of such a function because of a signal, or (recursively) of any further functions called by that invocation (other than functions in the standard library), is called a &quot;signal handler&quot;.
[p_00007] When a signal occurs, and [I10]func[/I10] points to a function, it is implementation-defined whether the equivalent of a:
[p_00008] is executed or the implementation prevents some implementation-defined set of signals (at least including [I11]sig[/I11]) from occurring until the current signal handling has completed. (If the value of [I12]sig[/I12] is SIGILL, the implementation may alternatively define that no action is taken.) Next the equivalent of:
[p_00009] is executed. If and when the function returns, if the value of [I13]sig[/I13] was SIGFPE, SIGILL, or SIGSEGV or any other implementation-defined value corresponding to a computational exception, the behavior is undefined. Otherwise, the program shall resume execution at the point it was interrupted. The ISO&nbsp;C standard places a restriction on applications relating to the use of [A14][I15]raise[/I15]()[/A14] from signal handlers. [S16][[A17]CX[/A17]][/S16] [IMG18] &nbsp;This restriction does not apply to POSIX applications, as POSIX.1-2024 requires [A19][I20]raise[/I20]()[/A19] to be async-signal-safe (see [A21][I22]2.4.3 Signal Actions[/I22][/A21]). [p_00020] [S74][[A75]CX[/A75]][/S74] [IMG76] The [I77]signal[/I77]() function is required to be thread-safe. (See [A78][I79]2.9.1 Thread-Safety[/I79][/A78].) [IMG80]
[h4_00021] [A81][/A81]RETURN VALUE
[p_00022] If the request can be honored, [I82]signal[/I82]() shall return the value of [I83]func[/I83] for the most recent call to [I84]signal[/I84]() for the specified signal [I85]sig[/I85]. Otherwise, SIG_ERR shall be returned and a positive value shall be stored in [I86]errno[/I86].
[h4_00023] [A87][/A87]ERRORS
[p_00024] The [I88]signal[/I88]() function shall fail if:
[dt_00025] [EINVAL]
[dd_00026] [S89][[A90]CX[/A90]][/S89] [IMG91] The [I92]sig[/I92] argument is not a valid signal number or an attempt is made to catch a signal that cannot be caught or ignore a signal that cannot be ignored. [IMG93]
[p_00027] The [I94]signal[/I94]() function may fail if:
[dt_00028] [EINVAL]
[dd_00029] [S95][[A96]CX[/A96]][/S95] [IMG97] An attempt was made to set the action to SIG_DFL for a signal that cannot be caught or ignored (or both). [IMG98]
[h4_00030] [A99][/A99]EXAMPLES
[p_00031] None.
[h4_00032] [A100][/A100]APPLICATION USAGE
[p_00033] The [A101][I102]sigaction[/I102]()[/A101] function provides a more comprehensive and reliable mechanism for controlling signals; new applications should use [A103][I104]sigaction[/I104]()[/A103] rather than [I105]signal[/I105]().
[h4_00034] [A106][/A106]RATIONALE
[p_00035] The ISO&nbsp;C standard says that the use of [I107]signal[/I107]() in a multi-threaded program results in undefined behavior. However, POSIX.1 has required [I108]signal[/I108]() to be thread-safe since before threads were added to the ISO&nbsp;C standard.
