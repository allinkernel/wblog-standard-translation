[h4_00005] [A5][/A5]DESCRIPTION
[p_00006] The [I6]sigaction[/I6]() function allows the calling process to examine and/or specify the action to be associated with a specific signal. The argument [I7]sig[/I7] specifies the signal; acceptable values are defined in [A8][I9]&lt;signal.h&gt;[/I9][/A8].
[p_00007] The structure [B10]sigaction[/B10], used to describe an action to be taken, is defined in the [A11][I12]&lt;signal.h&gt;[/I12][/A11] header to include at least the following members:

[td_00013] ctx="列头: Description" Additional set of signals to be blocked during execution of signal-catching function.

[p_00020] The storage occupied by [I21]sa_handler[/I21] and [I22]sa_sigaction[/I22] may overlap, and a conforming application shall not use both simultaneously.
[p_00021] If the argument [I23]act[/I23] is not a null pointer, it points to a structure specifying the action to be associated with the specified signal. If the argument [I24]oact[/I24] is not a null pointer, the action previously associated with the signal is stored in the location pointed to by the argument [I25]oact[/I25]. If the argument [I26]act[/I26] is a null pointer, signal handling is unchanged; thus, the call can be used to enquire about the current handling of a given signal. The SIGKILL and SIGSTOP signals shall not be added to the signal mask using this mechanism; this restriction shall be enforced by the system without causing an error to be indicated.
[p_00022] If the SA_SIGINFO flag (see below) is cleared in the [I27]sa_flags[/I27] field of the [B28]sigaction[/B28] structure, the [I29]sa_handler[/I29] field identifies the action to be associated with the specified signal. If the SA_SIGINFO flag is set in the [I30]sa_flags[/I30] field, the [I31]sa_sigaction[/I31] field specifies a signal-catching function.
[p_00023] The [I32]sa_flags[/I32] field can be used to modify the behavior of the specified signal.
[p_00024] The following flags, defined in the [A33][I34]&lt;signal.h&gt;[/I34][/A33] header, can be set in [I35]sa_flags[/I35]:
[dt_00025] SA_NOCLDSTOP
[p_00026] If [I36]sig[/I36] is SIGCHLD and the SA_NOCLDSTOP flag is not set in [I37]sa_flags[/I37], and the implementation supports the SIGCHLD signal, then a SIGCHLD signal shall be generated for the calling process whenever any of its child processes stop [S38][[A39]XSI[/A39]][/S38] [IMG40] &nbsp;and a SIGCHLD signal may be generated for the calling process whenever any of its stopped child processes are continued. [IMG41] &nbsp;If [I42]sig[/I42] is SIGCHLD and the SA_NOCLDSTOP flag is set in [I43]sa_flags[/I43], then the implementation shall not generate a SIGCHLD signal in this way.
[dt_00027] SA_ONSTACK
[dd_00028] [S44][[A45]XSI[/A45]][/S44] [IMG46] If set and an alternate signal stack has been declared with [A47][I48]sigaltstack[/I48]()[/A47], the signal shall be delivered to the calling process on that stack. Otherwise, the signal shall be delivered on the current stack. [IMG49]
[dt_00029] SA_RESETHAND
[dd_00030] If set, the disposition of the signal shall be reset to SIG_DFL and the SA_SIGINFO flag shall be cleared on entry to the signal handler.   [B50]Note:[/B50] SIGILL and SIGTRAP cannot be automatically reset when delivered; the system silently enforces this restriction.   Otherwise, the disposition of the signal shall not be modified on entry to the signal handler. In addition, if this flag is set, [I51]sigaction[/I51]() may behave as if the SA_NODEFER flag were also set.
[dt_00031] SA_RESTART
[dd_00032] This flag affects the behavior of interruptible functions; that is, those specified to fail with [I52]errno[/I52] set to [EINTR]. If set, and a function specified as interruptible is interrupted by this signal, the function shall restart and shall not fail with [EINTR] unless otherwise specified. If an interruptible function which uses a timeout is restarted, the duration of the timeout following the restart is set to an unspecified value that does not exceed the original timeout value. If the flag is not set, interruptible functions interrupted by this signal shall fail with [I53]errno[/I53] set to [EINTR].

[dt_00042] SA_NODEFER
[dd_00043] If set and [I77]sig[/I77] is caught, [I78]sig[/I78] shall not be added to the thread's signal mask on entry to the signal handler unless it is included in [I79]sa_mask[/I79]. Otherwise, [I80]sig[/I80] shall always be added to the thread's signal mask on entry to the signal handler.
[p_00044] When a signal is caught by a signal-catching function installed by [I81]sigaction[/I81](), a new signal mask is calculated and installed for the duration of the signal-catching function (or until a call to either [A82][I83]sigprocmask[/I83]()[/A82] or [A84][I85]sigsuspend[/I85]()[/A84] is made). This mask is formed by taking the union of the current signal mask and the value of the [I86]sa_mask[/I86] for the signal being delivered, and unless SA_NODEFER or SA_RESETHAND is set, then including the signal being delivered. If and when the user's signal handler returns normally, the original signal mask is restored.
[p_00045] Once an action is installed for a specific signal, it shall remain installed until another action is explicitly requested (by another call to [I87]sigaction[/I87]()), until the SA_RESETHAND flag causes resetting of the handler, or until one of the [I88][A89]exec[/A89][/I88] functions is called.
[p_00046] If the previous action for [I90]sig[/I90] had been established by [A91][I92]signal[/I92]()[/A91], the values of the fields returned in the structure pointed to by [I93]oact[/I93] are unspecified, and in particular [I94]oact[/I94]-&gt;[I95]sa_handler[/I95] is not necessarily the same value passed to [A96][I97]signal[/I97]()[/A96]. However, if a pointer to the same structure or a copy thereof is passed to a subsequent call to [I98]sigaction[/I98]() via the [I99]act[/I99] argument, handling of the signal shall be as if the original call to [A100][I101]signal[/I101]()[/A100] were repeated.
[p_00047] If [I102]sigaction[/I102]() fails, no new signal handler is installed.
[p_00048] It is unspecified whether an attempt to set the action for a signal that cannot be caught or ignored to SIG_DFL is ignored or causes an error to be returned with [I103]errno[/I103] set to [EINVAL].
[p_00049] If SA_SIGINFO is not set in [I104]sa_flags[/I104], then the disposition of subsequent occurrences of [I105]sig[/I105] when it is already pending is implementation-defined; the signal-catching function shall be invoked with a single argument. If SA_SIGINFO is set in [I106]sa_flags[/I106], then subsequent occurrences of [I107]sig[/I107] generated by [A108][I109]sigqueue[/I109]()[/A108] or as a result of any signal-generating function that supports the specification of an application-defined value (when [I110]sig[/I110] is already pending) shall be queued in FIFO order until delivered or accepted; the signal-catching function shall be invoked with three arguments. The application specified value is passed to the signal-catching function as the [I111]si_value[/I111] member of the [B112]siginfo_t[/B112] structure.
[p_00050] The result of the use of [I113]sigaction[/I113]() and a [A114][I115]sigwait[/I115]()[/A114] function concurrently within a process on the same signal is unspecified.
[h4_00051] [A116][/A116]RETURN VALUE
[p_00052] Upon successful completion, [I117]sigaction[/I117]() shall return 0; otherwise, -1 shall be returned, [I118]errno[/I118] shall be set to indicate the error, and no new signal-catching function shall be installed.

[h4_00064] [A129][/A129]APPLICATION USAGE
[p_00065] The [I130]sigaction[/I130]() function supersedes the [A131][I132]signal[/I132]()[/A131] function, and should be used in preference. In particular, [I133]sigaction[/I133]() and [A134][I135]signal[/I135]()[/A134] should not be used in the same process to control the same signal. The behavior of async-signal-safe functions, as defined in their respective DESCRIPTION sections, is as specified by this volume of POSIX.1-2024, regardless of invocation from a signal-catching function. This is the only intended meaning of the statement that async-signal-safe functions may be used in signal-catching functions without restrictions. Applications must still consider all effects of such functions on such things as data structures, files, and process state. In particular, application developers need to consider the restrictions on interactions when interrupting [A136][I137]sleep[/I137]()[/A136] and interactions among multiple handles for a file description. The fact that any specific function is listed as async-signal-safe does not necessarily mean that invocation of that function from a signal-catching function is recommended.
[p_00066] In order to prevent errors arising from interrupting non-async-signal-safe function calls, applications should protect calls to these functions either by blocking the appropriate signals or through the use of some programmatic semaphore (see [A138][I139]semget[/I139]()[/A138], [A140][I141]sem_init[/I141]()[/A140], [A142][I143]sem_open[/I143]()[/A142], and so on). Note in particular that even the &quot;safe&quot; functions may modify [I144]errno[/I144]; the signal-catching function, if not executing as an independent thread, should save and restore its value in order to avoid the possibility that delivery of a signal in between an error return from a function that sets [I145]errno[/I145] and the subsequent examination of [I146]errno[/I146] could result in the signal-catching function changing the value of [I147]errno[/I147]. Naturally, the same principles apply to the async-signal-safety of application routines and asynchronous data access. Note that [A148][I149]longjmp[/I149]()[/A148] and [A150][I151]siglongjmp[/I151]()[/A150] are not in the list of async-signal-safe functions. This is because the code executing after [A152][I153]longjmp[/I153]()[/A152] and [A154][I155]siglongjmp[/I155]()[/A154] can call any unsafe functions with the same danger as calling those unsafe functions directly from the signal handler. Applications that use [A156][I157]longjmp[/I157]()[/A156] and [A158][I159]siglongjmp[/I159]()[/A158] from within signal handlers require rigorous protection in order to be portable. Many of the other functions that are excluded from the list are traditionally implemented using either [A160][I161]malloc[/I161]()[/A160] or [A162][I163]free[/I163]()[/A162] functions or the standard I/O library, both of which traditionally use data structures in a non-async-signal-safe manner. Since any combination of different functions using a common data structure can cause async-signal-safety problems, this volume of POSIX.1-2024 does not define the behavior when any unsafe function is called in a signal handler that interrupts an unsafe function.
[p_00067] Usually, the signal is executed on the stack that was in effect before the signal was delivered. An alternate stack may be specified to receive a subset of the signals being caught.
[p_00068] When the signal handler returns, the receiving thread resumes execution at the point it was interrupted unless the signal handler makes other arrangements. If [A164][I165]longjmp[/I165]()[/A164] is used to leave the signal handler, then the signal mask must be explicitly restored.
[p_00069] This volume of POSIX.1-2024 defines the third argument of a signal handling function when SA_SIGINFO is set as a [B166]void *[/B166] instead of a [B167]ucontext_t *[/B167], but without requiring type checking. New applications should explicitly cast the third argument of the signal handling function to [B168]ucontext_t *[/B168].

Much the same information is available in the objects pointed to by the second argument of the signal handler specified when SA_SIGINFO is set.
[p_00072] Since the [I174]sigaction[/I174]() function is allowed but not required to set SA_NODEFER when the application sets the SA_RESETHAND flag, applications which depend on the SA_RESETHAND functionality for the newly installed signal handler must always explicitly set SA_NODEFER when they set SA_RESETHAND in order to be portable.

[h4_00074] [A177][/A177]RATIONALE
[p_00075] Although this volume of POSIX.1-2024 requires that signals that cannot be ignored shall not be added to the signal mask when a signal-catching function is entered, there is no explicit requirement that subsequent calls to [I178]sigaction[/I178]() reflect this in the information returned in the [I179]oact[/I179] argument. In other words, if SIGKILL is included in the [I180]sa_mask[/I180] field of [I181]act[/I181], it is unspecified whether or not a subsequent call to [I182]sigaction[/I182]() returns with SIGKILL included in the [I183]sa_mask[/I183] field of [I184]oact[/I184].
[p_00076] The SA_NOCLDSTOP flag, when supplied in the [I185]act[/I185]-&gt;[I186]sa_flags[/I186] parameter, allows overloading SIGCHLD with the System V semantics that each SIGCLD signal indicates a single terminated child. Most conforming applications that catch SIGCHLD are expected to install signal-catching functions that repeatedly call the [A187][I188]waitpid[/I188]()[/A187] function with the WNOHANG flag set, acting on each child for which status is returned, until [A189][I190]waitpid[/I190]()[/A189] returns zero. If stopped children are not of interest, the use of the SA_NOCLDSTOP flag can prevent the overhead from invoking the signal-catching routine when they stop.
[p_00077] Some historical implementations also define other mechanisms for stopping processes, such as the [I191]ptrace[/I191]() function. These implementations usually do not generate a SIGCHLD signal when processes stop due to this mechanism; however, that is beyond the scope of this volume of POSIX.1-2024.
[p_00078] This volume of POSIX.1-2024 requires that calls to [I192]sigaction[/I192]() that supply a NULL [I193]act[/I193] argument succeed, even in the case of signals that cannot be caught or ignored (that is, SIGKILL or SIGSTOP). The System V [A194][I195]signal[/I195]()[/A194] and BSD [I196]sigvec[/I196]() functions return [EINVAL] in these cases and, in this respect, their behavior varies from [I197]sigaction[/I197]().
[p_00079] This volume of POSIX.1-2024 requires that [I198]sigaction[/I198]() properly save and restore a signal action set up by the ISO&nbsp;C standard [A199][I200]signal[/I200]()[/A199] function. However, there is no guarantee that the reverse is true, nor could there be given the greater amount of information conveyed by the [B201]sigaction[/B201] structure. Because of this, applications should avoid using both functions for the same signal in the same process. Since this cannot always be avoided in case of general-purpose library routines, they should always be implemented with [I202]sigaction[/I202]().
[p_00080] It was intended that the [A203][I204]signal[/I204]()[/A203] function should be implementable as a library routine using [I205]sigaction[/I205]().
[p_00081] The POSIX Realtime Extension extends the [I206]sigaction[/I206]() function as specified by the POSIX.1-1990 standard to allow the application to request on a per-signal basis via an additional signal action flag that the extra parameters, including the application-defined signal value, if any, be passed to the signal-catching function.
