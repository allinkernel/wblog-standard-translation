[h4_00001] [A1][/A1]NAME
[blockquote_00002] exit — terminate a process
[h4_00003] [A2][/A2]SYNOPSIS
[p_00004] [CODE3]
[h4_00005] [A4][/A4]DESCRIPTION
[p_00006] The [I5]exit[/I5]() function shall cause normal process termination to occur. No functions registered by the [A6][I7]at_quick_exit[/I7]()[/A6] function shall be called. If a process calls the [I8]exit[/I8]() function more than once, or calls the [A9][I10]quick_exit[/I10]()[/A9] function in addition to the [I11]exit[/I11]() function, the behavior is undefined.
[p_00007] The value of [I12]status[/I12] can be 0, EXIT_SUCCESS, EXIT_FAILURE, [S13][[A14]CX[/A14]][/S13] [IMG15] &nbsp;or any other value, though only the least significant 8 bits (that is, [I16]status[/I16] & 0377) shall be available from [A17][I18]wait[/I18]()[/A17] and [A19][I20]waitpid[/I20]()[/A19]; the full value shall be available from [A21][I22]waitid[/I22]()[/A21] and in the [B23]siginfo_t[/B23] passed to a signal handler for SIGCHLD. [IMG24]
[p_00008] The [I25]exit[/I25]() function shall first call all functions registered by [A26][I27]atexit[/I27]()[/A26], in the reverse order of their registration, except that a function is called after any previously registered functions that had already been called at the time it was registered. Each function is called as many times as it was registered. If, during the call to any such function, a call to the [A28][I29]longjmp[/I29]()[/A28] function is made that would terminate the call to the registered function, the behavior is undefined.
[p_00009] If a function registered by a call to [A30][I31]atexit[/I31]()[/A30] fails to return, the remaining registered functions shall not be called and the rest of the [I32]exit[/I32]() processing shall not be completed.
[p_00010] The [I33]exit[/I33]() function shall then flush all open streams with unwritten buffered data. [S34][[A35]CX[/A35]][/S34] [IMG36] For each stream which is the active handle to its underlying file descriptor, and for which the file is not already at EOF and is capable of seeking, the file offset of the underlying open file description shall be set to the file position of the stream. For each open stream, the [I37]exit[/I37]() function shall perform the equivalent of a [A38][I39]close[/I39]()[/A38] on the file descriptor that is associated with the stream. [IMG40] Finally, the process shall be terminated [S41][[A42]CX[/A42]][/S41] [IMG43] &nbsp;with the same consequences as described in [A44][I45]Consequences of Process Termination[/I45]()[/A44]. [IMG46]
[h4_00011] [A47][/A47]RETURN VALUE
[p_00012] The [I48]exit[/I48]() function does not return.
[h4_00013] [A49][/A49]ERRORS
[p_00014] No errors are defined.
[h4_00015] [A50][/A50]EXAMPLES
[p_00016] See APPLICATION USAGE.
[h4_00017] [A51][/A51]APPLICATION USAGE
[p_00018] When a stream that has unwritten buffered data is flushed by [I52]exit[/I52]() there is no way for the calling process to discover whether or not [I53]exit[/I53]() successfully wrote the data to the underlying file descriptor. Therefore, it is strongly recommended that applications always ensure there is no unwritten buffered data in any stream when calling [I54]exit[/I54](), or returning from the initial call to [I55]main[/I55](), with a [I56]status[/I56] value that indicates no errors occurred.
[p_00019] For example, the following code demonstrates one way to ensure that [I57]stdout[/I57] has already been successfully flushed before calling [I58]exit[/I58]() with status 0. If the flush fails, the file descriptor underlying [I59]stdout[/I59] is closed so that [I60]exit[/I60]() will not try to repeat the failed write operation. If the flush succeeds, a final check with [A61][I62]ferror[/I62]()[/A61] is performed to ensure that there were no write errors during earlier flush operations (that were not handled at the time).
