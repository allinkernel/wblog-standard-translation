XSH 函数：_exit()

名称 (NAME)

_Exit, _exit — 终止进程 (terminate a process)

概要 (SYNOPSIS)

#include <stdlib.h>

_Noreturn void _Exit(int status);


#include <unistd.h>
_Noreturn void _exit(int status);

说明 (DESCRIPTION)

对于 _Exit()：[CX] 此参考页上描述的功能与 ISO C 标准保持一致。此处描述的要求与 ISO C 标准之间的任何冲突都是无意的。本卷 POSIX.1-2024 遵从 ISO C 标准。

status 的值可以是 0、EXIT_SUCCESS、EXIT_FAILURE、[CX] 或任何其他值，尽管只有最低有效的 8 位（即 status & 0377）应可从 wait() 和 waitpid() 获得；完整值应可从 waitid() 以及传递给 SIGCHLD 信号处理器的 siginfo_t 中获得。

[CX] _Exit() 和 _exit() 函数应在功能上等效。

_Exit() [CX] 和 _exit() 函数不应调用用 atexit() 或 at_quick_exit() 注册的函数，也不应调用任何注册的信号处理器。[CX] 打开的流不应被刷新。 打开的流是否被关闭（不刷新）是实现定义的。最后，调用进程应被终止，并产生下述后果。

进程终止的后果 (Consequences of Process Termination)

[CX] 由任何原因引起的进程终止应具有以下后果：

注意：
这些后果都是对 ISO C 标准的扩展，并且不再进一步 CX 阴影标记。然而，与 XSI 选项相关的功能被阴影标记。

  • 在调用进程中打开的所有文件描述符、目录流、转换描述符和消息目录描述符应被关闭。

  • [XSI] 如果调用进程的父进程已设置其 SA_NOCLDWAIT 标志或将 SIGCHLD 信号的动作设置为 SIG_IGN：

    • 进程的状态信息（参见 2.12 状态信息）（如果有）应被丢弃。

    • 调用进程的生命周期应立即结束。如果设置了 SA_NOCLDWAIT，是否向父进程发送 SIGCHLD 信号是实现定义的。

    • 如果调用进程的父进程中的某个线程阻塞在 wait()、waitpid() 或 waitid() 中，并且父进程在等待的子进程集合中没有剩余的子进程，则 wait()、waitid() 或 waitpid() 函数应失败并将 errno 设置为 [ECHILD]。

    否则：

    • 应生成状态信息（参见 2.12 状态信息）。

    • 调用进程应转变为僵尸进程。其状态信息应可供父进程使用，直到进程的生命周期结束。

    • 一旦其父进程通过当前阻塞的或未来的对 wait()、waitid()（不带 WNOWAIT）或 waitpid() 的调用获得进程的状态信息，进程的生命周期应结束。

    • 如果调用进程的父进程中的一个或多个线程阻塞在对 wait()、waitid() 或 waitpid() 的调用中等待该进程终止，则这些线程中的一个（或者，如果有任何线程以 WNOWAIT 调用 waitid()，则可能不止一个）应按 2.12 状态信息 中的规定获得进程的状态信息并解除阻塞。

    • 应向父进程发送 SIGCHLD。

  • 进程的终止不会直接终止其子进程。如下所述发送 SIGHUP 信号在某些情况下会间接终止子进程。

  • 调用进程的所有现有子进程和僵尸进程的父进程 ID 应被设置为实现定义的系统进程的进程 ID。也就是说，这些进程应被特殊的系统进程继承。

  • [XSI] 每个附加的共享内存段被分离，并且与其共享内存 ID 关联的数据结构中的 shm_nattch（参见 shmget()）值应减 1。

  • [XSI] 对于调用进程已为其设置 semadj 值（参见 semop()）的每个信号量，该值应被添加到指定信号量的 semval 中。

  • 如果进程是控制进程，则 SIGHUP 信号应被发送到属于调用进程的控制终端的前台进程组中的每个进程。

  • 如果进程是控制进程，则与会话关联的控制终端应与会话分离，允许它被新的控制进程获取。

  • 如果进程的退出导致进程组成为孤儿进程组，并且新成为孤儿的进程组中有任何成员被停止，则 SIGHUP 信号后跟 SIGCONT 信号应被发送到新成为孤儿的进程组中的每个进程。

  • 调用进程中所有打开的命名信号量应如同通过适当调用 sem_close() 一样被关闭。调用进程中所有打开的未命名信号量应如同通过适当调用 sem_destroy() 一样被销毁。

  • [ML] 由进程通过调用 mlockall() 或 mlock() 建立的任何内存锁应被移除。如果调用进程地址空间中被锁定的页面也被映射到其他进程的地址空间中并被那些进程锁定，则由其他进程建立的锁不应受到此进程对 _Exit() 或 _exit() 的调用的影响。

  • 在进程中创建的内存映射应在进程被销毁之前被取消映射。

  • [TYM] 在调用进程中映射的任何类型化内存块应被取消映射，如同隐式调用 munmap() 来取消映射它们。

  • [MSG] 调用进程中所有打开的消息队列描述符应如同通过适当调用 mq_close() 一样被关闭。

  • 任何未完成的可取消异步 I/O 操作可以被取消。未被取消的那些异步 I/O 操作应如同 _Exit() 或 _exit() 操作尚未发生一样完成，但任何相关的信号通知应被抑制。_Exit() 或 _exit() 操作可以阻塞等待此类 I/O 完成。是否有任何 I/O 被取消，以及在 _Exit() 或 _exit() 时可以取消哪些 I/O，是实现定义的。

  • 由对 _Exit() 或 _exit() 的调用终止的线程不应调用其取消清理处理器或每线程数据析构函数。

应用程序用法 (APPLICATION USAGE)

通常应用程序应使用 exit() 而不是 _Exit() 或 _exit()。

退出状态 126 及更大在某些情况下是模糊的，因为它们在 shell 中具有特殊含义（参见 2.8.2 命令的退出状态 和 sh 的 EXIT STATUS 部分）。

原理 (RATIONALE)

进程终止 (Process Termination)

早期的提案在正常和异常进程终止之间作了区分。异常终止仅由某些信号引起，并导致实现定义的 "动作"，如下所述。后来的提案区分了三种终止类型：正常终止（如当前规范中）、简单异常终止 和 带动作的异常终止。两种异常终止类型之间的区别再次在于它们由不同的信号引起，并且在后者的情况下会导致实现定义的动作。鉴于这些动作完全是实现定义的，早期提案只是说明动作何时可能发生以及如何检测它们的发生，而不是说明它们是什么。这对符合规范的应用程序几乎没有或根本没有用处，因此本卷 POSIX.1-2024 不做此区分。

在大多数历史实现中，实现定义的动作通常包括在进程的当前工作目录中创建名为 core 的文件。此文件包含进程内存的映像，以及关于进程的描述性信息，可能足以重建进程在收到信号时的状态。

如果进程是设置用户 ID 的且当前用户不是程序的所有者，或者进程是设置组 ID 的且用户的组中没有与程序的组匹配的组，或者用户没有在当前目录中写入的权限，则创建 core 文件存在潜在的安全问题。在这种情况下，实现要么不应创建 core 文件，要么应使其对用户不可读。

尽管本卷 POSIX.1-2024 对此功能保持沉默，但建议应用程序不要创建名为 core 的文件，因为在许多实现中存在潜在冲突。某些实现使用 core 以外的名称作为文件名；例如，通过将进程 ID 附加到文件名。

终止进程 (Terminating a Process)

重要的是，所述进程终止的后果无论进程是调用了 _exit()（可能通过 exit() 间接调用）还是因信号或其他原因被终止，都应发生。请注意，在 exit() 的具体情况下，这意味着传递给 exit() 的 status 参数与传递给 _exit() 的 status 参数以相同的方式被对待。

C 以外的语言可能具有不同于 C 语言 exit() 函数的其他终止原语，并且以这种语言编写的程序应使用其原生终止原语，但这些原语应具有 _exit() 所述行为作为其功能的一部分。然而，C 以外的语言的实现不在本版本的本卷 POSIX.1-2024 的范围内。

按照 ISO C 标准的要求，从 main() 使用 return 与使用返回的值调用 exit() 具有相同的行为（除了与语言作用域问题有关的方面）。到达 main() 函数的末尾与调用 exit(0) 具有相同的行为。

参数 status 的零值（或 EXIT_SUCCESS，它被要求为零）按惯例指示成功终止。这对应于 ISO C 标准中对 exit() 的规定。该惯例被 make 和各种 shell 等实用程序遵循，它们将子进程的零状态解释为成功。因此，当应用程序不成功地终止时，不应调用 exit(0) 或 _exit(0)；例如，在信号捕获函数中。

历史上，继承其父进程在未等待它们的情况下已终止的子进程的实现定义进程被称为 init，其进程 ID 为 1。

当控制进程终止时向前台进程组发送 SIGHUP 对应于一些不同的历史实现。在 System V 中，内核在（本质上）控制进程终止时发送 SIGHUP。在 4.2 BSD 中，内核在这种情况下不发送 SIGHUP，但控制进程的终止通常被系统守护进程注意到，该守护进程安排使用 vhangup() 函数向前台进程组发送 SIGHUP。然而，在 4.2 BSD 中，由于支持作业控制的 shell 的行为，控制进程通常是其进程组中没有其他进程的 shell。因此，在此类系统中使 _exit() 以这种方式行为的更改不应导致现有应用程序出现问题。

进程的终止可能以两种方式之一导致进程组成为孤儿进程组。进程组与其组外的父进程的连接取决于父进程及其子进程两者。因此，进程组可能因组外最后一个连接的父进程终止而成为孤儿，或因父进程的最后一个直接后代终止而成为孤儿。在任一情况下，如果进程的终止导致进程组成为孤儿进程组，则组内的进程与其作业控制 shell 断开连接，该 shell 不再有任何关于进程组存在的信息。组内被停止的进程将永远搁置。为了避免此问题，包含被停止进程的新成为孤儿的进程组被发送 SIGHUP 信号和 SIGCONT 信号，以指示它们已与其会话断开连接。SIGHUP 信号导致进程组成员终止，除非它们正在捕获或忽略 SIGHUP。在大多数情况下，如果进程组的任何成员被停止，则其所有成员都被停止。

向新成为孤儿的进程组的成员发送 SIGHUP 和 SIGCONT 信号的动作类似于 4.2 BSD 的动作，后者向退出进程的每个被停止的子进程发送 SIGHUP 和 SIGCONT。如果此类子进程响应 SIGHUP 而退出，则任何额外的后代在该时侯受到类似处理。在本卷 POSIX.1-2024 中，信号同时发送给整个进程组。此外，在本卷 POSIX.1-2024 中（但在 4.2 BSD 中不是），被停止的进程可能成为孤儿，但可能是未成为孤儿的进程组的成员；因此，在 _exit() 时采取的动作必须考虑子进程以外的进程。

进程组可能因调用 setpgid() 或 setsid() 以及因进程终止而成为孤儿进程组。本卷 POSIX.1-2024 不要求在这些情况下发送 SIGHUP 和 SIGCONT，因为与进程终止不同，这些情况不是由不了解作业控制的应用程序意外引起的。实现可以选择在这些情况下发送 SIGHUP 和 SIGCONT 作为扩展；此类扩展必须按 <signal.h> 中的要求被记录。

ISO/IEC 9899:1999 标准添加了 _Exit() 函数，它导致立即程序终止，而不触发信号或 atexit() 注册的函数。在 POSIX.1-2024 中，这等同于 _exit() 函数。
