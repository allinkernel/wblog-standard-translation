XSH 函数：system()

名称 (NAME)

system — 发出命令 (issue a command)

概要 (SYNOPSIS)

#include <stdlib.h>

int system(const char *command);

说明 (DESCRIPTION)

[CX] The functionality described on this reference page is aligned with the ISO C standard. Any conflict between the requirements described here and the ISO C standard is unintentional. This volume of POSIX.1-2024 defers to the ISO C standard.

如果 command 是空指针，system() 函数应确定宿主环境是否具有命令处理器。如果 command 不是空指针，system() 函数应将 command 指向的字符串传递给该命令处理器以按实现定义的方式执行；这随后可能导致调用 system() 的程序以不符合规范的方式行为或终止。

[CX] system() 函数应表现为使用 fork() 创建了子进程，并且子进程使用 execl() 调用 sh 实用程序，如下所示：

execl(<shell path>, "sh", "-c", "--", command, (char *)0);

其中 <shell 路径> 是 sh 实用程序的未指定路径名。用 pthread_atfork() 注册的处理器是否作为子进程创建的一部分被调用是实现定义的。

system() 函数在等待命令终止时应忽略 SIGINT 和 SIGQUIT 信号，并应阻塞 SIGCHLD 信号。如果这可能导致应用程序错过本来会杀死它的信号，则应用程序应检查 system() 的返回值，并在命令因收到信号而终止时采取对应用程序适当的任何动作。

system() 函数不应影响调用进程的任何子进程的终止状态，除了它自己创建的那个或那些进程。

system() 函数在子进程终止之前不应返回。

如果从多个线程并发调用 system()，以下情况是未指定的：

  • 每次调用是否独立地保存和恢复 SIGINT 和 SIGQUIT 信号的处置，或者

  • 在一组并发调用中，最后一次调用返回后生效的处置是否是进入第一次调用时生效的那些处置。

如果线程在处于对 system() 的调用中时被取消，则子进程是被终止并等待，还是被留下继续运行，是未指定的。

返回值 (RETURN VALUE)

如果 command 是空指针，system() 应返回非零以指示命令处理器可用，如果没有可用的则返回零。[CX] 当 command 为 NULL 时，system() 函数应始终返回非零。

[CX] 如果 command 不是空指针，system() 应以 waitpid() 规定的格式返回命令语言解释器的终止状态。终止状态应如为 sh 实用程序定义的那样；否则，终止状态是未指定的。如果某些错误阻止命令语言解释器在子进程创建后执行，则 system() 的返回值应如同命令语言解释器使用 exit(127) 或 _exit(127) 终止一样。如果无法创建子进程，或者无法获得命令语言解释器的终止状态，system() 应返回 -1 并设置 errno 以指示错误。

错误 (ERRORS)

[CX] system() 函数可以设置 fork() 所述的 errno 值。

此外，system() 在以下情况下可以失败：

[ECHILD]
[CX] 由 system() 创建的子进程的状态不再可用。

应用程序用法 (APPLICATION USAGE)

如果 system() 的返回值不是 -1，则可以通过使用 <sys/wait.h> 中描述的宏来解码其值。为方便起见，这些宏也在 <stdlib.h> 中提供。

请注意，虽然 system() 在等待子进程终止时必须忽略 SIGINT 和 SIGQUIT 并阻塞 SIGCHLD，但被执行的命令中的信号处理按 fork() 和 exec 的规定进行。例如，如果在调用 system() 时 SIGINT 正被捕获或被设置为 SIG_DFL，则子进程以 SIGINT 处理设置为 SIG_DFL 启动。

在父进程中忽略 SIGINT 和 SIGQUIT 防止了当被执行的命令忽略或捕获其中一个信号时的协调问题（例如两个进程从同一终端读取）。当用户已向应用程序给出要同步执行的命令时（如在许多交互式应用程序中的 '!' 命令），这通常也是正确的动作。在任一情况下，信号应仅递送给子进程，而不是应用程序本身。有一种情况忽略信号可能产生低于期望的效果。这是当应用程序使用 system() 执行对用户不可见的某些任务时。如果用户在以这种方式使用 system() 时键入了中断字符（例如 "^C"），人们会期望应用程序被杀死，但只有被执行的命令被杀死。以这种方式使用 system() 的应用程序应仔细检查 system() 的返回状态以查看被执行的命令是否成功，并且应在命令失败时采取适当的动作。

在等待子进程终止时阻塞 SIGCHLD 防止应用程序在 system() 自己获得状态之前捕获信号并从 system() 的子进程获得状态。

实用程序最终被执行的上下文可能不同于调用 system() 时的上下文。例如，设置了 FD_CLOEXEC 或 FD_CLOFORK 标志的文件描述符被关闭，并且进程 ID 和父进程 ID 不同。此外，如果被执行的实用程序更改其环境变量或其当前工作目录，该更改不会反映在调用者的上下文中。

没有定义的方式让应用程序找到 shell 的具体路径。然而，confstr() 可以提供 PATH 的一个值，该值保证能找到 sh 实用程序。

虽然 system() 被要求是线程安全的，但建议避免从多个线程并发调用，因为 system() 不被要求在重叠调用集合之间协调 SIGINT 和 SIGQUIT 信号处置的保存和恢复，因此信号可能在最后一次调用返回后被设置为忽略。应用程序还应避免在线程处于对 system() 的调用中时取消它，因为在那种情况下子进程可能被留下继续运行。此外，如果另一个线程更改 SIGCHLD 信号的处置，对 signal() 的调用可能产生意外结果。

原理 (RATIONALE)

system() 函数不应被已设置用户（或组）ID 特权的程序使用。应改用 fork() 和 exec 函数族（execlp() 和 execvp() 除外）。这防止对用户环境的任何不可预见的操纵，这些操纵可能导致执行调用程序未预期的命令。

对 system() 函数有三层规范。ISO C 标准给出最基本的。它要求函数存在，并定义了应用程序查询命令语言解释器是否存在的方式。它没有说明命令语言或解释命令的环境。

POSIX.1-2024 对 system() 施加了额外的限制。它要求如果存在命令语言解释器，则环境必须按 fork() 和 exec 的规定。这确保，例如，close-on-exec 起作用，进程拥有的文件锁不被继承，并且进程 ID 不同。它还规定了当命令行可以运行时 system() 的返回值，从而给应用程序一些关于命令完成状态的信息。

最后，POSIX.1-2024 要求命令按 POSIX.1-2024 的 Shell 和实用程序卷中定义的 shell 命令语言被解释。

请注意，system(NULL) 被要求返回非零，指示存在命令语言解释器。乍一看，这似乎与允许 system(NULL) 返回零的 ISO C 标准冲突。然而，没有冲突。系统必须具有命令语言解释器，如果没有，则是不符合规范的。因此，只要理解如果 system(NULL) 返回零则该实现不符合 POSIX.1-2024，此类系统上的 system() 函数实现 ISO C 标准规定的行为是可允许的。

明确决定的是，当 command 为 NULL 时，不应要求 system() 检查以确保命令语言解释器确实以正确的模式存在、有足够的进程来执行它等等。system(NULL) 调用理论上可以检查诸如太多现有子进程之类的问题并返回零。然而，由于这种（大概）短暂的情况而返回零是不恰当的。如果存在不受此应用程序控制且会导致任何 system() 调用失败的情况，则该系统已被视为不符合规范。

早期草案要求或允许 system() 在因信号被中断时以 errno 设置为 [EINTR] 返回。此错误返回被移除，并且添加了 system() 在子进程终止之前不返回的要求。这意味着如果 system() 中的 waitpid() 调用以 errno 设置为 [EINTR] 退出，system() 必须重新发出 waitpid()。此更改出于两个原因：

  1. 如果 system() 返回 [EINTR]，应用程序除了调用 wait() 之外没有清理的方式，而那可能具有返回除 system() 启动的那个子进程以外的子进程状态的不好效果。

  2. 虽然它可能要求更改某些历史实现，但那些实现已经必须更改，因为它们使用 wait() 而不是 waitpid()。

请注意，如果应用程序正在捕获 SIGCHLD 信号，它将在成功的 system() 调用返回之前收到此类信号。

为了符合 POSIX.1-2024，system() 必须使用 waitpid() 或某些类似的函数，而不是 wait()。

以下代码示例说明 system() 如何在符合 POSIX.1-2024 的实现上被实现。

int system(const char *cmd)
{
    int stat;
    pid_t pid;
    struct sigaction sa, savintr, savequit;
    sigset_t saveblock;
    if (cmd == NULL)
        return(1);
    sa.sa_handler = SIG_IGN;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;
    sigemptyset(&savintr.sa_mask);
    sigemptyset(&savequit.sa_mask);
    sigaction(SIGINT, &sa, &savintr);
    sigaction(SIGQUIT, &sa, &savequit);
    sigaddset(&sa.sa_mask, SIGCHLD);
    pthread_sigmask(SIG_BLOCK, &sa.sa_mask, &saveblock);
    if ((pid = fork()) == 0) {
        sigaction(SIGINT, &savintr, (struct sigaction *)0);
        sigaction(SIGQUIT, &savequit, (struct sigaction *)0);
        sigprocmask(SIG_SETMASK, &saveblock, (sigset_t *)0);
        execl("/bin/sh", "sh", "-c", "--", cmd, (char *)0);
        _exit(127);
    }
    if (pid == -1) {
        stat = -1; /* errno comes from fork() */
    } else {
        while (waitpid(pid, &stat, 0) == -1) {
            if (errno != EINTR){
                stat = -1;
                break;
            }
        }
    }
    sigaction(SIGINT, &savintr, (struct sigaction *)0);
    sigaction(SIGQUIT, &savequit, (struct sigaction *)0);
    sigprocmask(SIG_SETMASK, &saveblock, (sigset_t *)0);
    return(stat);
}

请注意，虽然 system() 的特定实现（如上述）可以假定 shell 的特定路径，但此类路径在另一个系统上不一定是有效的。上述示例不可移植，也不打算可移植。

本标准的早期版本不要求 system() 是线程安全的，因为它更改 SIGINT 和 SIGQUIT 信号的进程范围处置。现在要求它是线程安全的以与 ISO C 标准保持一致，后者（自 2011 年引入线程以来）要求它避免数据竞争。然而，该函数不被要求在重叠调用集合之间协调 SIGINT 和 SIGQUIT 信号处置的保存和恢复，并且上述示例也没有这样做。该示例在调用线程被取消时也不终止并等待子进程，因此在那种情况下会泄漏进程 ID。

一位评审者建议 system() 的实现可能希望使用诸如 SHELL 之类的环境变量来确定使用哪个命令解释器。假定的实现将使用默认命令解释器，如果环境变量指定的那个不可用。这将允许用户在使用提示使用 system() 处理命令行的应用程序时指定不同的命令解释器。此类实现是不鼓励的。如果替代命令解释器不遵循 POSIX.1-2024 的 Shell 和实用程序卷中规定的命令行语法，则更改 SHELL 将使 system() 不符合规范。这将影响期望 system() 具有规定行为的应用程序，并且由于 POSIX.1-2024 的 Shell 和实用程序卷没有提到 SHELL 影响 system()，应用程序将不知道它需要取消设置 SHELL 。

本标准的早期版本要求 command 字符串作为 "-c" 之后的下一个参数传递（省略 "--"）。这意味着可移植应用程序需要注意不要传递以 <hyphen-minus>（'-'）或 <plus-sign>（'+'）开头的命令字符串，因为它随后会被解释为包含选项。现在实现被要求传递 "--"，应用程序不再需要这样做。
