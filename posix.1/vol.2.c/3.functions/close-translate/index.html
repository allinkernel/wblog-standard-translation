XSH 函数：close()

名称

close, posix_close — 关闭一个文件描述符

概要

#include <unistd.h>

int close(int fildes);
int posix_close(int fildes, int flag);

说明

close() 函数应释放由 fildes 指示的文件描述符。释放意味着使该文件描述符可被后续对 open() 或其他分配文件描述符的函数的调用所返回。调用进程在该文件描述符关联的文件上拥有的所有进程所有的文件锁应被解锁。

如果 close() 被一个将被捕获的信号中断，那么它返回 -1 且 errno 设为 [EINTR] 且 fildes 保持打开，还是返回 -1 且 errno 设为 [EINPROGRESS] 且 fildes 被关闭，还是返回 0 以表示成功完成，是未指定的；除非如果 POSIX_CLOSE_RESTART 被定义为 0，那么返回 -1 且 errno 设为 [EINTR] 且 fildes 保持打开这一选项不应发生。如果 close() 返回 -1 且 errno 设为 [EINTR]，那么 fildes 随后是否可以被无错误地传给除 close() 或 posix_close() 之外的任何函数是未指定的。对于所有其他错误情形（[EBADF] 且 fildes 无效的情况除外），fildes 应被关闭。如果即使 close 操作不完整 fildes 也被关闭了，那么 close 操作应异步继续，且进程应不再有能力跟踪 close 操作的完成或最终状态。

当与管道或 FIFO 特殊文件关联的所有文件描述符都被关闭时，管道或 FIFO 中剩余的任何数据应被丢弃。

当与一个打开文件描述关联的所有文件描述符都被关闭时，该打开文件描述应被释放。

如果文件的链接计数为 0，当与该文件关联的所有文件描述符都被关闭时，该文件占用的空间应被释放，且该文件不应再可访问。

[XSI] 如果 fildes 引用伪终端的管理端，且这是最后一次关闭，则应向伪终端的附属端是其控制终端的控制进程（如果有）发送 SIGHUP 信号。关闭伪终端的管理端是否刷新所有排队中的输入和输出是未指定的。

当调用 close() 时，如果针对 fildes 有一个未完成的可取消异步 I/O 操作，那么该 I/O 操作可以被取消。未被取消的 I/O 操作如同 close() 操作尚未发生一样完成。所有未被取消的操作应如同 close() 阻塞直到这些操作完成一样完成。close() 操作本身不必阻塞等待此类 I/O 完成。是否有任何 I/O 操作被取消，以及在 close() 时哪些 I/O 操作可以被取消，是实现定义的。

如果内存映射文件 [SHM] 或共享内存对象 在最后一次关闭时仍被引用（即，某个进程将其映射了），那么内存对象的全部内容应持续存在，直到内存对象不再被引用。如果这是内存映射文件 [SHM] 或共享内存对象 的最后一次关闭，且该关闭导致内存对象不再被引用，并且该内存对象已被取消链接，那么该内存对象应被移除。

当与套接字关联的所有文件描述符都被关闭时，该套接字应被销毁。如果该套接字处于连接模式，且为该套接字设置了具有非零停留时间的 SO_LINGER 选项，并且该套接字有未传输的数据，那么 close() 应阻塞最多当前的停留时间间隔，直到所有数据都被传输。

posix_close() 函数应等同于 close() 函数，但基于 flag 参数的如下所述修改除外。如果 flag 为 0，那么 posix_close() 不应返回 -1 且 errno 设为 [EINTR]，这暗示 fildes 将总是被关闭（[EBADF] 且 fildes 无效的情况除外）。如果 flag 包含 POSIX_CLOSE_RESTART 且 POSIX_CLOSE_RESTART 被定义为非零值，并且 posix_close() 被一个将被捕获的信号中断，那么 posix_close() 可以返回 -1 且 errno 设为 [EINTR]，在这种情况下 fildes 应保持打开；然而，fildes 随后是否可以被无错误地传给除 close() 或 posix_close() 之外的任何函数是未指定的。如果 flag 无效，posix_close() 可以失败且 errno 设为 [EINVAL]，但除此之外应表现得如同 flag 为 0 并关闭 fildes。

返回值

成功完成时，应返回 0；否则，应返回 -1 并将 errno 设为指示错误。

错误

如果以下情况，close() 和 posix_close() 函数应失败：

[EBADF]
fildes 参数不是一个打开的文件描述符。
[EINPROGRESS]
该函数被信号中断，且 fildes 已被关闭，但 close 操作仍在异步继续。

如果以下情况，close() 和 posix_close() 函数可以失败：

[EINTR]
该函数被信号中断，POSIX_CLOSE_RESTART 被定义为非零，并且（在 posix_close() 的情况下）flag 参数包含 POSIX_CLOSE_RESTART，在这种情况下 fildes 仍然打开。
[EIO]
在向文件系统读取或写入时发生了 I/O 错误。

如果以下情况，posix_close() 函数可以失败：

[EINVAL]
flag 参数的值无效。

close() 和 posix_close() 函数不应返回 [EAGAIN] 或 [EWOULDBLOCK] 错误。如果 POSIX_CLOSE_RESTART 为零，close() 函数不应返回 [EINTR] 错误。posix_close() 函数不应返回 [EINTR] 错误，除非 flag 包含非零的 POSIX_CLOSE_RESTART。

示例

重新分配文件描述符 (Reassigning a File Descriptor)

下面的示例关闭与当前进程的标准输出关联的文件描述符，将标准输出重新分配给一个新的文件描述符，并关闭原始文件描述符以进行清理。此示例假定文件描述符 0（即标准输入的描述符）未被关闭。

#include <unistd.h>
...
int pfd;
...
close(1);
dup(pfd);
close(pfd);
...

顺便说一下，这恰恰是可以使用以下方式实现的：

dup2(pfd, 1);
close(pfd);
关闭文件描述符 (Closing a File Descriptor)

在下面的示例中，在尝试将该文件描述符与一个流关联未成功之后，使用 close() 来关闭一个文件描述符。

#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>
 
#define LOCKFILE "/etc/ptmp"
...
int pfd;
FILE *fpfd;
...
if ((fpfd = fdopen (pfd, "w")) == NULL) {
    close(pfd);
    unlink(LOCKFILE);
    exit(1);
}
...

应用程序用法 (APPLICATION USAGE)

曾使用 stdio 例程 fopen() 打开文件的应用程序应使用相应的 fclose() 例程而不是 close()。一旦文件被关闭，文件描述符便不再存在，因为与其对应的整数不再引用文件。

实现可以使用必须被继承到子进程中的文件描述符，以使子进程保持符合性，例如用于消息目录或跟踪目的。因此，对任意整数调用 close() 的应用程序有非符合行为的风险，并且 close() 只能可移植地用于应用程序通过显式操作获得的文件描述符值，以及对应于标准文件流的三个文件描述符。在多线程父应用程序中，为了避免将意外文件描述符泄漏到子进程中的竞争条件，在 fork() 之后、exec 调用之前循环调用 close() 的做法因此是不安全的，取而代之应通过以设置 FD_CLOEXEC 位的方式打开所有文件描述符来应对该竞争，除非该文件描述符意在跨 exec 继承。

对文件描述符 STDIN_FILENO、STDOUT_FILENO 或 STDERR_FILENO 使用 close() 之后，应立即进行重新打开这些文件描述符的操作。如果这些文件描述符中的任何一个保持在关闭状态（例如，来自 perror() 的 [EBADF] 错误），或者如果应用程序稍后不相关的 open() 或类似调用意外地将一个文件分配给了这些知名文件描述符之一，将产生意外行为。此外，close() 后跟重新打开操作（例如 open()、dup() 等）不是原子的；应使用 dup2() 来更改标准文件描述符。

理由 (RATIONALE)

应不鼓励使用可中断的设备关闭例程，以避免文件描述符的隐式关闭（例如通过 exec、进程终止或 dup2()）带来的问题。本卷 POSIX.1-2024 仅意图通过为带非零 POSIX_CLOSE_RESTART 的 close() 和 posix_close() 指定 [EINTR] 错误条件来允许此类行为，以允许应用程序在收到中断后以可移植的方式恢复等待与 close 操作相关联的事件（例如，磁带驱动器倒带）。本标准还允许实现在不选择提供重启被中断的 close 操作的方式时，将 POSIX_CLOSE_RESTART 定义为 0。尽管在 [EINTR] 上文件描述符保持打开，但它可能不再可用；也就是说，将其传给除 close() 或 posix_close() 之外的任何函数可能导致诸如 [EIO] 的错误。如果应用程序必须保证数据不会丢失，建议应用程序在 close 操作之前使用 fsync() 或 fdatasync()，而不是让 close 操作处理挂起的 I/O 并冒中断的风险。

本标准的早期版本在诸如 [EINTR] 和 [EIO] 的错误之后将 fildes 的状态留作未指定；并且实现之间在 close() 在 [EINTR] 之后是否将 fildes 保持打开方面存在差异。一旦引入线程，这便令人不满意，因为多线程应用程序需要知道 fildes 是否已被关闭。应用程序不能盲目地再次调用 close()，因为如果 fildes 已被第一次调用关闭，另一个线程可能已被分配了与 fildes 相同值的文件描述符，该文件描述符绝不能被第一个线程关闭。另一方面，从不重试 close() 的替代方案将导致在 close() 未关闭 fildes 的实现中出现文件描述符泄漏，尽管如果进程即将退出或者文件描述符被标记为 FD_CLOEXEC 且进程即将被 exec 替换，此类泄漏可能是无害的。本标准引入了带 flag 参数的 posix_close()，该参数允许在两种可能的错误行为之间进行选择，并将 close() 实现两种行为中的哪一种留作未指定（尽管保证是 posix_close() 的两种行为之一，而不是像本标准早期版本那样将事情完全留作未指定）。

注意，本标准要求 close() 和 posix_close() 必须在 [EINTR] 之后将 fildes 保持打开（在允许 [EINTR] 的情况下），并且必须无论所有其他错误都关闭文件描述符（[EBADF] 且 fildes 已经无效的情况除外）。一般而言，可移植的应用程序应仅在检查 [EINTR] 之后重试 close()（并且在将 POSIX_CLOSE_RESTART 定义为零的实现上，此重试循环将是死代码），并且如果不尝试重试循环则有文件描述符泄漏的风险。还应注意到，仅当 close() 可以被中断时 [EINTR] 才可能发生；如果没有安装信号处理程序，那么 close() 将不会被中断。相反，如果单线程应用程序可以保证没有文件描述符在信号处理程序中被打开或关闭，那么不检查 [EINTR] 的重试循环将是无害的（因为重试将以 [EBADF] 失败），但要保证没有外部库引入线程的使用可能是困难的。对于将仅在被定义为 0 的 POSIX_CLOSE_RESTART 的系统上使用的应用程序，还有额外的保证。这些观察应有助于确定应用程序是否需要审计其 close() 调用以替换为 posix_close()。

还应注意到，要求 posix_close() 在 flag 为 0 时即使报告了错误也总是关闭 fildes，与要求 fclose() 即使刷新数据时遇到错误也总是释放流是类似的。

以前总是关闭 fildes 的实现可以通过在 close() 中将 [EINTR] 转换为 [EINPROGRESS] 来满足新要求；并且可以将 POSIX_CLOSE_RESTART 定义为 0，而不必添加重启语义。另一方面，以前在 [EINTR] 上将 fildes 保持打开的实现可以将其映射到带 POSIX_CLOSE_RESTART 的 posix_close()，并且必须添加 flag 为 0 时 posix_close() 的语义；一种可能性是调用原始 close() 实现，检查失败，并在 [EINTR] 上，使用类似于 dup2() 的操作，用另一个可以通过对原始 close() 的另一次调用立即关闭的文件描述符替换不完整的 close 操作，所有这一切都在返回到应用程序之前完成。无论哪种方式，close() 应总是映射到 posix_close() 的两种行为之一，并且鼓励实现保持 close() 的行为不变，以免破坏依赖于本标准旧版本未指定的行为的旧应用程序的特定于实现的预期。

标准制定者曾考虑引入一个线程局部变量，close() 在返回 -1 时将设置该变量以指示它是否已关闭 fildes。然而，这被否决了，取而代之的是更简单的解决方案：收紧 close() 以保证 fildes 除 [EINTR] 外总是被关闭，并通过添加 posix_close() 来暴露是否期望 [EINTR] 的选择。此外，虽然名称 posix_close() 对本标准来说是新的，但它让人联想到至少一个实现，该实现引入了一个名为 close_nocancel() 的替代系统调用，以允许应用程序选择是否需要重启语义。

另一个考虑是，实现是否可能作为扩展返回 [EAGAIN]，以及在这种情况下是否应要求 close() 保持文件描述符打开，因为 [EAGAIN] 通常意味着应重试某个操作。似乎任何实现都极不可能有合法理由返回 [EAGAIN] 或 [EWOULDBLOCK]，因此这一要求将意味着应用程序必须为永远不会使用的错误情况包含代码。因此，close() 现在被禁止返回 [EAGAIN] 和 [EWOULDBLOCK] 错误。

注意，要求 close() 在套接字上阻塞最多当前的停留时间间隔并不以 O_NONBLOCK 设置为条件。

标准制定者否决了向标准添加 closefrom() 的提案。因为本标准允许实现使用继承的文件描述符作为为子进程提供符合环境的手段，所以不可能标准化一个关闭高于某个值的任意文件描述符同时仍保证符合环境的接口。
