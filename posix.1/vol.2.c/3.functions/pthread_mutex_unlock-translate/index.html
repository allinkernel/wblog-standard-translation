XSH 函数：pthread_mutex_unlock()

名称 (NAME)

pthread_mutex_lock、pthread_mutex_trylock、pthread_mutex_unlock — 锁定和解锁互斥量

概要 (SYNOPSIS)

#include <pthread.h>

int pthread_mutex_lock(pthread_mutex_t *mutex);
int pthread_mutex_trylock(pthread_mutex_t *mutex);
int pthread_mutex_unlock(pthread_mutex_t *mutex);

说明 (DESCRIPTION)

mutex 所引用的互斥量对象应通过对 pthread_mutex_lock() 的调用而锁定，该调用返回零或 [EOWNERDEAD]。如果该互斥量已被另一线程锁定，则调用线程应阻塞，直到该互斥量变为可用。此操作返回时，mutex 所引用的互斥量对象应处于锁定状态，且调用线程为其所有者。如果线程试图重新锁定它已锁定的互斥量，pthread_mutex_lock() 的行为应如下表 重新锁定 列所述。如果线程试图解锁它未锁定的互斥量或已解锁的互斥量，pthread_mutex_unlock() 的行为应如下表 非所有者解锁 列所述。

†
如果互斥量类型是 PTHREAD_MUTEX_DEFAULT，则 pthread_mutex_lock() 的行为可以对应于上表所述的三种其他标准互斥量类型之一。如果它不对应于这三种类型之一，则对于标记 † 的情况，行为未定义。

在表格指明递归行为之处，该互斥量应维持锁计数的概念。当线程首次成功获取互斥量时，锁计数应置为一。每当线程重新锁定该互斥量时，锁计数应加一。每次线程解锁该互斥量时，锁计数应减一。当锁计数达到零时，该互斥量应变为可供其他线程获取。

pthread_mutex_trylock() 函数应等价于 pthread_mutex_lock()，不同之处在于：如果 mutex 所引用的互斥量对象当前已被锁定（被任何线程锁定，包括当前线程），则调用应立即返回。如果互斥量类型是 PTHREAD_MUTEX_RECURSIVE 且该互斥量当前由调用线程拥有，则互斥量锁计数应加一，且 pthread_mutex_trylock() 函数应立即返回成功。

pthread_mutex_unlock() 函数应释放 mutex 所引用的互斥量对象。互斥量被释放的方式取决于该互斥量的类型属性。如果在调用 pthread_mutex_unlock() 时存在阻塞在 mutex 所引用的互斥量对象上的线程，导致该互斥量变为可用，则调度策略应决定哪个线程应获取该互斥量。

（对于 PTHREAD_MUTEX_RECURSIVE 互斥量，当计数达到零且调用线程不再持有该互斥量的任何锁时，该互斥量应变为可用。）

如果向等待互斥量的线程递送信号，则从信号处理程序返回后，该线程应如同未被中断一样继续等待该互斥量。

如果 mutex 是健壮互斥量，且包含拥有线程的进程在持有互斥量锁期间终止，则对 pthread_mutex_lock() 的调用应返回错误值 [EOWNERDEAD]。如果 mutex 是健壮互斥量，且拥有线程在持有互斥量锁期间终止，则对 pthread_mutex_lock() 的调用可以返回错误值 [EOWNERDEAD]，即使拥有线程所在的进程尚未终止。在这些情况下，互斥量应由调用线程锁定，但其保护的状态被标记为不一致。应用程序应确保该状态被恢复一致以供复用，并在完成后调用 pthread_mutex_consistent()。如果应用程序无法恢复该状态，则应在未先调用 pthread_mutex_consistent() 的情况下解锁该互斥量，此后该互斥量被标记为永久不可用。

如果 mutex 未引用已初始化的互斥量对象，则 pthread_mutex_lock()、pthread_mutex_trylock() 和 pthread_mutex_unlock() 的行为未定义。

返回值 (RETURN VALUE)

如果成功，pthread_mutex_lock()、pthread_mutex_trylock() 和 pthread_mutex_unlock() 函数应返回零；否则，应返回错误号以指示错误。

错误 (ERRORS)

pthread_mutex_lock() 和 pthread_mutex_trylock() 函数在以下情况下应失败：

[EAGAIN]
由于已超过 mutex 的递归锁最大数量，无法获取该互斥量。
[EAGAIN]
该互斥量是健壮互斥量，且可用于被拥有的健壮互斥量的系统资源将被超出。
[EINVAL]
[RPP|TPP] 创建 mutex 时，协议属性取值为 PTHREAD_PRIO_PROTECT，且调用线程的优先级高于该互斥量当前的优先级上限。
[ENOTRECOVERABLE]
该互斥量保护的状态不可恢复。
[EOWNERDEAD]
该互斥量是健壮互斥量，且包含先前拥有线程的进程在持有互斥量锁期间终止。互斥量锁应由调用线程获取，且由新所有者负责使状态保持一致。

pthread_mutex_lock() 函数在以下情况下应失败：

[EDEADLK]
互斥量类型是 PTHREAD_MUTEX_ERRORCHECK，且当前线程已拥有该互斥量。

pthread_mutex_trylock() 函数在以下情况下应失败：

[EBUSY]
由于 mutex 已被锁定，无法获取它。

pthread_mutex_unlock() 函数在以下情况下应失败：

[EPERM]
互斥量类型是 PTHREAD_MUTEX_ERRORCHECK 或 PTHREAD_MUTEX_RECURSIVE，或者该互斥量是健壮互斥量，且当前线程不拥有该互斥量。

pthread_mutex_lock() 和 pthread_mutex_trylock() 函数在以下情况下可以失败：

[EOWNERDEAD]
该互斥量是健壮互斥量，且先前拥有线程在持有互斥量锁期间终止。互斥量锁应由调用线程获取，且由新所有者负责使状态保持一致。

pthread_mutex_lock() 函数在以下情况下可以失败：

[EDEADLK]
检测到死锁条件。

这些函数不应返回 [EINTR] 错误码。

应用程序用法 (APPLICATION USAGE)

假定非零返回值是错误的应用程序将需要更新以用于健壮互斥量，因为线程获取保护当前不一致状态的互斥量时的有效返回值是 [EOWNERDEAD]。由于排除了此类错误出现的可能性而不检查错误返回值的应用程序，不应使用健壮互斥量。如果应用程序应同时适用于普通互斥量和健壮互斥量，则它应检查所有返回值的错误条件，并在必要时采取适当行动。

原理 (RATIONALE)

互斥量对象旨在充当低层原语，其他线程同步函数可以在此基础上构建。因此，互斥量的实现应尽可能高效，而这会对接口上可用的特性产生影响。

互斥量函数和互斥量属性的特定默认设置是出于不排除快速、内联的互斥量锁定和解锁实现的愿望。

由于大多数属性仅在线程将要被阻塞时才需要检查，因此属性的使用不会减慢（常见的）互斥量锁定情形。

同样，虽然能够提取互斥量所有者的线程 ID 可能可取，但它需要在每次互斥量被锁定时存储当前线程 ID，而这可能带来不可接受级别的额外开销。类似的论点也适用于 mutex_tryunlock 操作。

关于扩展互斥量类型的进一步原理，请参见 XRAT 线程扩展。

如果实现检测到 mutex 参数指定的值未引用已初始化的互斥量对象，则建议该函数应失败并报告 [EINVAL] 错误。

变更历史 (CHANGE HISTORY)

第 5 版首次发布。为与 POSIX 线程扩展保持一致而包含。

第 6 版 (Issue 6)

pthread_mutex_lock()、pthread_mutex_trylock() 和 pthread_mutex_unlock() 函数被标记为 Threads 选项的一部分。

以下对 POSIX 实现的新要求源于与单一 UNIX 规范的一致性：

  • 尝试重新锁定互斥量时的行为已定义。

为与 IEEE Std 1003.1d-1999 保持一致，pthread_mutex_timedlock() 函数被添加到 SEE ALSO 一节。

应用了 IEEE Std 1003.1-2001/Cor 2-2004 项目 XSH/TC2/D6/98，更新了 ERRORS 一节，使 [EDEADLK] 错误包括死锁条件的检测。RATIONALE 一节也重新措辞，以考虑不符合 XSI 的系统。

第 7 版 (Issue 7)

应用了 SD5-XSH-ERN-43，将 [EINVAL] 错误的 "shall fail" 情形标记为取决于 Thread Priority Protection 选项。

变更来自开放集团技术标准 2006，扩展 API 集第 3 部分。

pthread_mutex_lock()、pthread_mutex_trylock() 和 pthread_mutex_unlock() 函数从 Threads 选项移至 Base。

以下扩展互斥量类型从 XSI 选项移至 Base：

PTHREAD_MUTEX_NORMAL
PTHREAD_MUTEX_ERRORCHECK
PTHREAD_MUTEX_RECURSIVE
PTHREAD_MUTEX_DEFAULT

更新了 DESCRIPTION，以澄清 mutex 未引用已初始化互斥量时的行为。

更新了 ERRORS 一节，以适当地说明所有各种互斥量类型。

应用了 POSIX.1-2008 技术勘误 1 的 XSH/TC1-2008/0461 [121]、XSH/TC1-2008/0462 [92,428] 和 XSH/TC1-2008/0463 [121]。

第 8 版 (Issue 8)

应用了 Austin Group Defect 354，为超出可用于被拥有的健壮互斥量的系统资源添加 [EAGAIN] 错误。

应用了 Austin Group Defect 1115，将 "the thread" 改为 "the calling thread"。
